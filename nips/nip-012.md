# NIP-012: Explained Literals and Deterministic Grounding

## Abstract

NIP-012 defines the mechanisms for evaluating explained literals and establishing deterministic grounding in the Noe Protocol. An explained literal `@x` may be evaluated only when its required context is fully satisfied, evidence is fresh and consistent, and independence groups achieve agreement. This specification defines the conditions for literal explanation, the structure and validation of evidence items, the role of independence groups in consensus, and the promotion of literals into the safe context through the `pi_safe` filter. Evaluation operates exclusively on the safe context, ensuring deterministic semantics and preventing undefined behavior from propagating through the system.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

- `@x` - A literal reference
- `C_rich` - Rich context, containing all available evidence
- `C_safe` - Safe context, containing only promoted and validated literals
- `R_x` - Set of required_context paths for literal `@x`
- `pi_safe` - Safety filter that promotes literals from `C_rich` to `C_safe`
- `V(@x, C)` - Evaluation of literal `@x` in context `C`
- `now_ms` - Current time in milliseconds
- `stale_threshold_ms` - Maximum age for fresh evidence
- `independence_group` - Partition of sensor sources for consistency checking

---

## 1. Purpose

The purpose of NIP-012 is to establish a rigorous framework for evaluating literals in the presence of multiple evidence sources, contextual dependencies, and consistency requirements. Specifically, NIP-012:

1. Defines the conditions under which a literal may be considered "explained" and thus eligible for evaluation
2. Specifies the structure and semantics of evidence items, including confidence, timestamp, source, and independence group information
3. Establishes mechanisms for detecting and handling evidence conflicts both within and across independence groups
4. Defines the `pi_safe` filter that promotes explained literals into the safe context
5. Ensures that evaluation operates exclusively on the safe context, providing deterministic and auditable semantics

---

## 2. Scope

NIP-012 applies to all contexts in which literals must be evaluated in the Noe Protocol. It defines:

- The structure of evidence items associated with literals
- The conditions for a literal to be considered explained
- Freshness requirements for evidence
- Independence group partitioning and consistency checking
- The promotion mechanism from rich context to safe context
- Failure semantics for literals that cannot be explained

NIP-012 does not specify:

- The mechanisms for collecting or asserting evidence (see NIP-009)
- The format of specific literal types or domains
- Application-specific confidence thresholds or decision criteria
- The implementation details of independence group assignment

## 3. Definitions

### 3.1 Explained Literal

An explained literal `@x` is a literal whose required context is fully satisfied in the rich context. Formally:

```
@x is explained iff ∀ path ∈ R_x : path exists in C_rich
```

If any required path is missing from `C_rich`, the literal is not explained and remains undefined.

### 3.2 Evidence Item (AnnotatedLiteral)

An evidence item is a structured record with the following fields:

```
{
  predicate: <string, the literal key e.g. "@sensor_active">,
  value: <boolean or grounded value>,
  timestamp: <integer, UNIX milliseconds>,
  source: <string, identifier of evidence source>,
  confidence: <float, numerical confidence score>,
  meta: <object, optional metadata>
}
```

Each evidence item represents a single observation or assertion about a literal's value. Note that `independence_group` is NOT carried on the evidence item itself — group membership is determined by an external mapping from `source` to group identifier, applied at projection time (see §4.3).

### 3.3 Candidacy

An evidence item is a **candidate** for promotion if it passes three gates:

1. **Freshness**: Its age does not exceed the staleness threshold:
   ```
   fresh(evidence) iff (now_ms - evidence.timestamp) <= tau_stale_ms
   ```
   Evidence that is not fresh is considered stale and MUST NOT be used in evaluation.

2. **Confidence threshold**: Its confidence score meets or exceeds the minimum threshold:
   ```
   confident(evidence) iff evidence.confidence >= theta_thresh
   ```
   The default `theta_thresh` is 0.80. This threshold is a hard gate — evidence below it is rejected before consistency checking begins. Deployments SHOULD cross-reference NIP-017 epistemic thresholds (e.g., `t_shi_min = 0.90`) when configuring per-predicate confidence requirements.

3. **Source authority** (if configured): The evidence source is in the allow-list for the given predicate:
   ```
   authorised(evidence) iff auth_map[evidence.predicate] is undefined
                         OR evidence.source in auth_map[evidence.predicate]
   ```
   The `auth_map` is an optional per-predicate dictionary of authorised source sets. When active, evidence from unauthorised sources is silently rejected. See §9.7.

### 3.4 Independence Group

An independence group is a partition of sensor sources designed to detect systematic failures or adversarial behavior. Sources within the same group are assumed to be correlated and should provide consistent observations. Sources in different groups are assumed to be independent.

Group membership is determined by an external `independence_groups` mapping (source → group_id), NOT by a field on each evidence item. This separation allows group assignments to change without modifying evidence records. If no mapping is provided, each source is treated as its own group (i.e., `group_id = source`).

### 3.5 Leading Edge Window

Consistency checking does NOT operate on all candidate evidence. Instead, it uses a **leading edge window**: the newest observation timestamp (`max_t`) is identified, and only evidence within `tau_window_ms` of `max_t` is considered:

```
leading_edge(items) = { item ∈ items | (max_t - item.timestamp) <= tau_window_ms }
```

The default `tau_window_ms` is 100ms. Evidence older than the leading edge is silently ignored (not treated as stale — it was simply superseded by newer observations). This prevents old-but-not-yet-stale readings from causing false conflicts with current observations.

### 3.6 Internal Consistency

Evidence within a single independence group is internally consistent if all items **in the leading edge** from that group agree on the literal's value:

```
internally_consistent(group) iff ∀ items ∈ leading_edge(group) :
  item₁.value == item₂.value
```

A conflict within a group violates internal consistency.

### 3.7 Cross-Group Consistency

Evidence across all independence groups is cross-group consistent if all groups with leading-edge evidence agree on the literal's value:

```
cross_group_consistent iff ∀ groups with leading_edge evidence :
  group₁.value == group₂.value
```

A conflict between groups violates cross-group consistency.

### 3.8 Safe Context Promotion

A literal is promoted into the safe context `C_safe` through the `pi_safe` filter if and only if:

1. The literal is explained in `C_rich`
2. All evidence is fresh
3. All evidence within each independence group is internally consistent
4. All evidence across independence groups is cross-group consistent

Literals that do not meet these conditions are excluded from `C_safe`.

## 4. Specification

### 4.1 Literal Explanation

To determine if a literal `@x` is explained:

1. Obtain the literal's definition `D_x` from the registry
2. Extract the required_context paths `R_x` from the definition
3. Check that each path in `R_x` exists and is accessible in `C_rich`
4. If all paths exist, `@x` is explained
5. If any path is missing, `@x` is not explained and must be treated as undefined

### 4.2 Candidate Filtering

Each literal maintains a set of evidence items (AnnotatedLiterals) in `C_rich`. The first stage filters candidates:

1. Validate that each evidence item conforms to the AnnotatedLiteral structure (§3.2)
2. **Freshness gate**: Discard items where `(now_ms - item.timestamp) > tau_stale_ms`
3. **Confidence gate**: Discard items where `item.confidence < theta_thresh` (default 0.80)
4. **Authority gate**: If `auth_map` is configured, discard items from unauthorised sources
5. Group remaining candidates by predicate

### 4.3 Leading Edge and Consistency Checking

For each predicate with candidates:

1. Identify the newest timestamp `max_t` across all candidates for this predicate
2. Collect the **leading edge**: all candidates within `tau_window_ms` (default 100ms) of `max_t`
3. Partition leading edge items by independence group (via external `independence_groups` mapping; default: `group_id = source`)
4. **Internal consistency**: For each group, verify all items agree on value. If any group has conflicting values, suppress the literal
5. **Cross-group consistency**: Verify all groups agree on the same value. If groups disagree, suppress the literal

### 4.4 Promotion via pi_safe

The `pi_safe` filter performs the following steps:

1. Filter all evidence items in `C_rich` through the candidate gates (§4.2)
2. Group candidates by predicate
3. For each predicate, check if the literal is explained (all required context paths present in context)
4. If not explained, exclude from `C_safe`
5. If explained, apply leading edge window and consistency checking (§4.3)
6. If consistency holds across all groups, promote the literal to `C_safe` with its agreed-upon value
7. If any consistency check fails, suppress the literal (it does not appear in `C_safe`)

### 4.6 Evaluation Semantics

Evaluation of literals operates exclusively on `C_safe`:

```
V(@x, C_safe) =
  true    if @x is present in C_safe and its value is true
  false   if @x is present in C_safe and its value is false
  undefined otherwise
```

Literals not present in `C_safe` always evaluate to undefined, regardless of their presence in `C_rich`.

## 5. Rationale

### 5.1 Explained Literals and Context Dependence

The requirement that a literal be "explained" (all required context paths present) reflects the principle that literals do not exist in isolation. Some literals are meaningful only in the presence of other context elements. By enforcing explanation as a precondition for evaluation, NIP-012 prevents undefined behavior from arising due to missing dependencies.

### 5.2 Evidence as Observational Records

The structure of evidence items—including value, confidence, timestamp, source, and independence group—ensures that each observation is traceable and auditable. This enables the system to discriminate between agreement that reflects genuine consistency and apparent agreement that arises from correlated failures or adversarial collusion.

### 5.3 Freshness as a Consistency Measure

Evidence staleness is a proxy for the potential that a literal's true value has changed. By discarding stale evidence, the system avoids anchoring evaluation to outdated observations and maintains alignment with the current state of the world.

### 5.4 Independence Groups as Conflict Detection

Partitioning sources into independence groups allows the system to distinguish between:

- Internal failures (a single sensor malfunction): detected as conflicts within a group
- Systematic failures (multiple correlated sensors): detected as conflicts within a larger group
- Adversarial behavior (coordinated misreporting): detected as conflicts across groups

This layered approach to conflict detection enhances robustness and auditability.

### 5.5 Safety Filter as Invariant Enforcement

The `pi_safe` filter ensures that the safe context `C_safe` maintains strong invariants:

- All literals in `C_safe` are explained
- All literals in `C_safe` are supported by fresh evidence
- All literals in `C_safe` are internally consistent within each independence group
- All literals in `C_safe` are cross-group consistent

These invariants make `C_safe` suitable for use in critical decision logic and enable efficient reasoning about system state.

### 5.6 Deterministic Evaluation

By restricting evaluation to `C_safe`, the system achieves deterministic semantics: the same literal evaluated in the same safe context always produces the same result. This determinism is critical for auditability, reproducibility, and formal verification.

## 6. Examples

### 6.1 Simple Literal Evaluation

Consider a literal `@sensor_active` with required_context paths `["C_local.sensor_config", "C_local.network_status"]`.

1. Both paths exist in `C_rich` → explained
2. Two evidence items present:
   - `{predicate: "@sensor_active", value: true, timestamp: T, source: "cam_1", confidence: 0.95, meta: {}}`
   - `{predicate: "@sensor_active", value: true, timestamp: T+50, source: "lidar_1", confidence: 0.92, meta: {}}`
3. Both pass candidacy gates (fresh, confidence >= 0.80, authorised)
4. Leading edge: max_t = T+50, window = 100ms — both items included
5. Independence groups (via external mapping): cam_1 → "A", lidar_1 → "B"
6. Internal consistency holds for both groups
7. Cross-group consistency holds (both agree on true)
8. Literal is promoted to `C_safe` with value true
9. `V(@sensor_active, C_safe)` = true

### 6.2 Missing Required Context

Consider a literal `@device_ready` with required_context paths `["C_local.device_config", "C_local.calibration_data"]`.

1. `C_local.device_config` exists in `C_rich`, but `C_local.calibration_data` does not
2. Literal is not explained
3. Literal is excluded from `C_safe`
4. `V(@device_ready, C_safe)` = undefined

### 6.3 Stale Evidence

Consider a literal `@system_healthy` with required_context satisfied.

1. Two evidence items present:
   - `{predicate: "@system_healthy", value: true, timestamp: T1, source: "mon_1", confidence: 0.90, meta: {}}` where `(now_ms - T1) > tau_stale_ms`
   - `{predicate: "@system_healthy", value: false, timestamp: T2, source: "mon_2", confidence: 0.88, meta: {}}` where `(now_ms - T2) <= tau_stale_ms`
2. First item fails freshness gate and is discarded
3. Only one candidate remains (value false, confidence 0.88 >= 0.80)
4. Leading edge contains one item — consistency trivially holds
5. Literal is promoted to `C_safe` with value false
6. `V(@system_healthy, C_safe)` = false

### 6.4 Internal Group Conflict

Consider a literal `@network_reachable` with required_context satisfied.

1. Three evidence items, all pass candidacy gates:
   - `{predicate: "@network_reachable", value: true, timestamp: T1, source: "ping_1", confidence: 0.91, meta: {}}`
   - `{predicate: "@network_reachable", value: false, timestamp: T2, source: "ping_2", confidence: 0.87, meta: {}}`
   - `{predicate: "@network_reachable", value: true, timestamp: T3, source: "dns_1", confidence: 0.93, meta: {}}`
2. All within leading edge window (max_t - min_t <= 100ms)
3. Independence groups: ping_1 → "A", ping_2 → "A", dns_1 → "B"
4. Group A has conflicting values (true vs false)
5. Internal consistency fails for group A
6. Literal is suppressed — excluded from `C_safe`
7. `V(@network_reachable, C_safe)` = undefined

### 6.5 Cross-Group Conflict

Consider a literal `@user_authenticated` with required_context satisfied.

1. Two evidence items, both pass candidacy gates:
   - `{predicate: "@user_authenticated", value: true, timestamp: T1, source: "auth_svc_1", confidence: 0.95, meta: {}}`
   - `{predicate: "@user_authenticated", value: false, timestamp: T2, source: "auth_svc_2", confidence: 0.92, meta: {}}`
2. Both within leading edge window
3. Independence groups: auth_svc_1 → "A", auth_svc_2 → "B"
4. Internal consistency holds for both groups (one item each)
5. Groups disagree on value (true vs false)
6. Cross-group consistency fails
7. Literal is suppressed — excluded from `C_safe`
8. `V(@user_authenticated, C_safe)` = undefined

## 7. Conformance Requirements

### 7.1 Literal Definition Registry

All literals must be defined in the registry prior to evaluation. A literal without a definition must not be evaluated, and its absence must be treated as an evaluation failure.

### 7.2 Evidence Item Structure

Every evidence item MUST conform to the AnnotatedLiteral structure (§3.2): predicate, value, timestamp, source, confidence, and meta. Evidence items missing any required field MUST be rejected. Note that `independence_group` is NOT a field on the evidence item — group membership is determined externally (§3.4).

### 7.3 Timestamp Validation

All timestamps must be expressed in milliseconds since Unix epoch. Timestamps must not be in the future. Implementations must establish a reasonable clock skew tolerance.

### 7.4 Independence Group Assignment

Independence groups must be defined a priori. Evidence items referencing undefined independence groups must be rejected. The assignment of sources to independence groups must be deterministic and auditable.

### 7.5 Staleness Threshold

The `stale_threshold_ms` must be configured per system or per literal class. All implementations must consistently apply the same threshold for a given evaluation context.

### 7.6 Safe Context Enforcement

Evaluation must use `C_safe` exclusively. Implementations must not evaluate literals against `C_rich` or any context other than the output of `pi_safe`.

### 7.7 Error Reporting

When a literal cannot be promoted to `C_safe`, implementations must record the reason (missing context, stale evidence, internal conflict, cross-group conflict, or absent from registry). This information must be available for auditing and debugging.

---

## 8. Backwards Compatibility

NIP-012 introduces the concept of explained literals and deterministic grounding. Previous versions of the Noe Protocol did not define a formal framework for evidence validation and context dependence.

Implementations upgrading to NIP-012:

1. Must retroactively assign all existing evidence items an independence group (e.g., based on source or collection mechanism)
2. Must establish a staleness threshold for the deployment environment
3. Must populate literal definitions in the registry for all literals in active use
4. May encounter literals that were previously evaluated in `C_rich` but cannot be promoted to `C_safe` under NIP-012 rules; these literals must now evaluate to undefined
5. Must ensure that all downstream systems are prepared to handle undefined evaluations for literals previously considered defined

The introduction of `pi_safe` as the authoritative filter should be considered a breaking change for systems that previously evaluated literals directly from `C_rich` without validation.

## 9. Security and Safety Considerations

### 9.1 Evidence Spoofing

Adversaries may inject false evidence into `C_rich`. By requiring agreement across independence groups, NIP-012 mitigates this attack. If sources within a group are correlated (e.g., all controlled by an attacker), the adversary can still cause conflicts. Independence groups should be designed such that an attacker cannot simultaneously compromise all sources in a group without detection.

### 9.2 Timing Attacks

An adversary may attempt to exploit evidence timestamps to cause evidence to appear stale or fresh. All systems must implement secure time synchronization (e.g., NTP with authentication) and establish clock skew tolerances.

### 9.3 Denial of Service via Conflicts

An adversary may deliberately cause internal or cross-group conflicts to suppress the promotion of literals to `C_safe`. This forces literals to evaluate to undefined, potentially disrupting system operation. Systems should implement monitoring and alerting for unexplained literal conflicts and should design fallback behaviors for when critical literals are undefined.

### 9.4 Context Dependency Attacks

An adversary may prevent a literal from being explained by removing or corrupting required_context paths in `C_rich`. Systems should implement integrity checks and replicated storage for critical context elements.

### 9.5 Confidence Score Misuse

The default confidence threshold (`theta_thresh = 0.80`) acts as a hard gate before consistency checking (§3.3). Deployments that lower this threshold increase their exposure to low-quality evidence. Systems SHOULD validate that configured thresholds are appropriate for their security model. Confidence gating does NOT substitute for consistency checking — both gates MUST pass.

### 9.6 Independence Group Failures

If all sources in an independence group are simultaneously compromised, that group's evidence becomes untrustworthy. Systems should use additional mechanisms (e.g., Byzantine consensus, quorum voting) to detect and handle group-level failures.

### 9.7 Source Authority Bypass

The `auth_map` (§3.3) restricts which sources may contribute evidence for a given predicate. If `auth_map` is not configured, ALL sources are accepted by default. Deployments in adversarial environments SHOULD configure `auth_map` for all safety-critical predicates. An attacker who can register a new source identifier bypasses authority checks unless the allow-list is maintained independently of source self-reporting.
