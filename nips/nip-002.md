# NIP-002: Glyph Registry Specification

## Abstract

This document defines the canonical glyph registry for the Noe Protocol. The registry is the single source of truth for glyph identity: every glyph's semantic anchor, phonetic form, visual form, operator class, type signature, domain, and tier assignment are determined solely by its entry in `registry.json`. All morphology (NIP-003), grammar (NIP-004), semantics (NIP-005), and higher-layer NIPs resolve glyph identity exclusively through this registry. NIP-002 specifies the metadata schema, domain classification rules, uniqueness requirements, tier placement criteria, versioning rules, lifecycle management, and conformance requirements for `registry.json`.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

## 1. Purpose

The Glyph Registry defines the canonical universe of glyphs in the Noe Protocol. It ensures atomicity (one glyph maps to one meaning), determinism (identical interpretation across agents), interoperability (text, speech, BCI, haptic, and light channels), extensibility (safe addition of new glyphs via NIPs), and stability (no semantic drift over time).

NIP-002 is the authoritative source of truth for glyph identity.

## 2. Scope

### 2.1. In Scope

This specification covers the canonical glyph metadata schema, domain classification rules, glyph uniqueness requirements, tier placement criteria, registry versioning and lifecycle rules, collision prevention requirements, numeric domain separation, and conformance requirements for `registry.json`.

### 2.2. Out of Scope

This document does not define morphology (NIP-003), grammar (NIP-004), semantics (NIP-005), scalar and intensity operators (NIP-006), or numeric logic semantics (NIP-007).

## 3. Definitions

**Glyph:** An atomic symbolic unit registered in `registry.json`. Each glyph has a unique identifier, phonetic form, visual form, semantic domain, and tier assignment.

**Ontology:** The Tier-0 and Tier-1 ontology is the canonical semantic source for all glyph definitions. The ontology provides the formal semantic anchors that `registry.json` implements.

**registry.json:** The machine-readable file implementing the metadata schema defined in Section 5. Every evaluator MUST load this file to resolve glyph identity.

**Domain:** A glyph's semantic category. Each glyph MUST belong to exactly one domain. The canonical domains are: D_struct (structural), D_e (entity), D_s (state/quality), D_action (action/event), D_logic (logical), D_temporal (temporal), D_spatial (spatial), D_epistemic (epistemic), D_normative (normative), D_quantifier (quantifier), D_scalar (scalar), D_demonstrative (demonstrative), and D_numeric (numeric).

**Tier:** A structural classification level. Tier-0 glyphs are required by all evaluators and are globally immutable. Tier-1 glyphs extend the protocol for human/agent cognition. Tier-2 and above are domain-specific extensions.

**Collision:** A conflict between two glyphs in any of: semantics, operator behavior, phonetic similarity, visual similarity, BCI/haptic/light decoding, or human cognitive confusability.

## 4. Specification

### 4.1. Design Principles

#### 4.1.1. Atomicity

Each glyph MUST represent exactly one semantic concept. A glyph MUST NOT shift meaning across contexts, assume multiple operator classes, fuse unrelated interpretations, merge logical and spatial and numeric roles, or perform implicit structural work.

#### 4.1.2. Deterministic Interpretation

Each glyph MUST map deterministically to one semantic anchor, one domain, one type signature, one operator class, one phonetic form, and one visual form. No implicit disambiguation is allowed.

#### 4.1.3. Uniqueness

Two glyphs MUST NOT collide in semantics, operator behavior, phonetic similarity, visual similarity, BCI/haptic/light decoding, or human cognitive confusability. If any collision is detected, the glyph proposal MUST be rejected.

#### 4.1.4. Stability

Once registered, a glyph's semantics, type signature, domain, operator class, phonetic form, and visual form MUST NOT change. If correction is needed, the original glyph MUST be deprecated and a replacement glyph created. The decode path for deprecated glyphs MUST be preserved permanently.

#### 4.1.5. No Implicit Context

Glyph meanings MUST NOT depend on implicit subjects, cultural assumptions, implicit time or location, sentiment, or speaker intent. All defaults MUST be encoded explicitly at higher layers.

### 4.2. Tier Separation

#### 4.2.1. Tier-0: Structural Core

Tier-0 glyphs form the immutable structural core required for deterministic parsing. The complete Tier-0 set, as frozen in `registry.json` V1.0, is:

| Domain | Glyphs | Description |
|--------|--------|-------------|
| D_e | dai | Entity identity |
| D_struct | el, nul, nek, at, sek, da, qua | Identity/equivalence, null/empty, termination, literal marker (glyph ID: lit), scope boundary, clause introduction, interrogative root |
| D_logic | nai, an, ur, khi, nex | Negation, conjunction, disjunction, conditional guard, exclusion |
| D_state | es | Copula / predication |
| D_temporal | nau, ret, tri, qer | Present, past, future, repetition/loop |
| D_spatial | nel, tel, xel, en, tra, fra | Near, far, aligned, containment, ahead, behind |
| D_action | vus, vel, kra | Deliver, receive, integrity/assert |
| D_morph | ko, mek, tok, al, nei | Binder, verbalizer, concrete nominalizer, abstract nominalizer, inversion suffix |

The Tier-0 set is frozen as of v1.0. No Tier-0 glyph MAY be added, removed, renamed, visually altered, or semantically reinterpreted after v1.0.

**Note:** `sha` (certainty), `shi` (knowledge), and `vek` (belief) are Tier-1 epistemic operators (D_epistemic), not Tier-0, per `registry.json` V1.0. `noq` (request) is Tier-1, domain D_action.

#### 4.2.2. Tier-1: Extended Human Layer

Tier-1 includes valence glyphs (fel, dar, nem, zar, vai), sensory modality glyphs (vis, hau, per), WH-forms (soi, kru, fek), demonstratives (dia, doq), quantifiers (eni, sem, mun, fiu, sum), epistemic operators (shi, vek, sha), normative operators (tor), extended logic (kos, til), directional spatial operators (rai, lef, sup, bel, fai, ban), numeric atoms (zo, un, du, tua, fo, pen, hek, sep, ok, nan, ten), and scalar intensity operators (single-quote, double-quote, degree).

Tier-1 glyphs MUST NOT shadow Tier-0 semantics.

#### 4.2.3. Tier-2+ Extensions

Domain-specific expansions (robotics, medical, legal, etc.) require stricter collision review and are introduced via dedicated Domain Pack NIPs.

### 4.3. Glyph Metadata Schema

Every glyph entry in `registry.json` MUST include:

| Field | Required | Description |
|-------|----------|-------------|
| `glyph` | Yes | Unicode or Noe codepoint |
| `ascii` | Yes | Fallback ASCII transcription |
| `phonetic` | Yes | Canonical phoneme |
| `tier` | Yes | 0, 1, or 2+ |
| `semantic_class` | Yes | Domain identifier |
| `semantic_anchor` | Yes | Formal meaning definition |
| `type_signature` | Yes | Input/output semantic types |
| `operator_class` | If applicable | Unary, binary, constructor, etc. |
| `evaluation_class` | Yes (Tier-0/1) | Semantic evaluation pathway per NIP-005 |
| `return_domain` | Yes (Tier-0/1) | Domain guaranteed by evaluation |
| `parser_behavior` | Yes (Tier-0/1) | PEG parser handling (unary, binary, constructor, terminator) |
| `antonym_of` | Optional | Glyph reference for inversion (X·nei) |
| `visual_form` | Yes | SVG or visual reference |
| `phonetic_constraints` | Yes | Pronounceability rules |
| `example_usage` | Yes | Canonical minimal examples |
| `version_introduced` | Yes | Registry version |
| `version_deprecated` | Optional | Registry version if deprecated |
| `status` | Yes | "active" or "deprecated" |

`registry.json` MUST implement this schema exactly.

### 4.4. Numeric Domain Separation

Numeric atoms inhabit D_numeric exclusively. Evaluators MUST NOT treat numeric atoms as entities, allow fusion of numeric atoms with entity roots, allow numeric atoms to enter morphological derivation chains, or allow numeric atoms to satisfy entity-expecting operators. Domain-shift operators (D_numeric to D_e) MAY appear only in future NIPs.

### 4.5. Collision Prevention

A glyph MUST be rejected if it causes any of the following collisions: semantic collision (overlapping conceptual domain), operator collision (duplicate morphological or logical behavior), clause-introduction exclusivity violation (only `da` may introduce embedded propositions), class collision (spanning multiple semantic classes), phonetic collision (too similar to existing phonemes), visual collision (confusable shapes under noise or BCI compression), or cognitive collision (high confusion rate in human or model benchmarks).

### 4.6. Domain and Type Enforcement

Every glyph in the registry MUST define a domain, type signature, and semantic anchor. The registry MUST reflect all domain and type-signature constraints enforced by NIP-005 semantics and the reference evaluator.

**Action-class glyphs** (mek, vus, vel, men, kra, noq) MUST have domain D_action and type_signature Action. They MUST NOT appear in entity positions, state/quality positions, truth-positions (unless wrapped by kra/noq/es), inside lexical fusion, or inside quantifier heads.

**Predication** (es) MUST have domain D_s with type_signature Copula. It MUST NOT be used as an equality operator, inside morphology, as a logical connective, or as a substitute for el (identity) or = (numeric equality).

**Demonstratives** (dia, doq) MUST be classified as Tier-1, domain D_demonstrative, type_signature Ref. They MUST resolve against C_safe.demonstratives or evaluate to undefined.

**Numeric glyphs** (zo, un, du, tua, fo, pen, hek, sep, ok, nan, ten) MUST be domain D_numeric and MUST NOT coerce to entities or states.

**Equality:** Numeric equality (=) and conceptual identity (el) MUST be distinct and MUST NOT overlap.

### 4.7. Registry Versioning

`registry.json` MUST include a `registry_version` (monotonically increasing integer), a `last_updated` timestamp (ISO-8601), and an ordered `glyphs` array. Every conformant evaluator MUST advertise the highest registry version it supports.

Each glyph entry MUST include `version_introduced`, an optional `version_deprecated`, and a `status` field (active or deprecated). Deprecated glyphs MUST remain in the registry permanently.

### 4.8. Version Negotiation

Evaluators MUST expose their supported registry version range via `registry_version_min` and `registry_version_max`. When two agents communicate, they MUST negotiate a shared version V as follows:

1. Compute V_min = max(A.registry_version_min, B.registry_version_min).
2. Compute V_max = min(A.registry_version_max, B.registry_version_max).
3. If V_min > V_max, negotiation fails with ERR_NO_SHARED_REGISTRY_VERSION.
4. Otherwise, choose V = V_max as the active registry version.

All glyph interpretation for that session MUST use version V. Agents MUST NOT silently fall back to different registry versions for different chains within a single session.

### 4.9. Glyph Lifecycle

**Proposed to Active:** After collision checks and Ontology review.

**Active to Deprecated:** If replaced or superseded. Deprecation requires setting status to "deprecated", adding `version_deprecated`, and retaining the glyph in `registry.json` permanently. Evaluators MUST still recognize deprecated glyphs. Parsers MUST NOT reinterpret deprecated glyphs.

**Deprecated to Retired:** The glyph is no longer used in new chains, but legacy chains remain valid. Deprecated glyphs MUST remain in the registry.

### 4.10. Semantic Change Prohibition

A glyph's meaning MUST NOT change after publication of the version in which it appeared. If a correction is required, the old glyph MUST be deprecated and a new glyph MUST be created. Semantic drift is forbidden.

### 4.11. Deterministic Resolution

Evaluators MUST accept only canonical forms, reject unrecognized glyphs via ERR_UNKNOWN_GLYPH, avoid auto-mapping deprecated glyphs, and never infer meaning from context or appearance.

### 4.12. Reserved Glyphs

All Tier-0 glyphs defined in the Ontology are permanently reserved and MUST NOT be reassigned, visually redesigned, repurposed, overloaded, or removed. The following structural roles are exclusive and MUST NOT be duplicated by future glyphs: clause introduction (da), scope boundary (sek), termination (nek), morphological operators (fusion, inversion, tok, al, mek), and core logical operators (nai, an, ur, nex, khi).

`registry.json` MAY designate specific codepoints or ranges as reserved_for_future_tier0, reserved_for_future_tier1, or reserved_for_experimental. Once a glyph is introduced (even if later deprecated), its codepoint, visual form, and phonetic identifier are permanently bound to its original meaning and MUST NOT be reused.

### 4.13. Interpreter-Consistency Metadata

`registry.json` MUST embed metadata required for deterministic evaluator behavior, including `nex_scope: "local"` (nex never escapes sek...sek) and `men_requires_DAG: true` (men creates DAG edges and forbids cycles). These fields MUST be included for all glyph classes whose semantics require structural invariants at runtime. Missing fields invalidate the registry version.

## 5. Rationale

A canonical glyph registry is necessary because Noe's determinism guarantee depends on every evaluator resolving glyphs identically. Without a single source of truth, evaluators could disagree on glyph semantics, domains, or type signatures, leading to divergent chain evaluation. The tier system provides a controlled extension mechanism: Tier-0 is frozen to prevent breaking changes, while Tier-1 and above allow growth without destabilizing the core. The collision-prevention rules exist because Noe operates across modalities (text, speech, BCI, haptics) where similar-looking or similar-sounding glyphs would cause decoding errors. The lifecycle rules ensure that deprecated glyphs never vanish, preserving backwards compatibility for chains in the field.

## 7. Conformance Requirements

An evaluator conforms to NIP-002 if and only if:

1. It loads `registry.json` and validates it against the schema in Section 4.3.
2. All glyphs it parses appear in `registry.json` with status "active" or "deprecated".
3. All Tier-0 glyphs match the Ontology exactly.
4. No glyph violates atomicity, uniqueness, or exclusivity.
5. Numeric atoms remain in D_numeric and are not coerced to other domains.
6. Morphology, grammar, and semantics reference glyphs only through the registry.
7. Unrecognized glyphs are rejected with ERR_UNKNOWN_GLYPH.
8. Registry version negotiation follows the protocol in Section 4.8.
9. Deprecated glyphs are recognized but not used in new chain construction.
10. All parser-alignment fields (evaluation_class, return_domain, parser_behavior) are present for Tier-0 and Tier-1 glyphs.

## 8. Backwards Compatibility

Breaking changes to glyph semantics are forbidden. If a glyph must change meaning, the original MUST be deprecated and a replacement created. The legacy decode path MUST be preserved permanently. The Ontology and `registry.json` MUST always include all deprecated glyphs.

## 9. Security and Safety Considerations

NIP-002 prevents semantic poisoning (a malicious glyph that subtly alters meaning), symbolic drift (gradual change in interpretation over deployments), cross-agent misalignment (agents disagreeing on glyph identity), multimodal confusion (glyphs that are indistinguishable under noise, BCI, or haptic channels), operator misuse (glyphs escaping their declared domain), numeric/domain bleed (numeric atoms entering entity positions), and decoding ambiguity in constrained channels. Strict versioning, lifecycle rules, and collision prevention create a stable, deterministic symbolic substrate.
