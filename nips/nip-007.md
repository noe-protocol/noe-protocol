# NIP-007: Quantitative and Numeric Logic

## Abstract

NIP-007 defines the quantitative and numeric operator system for the Noe Protocol. Numeric atoms inhabit an exclusive domain and are operated upon by comparison, arithmetic, interval, and approximation operators. Domain separation is strictly enforced: numeric operators are undefined when applied to non-numeric values. This specification establishes operator semantics, precedence rules, and the distinction between numeric equality and structural equivalence.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

## 1. Purpose

This specification defines the arithmetic, comparison, interval, and approximation operators that operate on numeric values in the Noe Protocol. It establishes domain separation rules ensuring that numeric operations are only performed on numeric atoms, defines operator precedence, and clarifies the distinction between numeric equality and identity equivalence.

## 2. Scope

This specification covers:

- Numeric atom definitions and the D_numeric domain
- Comparison operators and their semantics (=, ≠, >, <, >=, <=)
- Arithmetic operators and their semantics (+, -, *, /)
- Interval operators (..)
- Approximation operators (≈)
- ASCII linear forms for operator notation
- Operator precedence rules
- Division by zero and undefined propagation
- Approximate equality with implementation-determined epsilon
- Distinction between numeric equality and structural equivalence

This specification does not cover logical operators (AND, OR, NOT), which are defined in NIP-005.

## 3. Definitions

**Numeric Atom**: An atomic value denoting a cardinal number, inhabiting the D_numeric domain exclusively. See [NIP-002 §3](#references).

**D_numeric**: The domain of numeric values, comprising the atoms with numeric denotations: zo (0), un (1), du (2), tua (3), fo (4), pen (5), hek (6), sep (7), ok (8), nan (9), and potentially extended numeric atoms per implementation (e.g., ten for 10).

**Numeric Operator**: An operator defined only on D_numeric values. Application to values outside D_numeric is undefined. See NIP-005 §4 for undefined propagation semantics.

**Structural Equivalence (el)**: The identity equivalence operator defined in NIP-005 §4.9, which compares denotations across all domains.

**Numeric Equality (=)**: The numeric equality operator, defined only on D_numeric, which compares numeric cardinal values.

**Epsilon (ε)**: The implementation-determined tolerance threshold for approximate equality (≈), specified in registry.json. ε MUST NOT vary dynamically during execution.

**Closed Interval [A, B]**: A range from A to B inclusive, denoted syntactically as A..B, where A, B ∈ D_numeric.

## 4. Specification

### 4.1 Numeric Atoms

Numeric atoms denote cardinal numbers and MUST inhabit D_numeric exclusively. The following atoms are required:

| Atom | Cardinal | ASCII Alt |
|------|----------|-----------|
| zo   | 0        | —         |
| un   | 1        | —         |
| du   | 2        | —         |
| tua  | 3        | —         |
| fo   | 4        | —         |
| pen  | 5        | —         |
| hek  | 6        | —         |
| sep  | 7        | —         |
| ok   | 8        | —         |
| nan  | 9        | —         |
Implementations MAY extend this set with additional numeric atoms (e.g., a `ten` atom for 10). All numeric atoms MUST be uniquely associated with their cardinal value and MUST have a corresponding entry in `registry.json` (NIP-002). Multi-digit numbers are represented using the NUMBER lexical rule in NIP-004 §4.8.1 rather than requiring dedicated glyph atoms for values beyond 9.

### 4.2 Domain Separation

Numeric operators (comparison, arithmetic, interval, approximation) operate exclusively on D_numeric values. Application of a numeric operator to any value not in D_numeric MUST result in undefined behavior as per NIP-005 §4. No type coercion is permitted.

### 4.3 Comparison Operators

Comparison operators MUST have type signature D_numeric × D_numeric → T (where T is the truth domain).

The comparison operators are:

| Operator | ASCII Alt | Semantics                              |
|----------|-----------|----------------------------------------|
| =        | ek        | Numeric equality: true iff both values have equal cardinal value |
| ≠        | ne-ek     | Numeric inequality: true iff both values have unequal cardinal values (deferred; not in v1.0 grammar) |
| >        | —         | Greater than: true iff left operand is strictly greater by cardinal value |
| <        | —         | Less than: true iff left operand is strictly less by cardinal value |
| >=       | —         | Greater than or equal: true iff left operand is greater or equal by cardinal value |
| <=       | —         | Less than or equal: true iff left operand is less or equal by cardinal value |

### 4.3.1 Numeric Equality vs. Structural Equivalence

The numeric equality operator = is **distinct** from the structural equivalence operator el defined in NIP-005 §4.9. The operator el compares denotations across all domains and tests referential identity, whereas = compares only numeric cardinal values. These operators MUST NOT be confused.

Example: el(zo, zo) evaluates to true (same denotation). el(zo, nul) evaluates to false (different denotations). The expression zo = nul is undefined because nul is not in D_numeric.

### 4.4 Arithmetic Operators (Deferred)

> **Status:** Arithmetic operators are specified here for completeness but are **not yet implemented** in the v1.0 grammar (NIP-004) or the reference runtime (noe-gate). No grammar production rule exists for arithmetic expressions. Implementations MUST NOT rely on arithmetic operator support until a future NIP adds the corresponding grammar rules and runtime semantics.

Arithmetic operators, when implemented, MUST have type signature D_numeric × D_numeric → D_numeric.

The arithmetic operators are:

| Operator | ASCII Alt | Semantics                              |
|----------|-----------|----------------------------------------|
| +        | ap        | Addition: result is numeric atom denoting sum of cardinal values |
| -        | su        | Subtraction: result is numeric atom denoting difference of cardinal values |
| *        | ka        | Multiplication: result is numeric atom denoting product of cardinal values |
| /        | vo        | Division: result is numeric atom denoting quotient; division by zero is undefined |

### 4.4.1 Division by Zero

When arithmetic is implemented, division by zero MUST be treated as undefined. Any expression of the form A / zo where A ∈ D_numeric is undefined and MUST propagate as described in NIP-005 §4.

### 4.5 Interval Operator

The interval operator has type signature D_numeric × D_numeric → Interval. An interval A..B denotes a closed interval [A, B] in D_numeric, where A, B ∈ D_numeric.

Intervals are **not truth-valued**. They serve as operands to predicates that test membership or properties. See §6 for examples.

The interval operator MUST satisfy:
- A..B is defined only when A, B ∈ D_numeric
- A..B denotes the closed interval [A, B], meaning all numeric atoms X such that A ≤ X ≤ B
- No ordering constraint is imposed; A..B and B..A denote the same closed interval

### 4.6 Approximation Operator

The approximation operator ≈ MUST have type signature D_numeric × D_numeric → T.

The approximation operator is defined as:

X ≈ Y evaluates to true if and only if |X - Y| ≤ ε

where ε is the implementation-determined epsilon value specified in registry.json.

The epsilon MUST NOT be dynamic. The value of ε MUST be fixed at load time and remain constant throughout execution.

### 4.7 Operator Precedence

Operator precedence, from highest to lowest, is:

1. **Arithmetic operators** (+, -, *, /): bind most tightly *(deferred; see §4.4)*
2. **Comparison operators** (=, ≠, >, <, >=, <=, ≈)
3. **Interval operator** (..)
4. **Logical operators** (AND, OR, NOT): bind least tightly

Within the same precedence level, operators associate left-to-right unless parentheses override. This precedence table is forward-looking; in v1.0, only comparison, interval, and logical bands are active in the grammar (NIP-004 §4.7). The arithmetic band is reserved for future use.

Example: `pen > tua AND du < fo` evaluates as `(pen > tua) AND (du < fo)` because comparison binds tighter than AND.

### 4.8 Undefined Propagation

All numeric operators follow the undefined propagation rules of NIP-005 §4. If either operand is undefined, the result is undefined. If an operation cannot be performed (e.g., division by zero, type mismatch), the result is undefined.

### 4.9 Grammar Tokens

Implementations MUST recognize the following grammar tokens for numeric operations:

```peg
/* v1.0 comparison operators */
comparison_op  = "=" / ">" / "<" / ">=" / "<=" / "≈"
                / "ek" / "ak"

/* deferred: "≠" / "ne-ek" (requires future grammar addition) */

/* deferred: arithmetic operators (no grammar production in v1.0) */
arith_op       = "+" / "-" / "*" / "/"
                / "ap" / "su" / "ka" / "vo"

interval_op    = ".."
                / "ran"

approx_op      = "≈"
                / "ak"

numeric_atom   = "zo" / "un" / "du" / "tua" / "fo" / "pen"
                / "hek" / "sep" / "ok" / "nan"
/* implementations MAY additionally recognize "ten" and other extensions */
```

## 5. Rationale

### 5.1 Domain Separation

Strict domain separation prevents silent type coercion and makes operations explicit and predictable. By restricting numeric operators to D_numeric, the protocol ensures that mixing numeric and non-numeric values is a detectable error rather than an implicit conversion.

### 5.2 Numeric Equality vs. Structural Equivalence

The distinction between numeric equality (=) and structural equivalence (el) is essential. Numeric equality tests only cardinal value; structural equivalence tests denotational identity. This separation allows protocols to maintain distinct notions of "the same value numerically" and "the same entity structurally."

### 5.3 Epsilon for Approximation

Approximate equality enables tolerance-based comparisons necessary in practical numeric systems. By fixing ε at load time and specifying it in the registry, the protocol ensures deterministic, auditable approximation semantics.

### 5.4 Closed Intervals

Closed intervals [A, B] are the standard mathematical convention and SHOULD be preferred in implementations. They simplify endpoint inclusion semantics.

### 5.5 Zero vs. Null

The atom zo (D_numeric, cardinal 0) is distinct from nul (a structural gap). The expression zo = nul is undefined, not false, because nul is not in D_numeric. This distinction preserves the semantic integrity of both representations.

## 6. Examples

### 6.1 Numeric Equality and Inequality

```noe
un = un        /* true */
un = du        /* false */
un ≠ du        /* true */
zo = zo        /* true */
```

### 6.2 Arithmetic Operations (Deferred)

> These examples illustrate intended semantics for when arithmetic operators are added to the grammar.

```noe
un + du        /* tua (1 + 2 = 3) */
pen - tua      /* du (5 - 3 = 2) */
du * tua       /* hek (2 * 3 = 6) */
hek / du       /* tua (6 / 2 = 3) */
```

### 6.3 Comparison Operations

```noe
pen > tua      /* true (5 > 3) */
du < fo        /* true (2 < 4) */
hek >= sep     /* false (6 >= 7 is false) */
nan <= nan     /* true (9 <= 9) */
```

### 6.4 Division by Zero

```noe
du / zo        /* undefined; propagates as per NIP-005 */
```

### 6.5 Approximation Equality

Assuming ε = 0.1 per registry.json:

```noe
un ≈ un        /* true (|1 - 1| = 0 ≤ 0.1) */
un ≈ un + ε    /* true (|1 - 1.1| = 0.1 ≤ 0.1) */
du ≈ tua       /* false (|2 - 3| = 1 > 0.1) */
```

### 6.6 Intervals

```noe
du..pen                /* denotes closed interval [2, 5] */
tua..sep               /* denotes closed interval [3, 7] */
```

> **Note:** Interval membership testing (e.g., whether tua ∈ du..pen) requires a predicate not yet defined in the v1.0 grammar. A future NIP MAY introduce a membership operator. For now, intervals serve as operands to predicates defined by implementations.

### 6.7 Operator Precedence

```noe
pen > tua AND du < fo  /* evaluates as (pen > tua) AND (du < fo) = true AND true = true */
```

> **Note:** Arithmetic precedence examples (e.g., `un + du * tua`) are deferred until arithmetic operators are added to the grammar. See §4.4.

### 6.8 Zero vs. Null

```noe
zo = zo                /* true */
zo = nul               /* undefined; nul ∉ D_numeric */
zo > nul               /* undefined; nul ∉ D_numeric */
el(zo, nul)            /* false; different denotations */
```

## 7. Conformance Requirements

Implementations MUST:

- Define the nine required numeric atoms (zo through nan) with their specified cardinal values
- Implement the five v1.0 comparison operators (=, >, <, >=, <=) with correct semantics
- Implement the interval operator (..) with closed interval semantics [A, B]
- Implement the approximation operator (≈) with fixed epsilon from registry.json
- Enforce strict domain separation: numeric operators MUST be undefined on non-numeric operands
- Respect operator precedence as specified in §4.7
- Distinguish numeric equality (=) from structural equivalence (el)
- Recognize both Unicode and ASCII linear forms for all implemented operators

When arithmetic operators are added to the grammar (future NIP), implementations MUST additionally:

- Implement all four arithmetic operators (+, -, *, /) with correct semantics
- Treat division by zero as undefined and propagate per NIP-005 §4
- Implement numeric inequality (≠ / ne-ek)

Implementations MAY:

- Extend the numeric domain with additional atoms (e.g., ten for 10)
- Implement additional operators or syntactic sugar for common operations
- Optimize numeric operations for specific hardware or runtime characteristics

## 8. Backwards Compatibility

NIP-007 supersedes any prior numeric operator definitions. Implementations upgrading from pre-NIP-007 systems MUST migrate numeric operations to conform to the domain separation and operator precedence rules specified herein.

The ASCII linear forms (ap, su, ka, vo, ek, ne-ek, ran, ak) are provided for systems with limited Unicode support and MUST be semantically equivalent to their Unicode counterparts.

## 9. Security and Safety Considerations

### 9.1 Division by Zero

Division by zero is a common source of runtime errors. Implementations MUST detect and handle division by zero as undefined behavior, preventing crashes or undefined machine state. See NIP-005 §4.

### 9.2 Numeric Overflow and Underflow

This specification does not mandate support for numbers beyond ten. Implementations that extend the numeric domain MUST document overflow and underflow behavior clearly. Arithmetic operations that exceed the supported numeric range SHOULD result in undefined behavior rather than silent wraparound.

### 9.3 Epsilon Precision

The epsilon value for approximation equality MUST be fixed at load time and documented in registry.json. Dynamic epsilon values introduce non-determinism and potential security vulnerabilities in systems relying on reproducible comparison semantics.

### 9.4 Type Safety

Strict domain separation prevents accidental mixing of numeric and non-numeric values, reducing the attack surface for type confusion vulnerabilities.
