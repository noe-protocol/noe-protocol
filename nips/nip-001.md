# NIP-001: Noe Improvement Proposal Process

## Abstract

This document defines the standard process, structure, numbering rules, and lifecycle for all Noe Improvement Proposals (NIPs). It establishes the canonical format that every NIP MUST follow, the dependency rules that prevent circular or unstable references, and the change-control procedures that preserve protocol integrity. NIP-001 is the root of the NIP dependency graph; all other NIPs MUST conform to this specification.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

## 1. Purpose

NIP-001 specifies the rules governing the creation, review, acceptance, and deprecation of Noe Improvement Proposals. It ensures consistency across the protocol suite and provides contributors with a deterministic, reviewable workflow.

The objectives are:

1. Establish a canonical document structure for all NIPs.
2. Define NIP states and lifecycle transitions.
3. Specify numbering and dependency ordering.
4. Set requirements for glyph introductions and breaking changes.
5. Provide a single root for governance and documentation consistency.

## 2. Scope

### 2.1. In Scope

This NIP covers the NIP structure and required sections, NIP states and lifecycle transitions, numbering and renumbering rules, cross-NIP dependencies and ordering, review and acceptance procedures, requirements for glyph additions, and requirements for grammar or semantic changes.

### 2.2. Out of Scope

This NIP does not cover technical protocol definitions (handled by NIP-002 and above), governance models for approving NIPs, or transport-layer and implementation-specific concerns.

## 3. Definitions

**NIP (Noe Improvement Proposal):** A formal document specifying a component of the Noe Protocol. Each NIP defines exactly one aspect of the protocol: a set of glyphs, a grammar rule, a semantic model, a context structure, or a governance procedure.

**Normative:** Text that prescribes required behavior. Normative sections contain MUST, SHOULD, and MAY requirements. Non-normative text (such as Rationale or Examples) is informative and does not impose implementation obligations.

**Conformant:** An implementation or document that satisfies all MUST requirements of the relevant NIP(s).

**Glyph:** An atomic symbolic unit registered in the Noe glyph registry (NIP-002). Each glyph has a unique identifier, phonetic form, visual form, semantic domain, and tier assignment.

**Tier:** A classification level for glyphs and operators. Tier-0 glyphs are frozen and globally immutable. Tier-1 glyphs are extended operators. Tier-2 and above are domain-specific extensions.

**Chain:** A well-formed Noe symbolic expression, as defined by the grammar in NIP-004.

## 4. Specification

### 4.1. NIP Categories

Each NIP MUST be assigned exactly one category:

- **Standards Track:** Core protocol specifications covering morphology, grammar, semantics, numeric logic, context models, validation, and related concerns.
- **Registry Track:** Glyph definitions, tier assignments, and operator domain declarations.
- **Informational:** Non-normative explanations, rationale documents, or surveys.
- **Experimental:** Proposals not yet intended for production use.

A NIP MUST NOT change categories once it reaches Accepted status.

### 4.2. NIP Numbering

NIP-001 is this document. NIP-002 and above follow strictly increasing integers. Numbers are permanent and MUST NOT be reused. Withdrawn NIPs retain their number. The Glyph Registry MUST always be NIP-002; all morphology, grammar, and semantics NIPs depend on it.

### 4.3. Required NIP Structure

Every NIP MUST contain the following sections, in this order:

1. **YAML Frontmatter** — machine-readable metadata (nip number, title, status, category, tier, author, dependencies, dates).
2. **Title Heading** — `# NIP-NNN: Full Title`.
3. **Abstract** — a self-contained summary of 2-5 sentences.
4. **Notation Convention** — the RFC 2119 / RFC 8174 boilerplate paragraph.
5. **Purpose** — why this NIP exists.
6. **Scope** — explicit In Scope and Out of Scope subsections.
7. **Definitions** — every term used normatively, defined here or by reference to another NIP.
8. **Specification** — the normative body containing all MUST/SHOULD/MAY requirements.
9. **Rationale** — non-normative design reasoning.
10. **Examples** — concrete illustrations of the specification.
11. **Conformance Requirements** — a numbered checklist of conditions for compliance.
12. **Backwards Compatibility** — what changes from prior state, or "None" for new features.
13. **Security and Safety Considerations** — threat model and mitigations relevant to this NIP.
14. **Normative References** — NIPs, RFCs, and external specs that this NIP depends on.
15. **Informative References** (OPTIONAL) — background reading and related work.

A NIP missing any required section is invalid and MUST NOT be accepted.

### 4.4. NIP States

A NIP MUST be in exactly one of the following states:

| State | Description |
|-------|-------------|
| Draft | Not yet ready for wide review. |
| Review | Under active review. |
| Accepted | Approved; becomes normative. |
| Final | Fully stable; future changes require a new NIP. |
| Deferred | Paused; no active progress. |
| Rejected | Declined; reasons documented. |
| Replaced | Superseded by another NIP. |
| Withdrawn | Voluntarily removed by author. |

Final supersedes Accepted. A NIP MUST be Accepted before it can transition to Final. State transitions MUST be recorded in the NIP's frontmatter and changelog.

### 4.5. Dependencies and Ordering

Dependencies MUST be listed in the YAML frontmatter. NIPs MUST NOT depend on Draft NIPs. Circular dependencies are forbidden. A NIP MUST NOT redefine or contradict any of its dependencies.

The canonical foundational ordering is:

1. NIP-001 — Meta-specification (this document)
2. NIP-002 — Glyph Registry Specification
3. NIP-003 — Core Morphology
4. NIP-004 — Core Grammar
5. NIP-005 — Core Semantics
6. NIP-006 — Scalar and Intensity Operators
7. NIP-007 — Quantitative and Numeric Logic

Any reordering MUST be justified and approved. Any intentional supersession MUST be expressed via the Replaced state and a reference to the superseding NIP, not by in-place contradiction.

### 4.6. Glyph Introduction Rules

Any NIP proposing a new glyph or modifying an existing glyph MUST include a Glyph Introduction Appendix containing:

1. **Domain declaration** — the exact semantic class (D_epistemic, D_spatial, D_action, etc.).
2. **Tier assignment** — Tier-0, Tier-1, or Tier-2+.
3. **Collision analysis:** visual collision check, phonetic collision check, and semantic domain collision check.
4. **Rationale for addition.**
5. **Backwards compatibility impact.**
6. **Corresponding update to registry.json.**

Glyphs that overlap with any Tier-0 domain MUST be rejected.

### 4.7. Change Control

**Breaking changes** to morphology, grammar, or semantics MUST be isolated to a new NIP, include a complete migration path, include a compatibility note in prior NIPs, and update the Glyph Registry if needed. Breaking changes MUST NOT be made by editing accepted NIPs.

**Editorial changes** (typographical, formatting, and structure-clarification changes) MAY be made without a new NIP provided no normative text is altered, no behavior changes, and no semantics, morphology, or grammar changes occur. All edits MUST be logged.

## 5. Rationale

A meta-specification is necessary to prevent schema drift across the NIP suite. Without a canonical structure, individual NIPs would diverge in format, terminology, and cross-reference style, making the protocol harder to implement and audit. The required section ordering mirrors established standards practice (IETF RFCs, Ethereum EIPs) adapted to Noe's specific needs: explicit glyph governance, tier-based evolution, and determinism requirements.

The prohibition on circular dependencies ensures that the NIP dependency graph forms a directed acyclic graph (DAG), which is necessary for incremental implementation and testing. The foundational ordering (001 through 007) reflects the natural layering: registry before morphology, morphology before grammar, grammar before semantics. Each layer depends only on layers below it, so an evaluator can be implemented and tested incrementally from NIP-001 upward.

The distinction between Standards Track, Registry Track, Informational, and Experimental categories exists because each category carries different normative weight. Standards Track NIPs impose MUST-level requirements on all conformant evaluators; Registry Track NIPs define the glyph universe; Informational NIPs carry no implementation obligations. Conflating these categories would obscure which requirements are binding. The state machine (Draft through Final) provides a clear lifecycle that prevents premature adoption of unstable specifications and ensures that once a NIP reaches Final status, its normative content is immutable.

## 7. Conformance Requirements

A NIP is conformant with NIP-001 if and only if:

1. It contains all required sections listed in Section 4.3, in the specified order.
2. All dependencies are satisfied, listed, and non-circular.
3. All normative clauses are testable or verifiable.
4. It introduces no glyph collisions or semantic ambiguity.
5. Grammar and semantics modifications preserve determinism.
6. Any new glyphs include a Glyph Introduction Appendix per Section 4.6.
7. Any breaking changes follow the change-control rules in Section 4.7.
8. The NIP's YAML frontmatter contains all required fields (nip, title, status, category, tier, author, dependencies, created, updated) and each field value is consistent with the NIP's content and the glyph registry.

## 8. Backwards Compatibility

NIP-001 is the initial meta-specification. No prior NIP process exists that this document supersedes. All NIPs authored before the formal adoption of NIP-001 SHOULD be updated to conform to its structure during their next revision cycle.

## 9. Security and Safety Considerations

Ambiguous or conflicting NIPs risk interpreter divergence, which in safety-critical deployments (robotics, autonomous agents) can lead to contradictory actions. NIP-001 mitigates this by requiring deterministic structure, explicit dependencies, collision checks for new glyphs, and strict change-control procedures. Redefinition of Tier-0 semantics is strictly prohibited to prevent silent behavioral changes in deployed systems.
