# NIP-015: Verified Compiler and Runtime Validator

## Abstract

NIP-015 establishes the trusted safety boundary for Noe protocol execution: Proposer → Verified Compiler → Validator → Interpreter → Actuators. This specification defines the compile-time and runtime validation pipeline that ensures all propositions are morphologically valid, semantically well-formed, contextually grounded, and safe for execution. Two v1.0 hardening invariants ensure deterministic behavior: strict blocking is success, and all chains reduce to one canonical form.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

- `P_canon`: canonical proposition chain (single source of truth)
- `C_rich`: rich context (merged from root, domain, local sources)
- `C_safe`: safe context (subset of C_rich filtered through epistemic and safety validators)
- `π_safe`: safety filtering function
- `ERR_*`: normative error codes
- `shi`, `vek`, `sha`: epistemic operators (knowledge, belief, certainty)
- `action`: executable operation produced by delivery operators (vus, vel, mek), guarded by khi or kra

---

## 1. Purpose

The Verified Compiler and Runtime Validator provide defense-in-depth verification of propositions before execution:

1. **Compile-time validation** ensures morphological correctness, grammar conformance, and registry alignment
2. **Runtime validation** ensures contextual completeness, epistemic grounding, temporal freshness, and action safety
3. **Canonical enforcement** prevents downstream re-interpretation and mutation of the execution chain
4. **Deterministic error handling** via normative error codes and strict validation modes

This specification is normative for all implementations claiming Noe protocol compliance.

## 2. Scope

This NIP specifies:

- Verified Compiler behavior and output schema
- Validator pipeline (strict and partial modes)
- Canonical form enforcement and non-idempotency detection
- Context construction (C_safe derivation)
- Epistemic and action validation semantics
- Error codes and conformance requirements
- Backwards compatibility boundaries

Out of scope:

- Specific interpreter implementation details (except safety boundaries)
- Proposer-side logic or UI
- Actuator action execution (only validation)

## 3. Definitions

**Canonical Chain (`P_canon`)**: The unique, immutable representation of a proposition after compilation. Once established by the Verified Compiler, no downstream component may re-canonicalize.

**Rich Context (`C_rich`)**: Union of root context (C_root), domain context (C_domain), and local context (C_local), merged with C_local > C_domain > C_root precedence. No default seeding; missing values remain undefined.

**Safe Context (`C_safe`)**: Subset of C_rich validated for epistemic correctness and safety constraints via π_safe filtering.

**Morphology**: Glyph-level structure and operator precedence as specified in NIP-003.

**Grammar**: Sentence-level syntax as specified in NIP-004.

**Registry**: Authoritative source of domain, literal, and action bindings (NIP-002).

**Strict Mode**: Validation that treats missing, stale, or unsafe values as errors. Blocks execution of propositions with any validation failure.

**Partial Mode**: Validation that treats missing values as undefined but still blocks unsafe actions. Allows non-action reasoning to proceed.

**Staleness**: A context value exceeds max_skew_ms from current time. Must be detected and rejected in strict mode.

**Epistemic Operators**: Prefix operators (`shi`, `vek`, `sha`) that check membership in modal sets within C_safe. `shi` checks knowledge, `vek` checks belief, `sha` checks certainty. Missing modal sets trigger ERR_BAD_CONTEXT; mismatched membership triggers ERR_EPISTEMIC_MISMATCH.

**Guard Semantics**: Only propositions with guard = true permit action execution. All other values (false, undefined, error) block action.

## 4. Specification

### 4.1 Verified Compiler

The Verified Compiler accepts a raw proposition and produces a `CompilerResult`.

#### 4.1.1 Compile-time Validation

The compiler performs three sequential validations:

1. **Morphology Resolution (NIP-003)**
   - Resolve all glyphs to canonical symbols
   - Validate operator precedence and nesting
   - Reject ERR_MORPHOLOGY, ERR_PARSE_FAILED

2. **Grammar Validation (NIP-004)**
   - Parse sentence structure
   - Validate terminal and non-terminal sequences
   - Reject ERR_PARSE

3. **Registry Validation (NIP-002)**
   - Validate all domain bindings exist in registry
   - Validate all literal references are resolvable
   - Validate all action names are registered
   - Reject ERR_INVALID_LITERAL

#### 4.1.2 Compiler Output

The compiler outputs `CompilerResult`:

```
CompilerResult {
  ok: Boolean,                    // true if all validations pass
  canonical_chain: String|null,   // P_canon; null on error
  parse_repr: Object|null,        // Abstract syntax tree; null on error
  domain: String|null,            // Domain name; null on error
  error: ErrorCode|null           // ERR_* code if !ok
}
```

#### 4.1.3 Invariants

The compiler MUST NOT:

- Inject, remove, or rewrite operators or connectors
- Infer literal values from undefined context
- Canonicalize in non-deterministic ways
- Permit invalid glyphs or grammar to pass to the validator

If a compiler detects non-determinism in its own output (i.e., compiling the same input produces different P_canon), it MUST reject with ERR_CANONICALIZATION_NON_IDEMPOTENT.

---

### 4.2 Validator Pipeline

The Validator accepts `(P_canon, parse_repr, C_rich, mode)` and produces a `ValidatorResult`.

#### 4.2.1 Validation Stages

**Stage 0: AST Depth Check**
- Compute the nesting depth of P_canon's abstract syntax tree
- If depth exceeds `MAX_CONTEXT_DEPTH` (default: 32): reject with reason "Context nesting exceeds limit"
- This gate prevents unbounded recursion and stack exhaustion in the evaluator
- `MAX_CONTEXT_DEPTH` is an implementation-defined parameter; implementations MUST enforce a finite limit and SHOULD default to 32

**Stage 1: Context Completeness**
- Merge C_root, C_domain, C_local → C_rich (with C_local > C_domain > C_root precedence)
- Check timestamp freshness against max_skew_ms
- In strict mode: missing values → error; stale → ERR_CONTEXT_STALE
- In partial mode: missing → undefined; stale still → ERR_CONTEXT_STALE (if strict_staleness = true)

**Stage 2: Epistemic Validation**
- Verify modal sets exist in C_safe (`modal.knowledge`, `modal.belief`, `modal.certainty`)
- Missing modal sets entirely → ERR_BAD_CONTEXT
- For each epistemic operator in P_canon: check its operand against the corresponding modal set
  - `shi`: operand must be in `modal.knowledge` with confidence ≥ `t_shi_min` (0.90)
  - `vek`: operand checked in `modal.belief`; absent → evaluates as undefined
  - `sha`: operand checked in `modal.certainty`; absent → evaluates as undefined
  - Membership mismatch in strict mode → ERR_EPISTEMIC_MISMATCH

**Stage 3: Literal Validation**
- For each literal reference in P_canon: verify it exists in C_safe
- In strict mode: missing → error
- In partial mode: missing → undefined (blocks action evaluation only)

**Stage 4: Action Safety Validation** (only if action present)
- Validate action structure: type, verb, target, kind
- Malformed action → ERR_INVALID_ACTION
- Undefined target of action → ERR_UNDEFINED_TARGET
- Evaluate guard expression:
  - true: action permitted
  - false: action blocked
  - undefined: action blocked
  - error: action blocked
- If action guard evaluates to true but action marked unsafe (epistemic confidence < threshold): ERR_UNSAFE_THRESHOLD
- Check recursion depth ≤ max_recursion_depth; else ERR_RECURSION_LIMIT

**Stage 5: Safety Threshold Validation**
- For each action: verify epistemic_confidence ≥ min_confidence_threshold
- If confidence unknown or below threshold in strict mode: ERR_UNSAFE_THRESHOLD
- If action guard semantics violated: ERR_ACTION_MISUSE

#### 4.2.2 Safe Context Construction

```
C_rich = merge(C_root, C_domain, C_local)  // C_local > C_domain > C_root
C_safe = π_safe(C_rich)
```

π_safe filtering (per NIP-009 and NIP-012):

- **Freshness gate**: Remove values where `(now_ms - timestamp) > tau_stale_ms` (default 1000ms)
- **Confidence gate**: Remove values where `confidence < theta_thresh` (default 0.80)
- **Authority gate**: If `auth_map` is configured, remove values from unauthorised sources
- **Leading edge window**: For each predicate, retain only values within `tau_window_ms` (default 100ms) of the newest observation
- **Consistency check**: Remove predicates with internal or cross-group conflicts

The interpreter MUST ONLY evaluate expressions over C_safe.

#### 4.2.3 Validator Output

The validator produces a `ValidationResult`:

```
ValidationResult {
  ok: Boolean,                        // true if validation passed
  context_hashes: {                   // hashes of each context layer
    root: String,
    domain: String,
    local: String,
    total: String
  },
  context_error: String|null,         // context-level error if any
  flags: Object,                      // validation flags
  reasons: [String],                  // human-readable validation notes
  errors: [{code: String, detail: String}],  // ERR_* codes with details
  warnings: [{code: String, detail: String}],
  provenance: Object|null,            // provenance record per NIP-010
  explained_literals: [String],       // literals that passed explanation check
  c_safe: Object|null,               // projected safe context (NIP-009)
  h_safe: String|null                 // SHA-256 hash of c_safe
}
```

The runtime wraps this into a `RuntimeResult` after evaluation:

```
RuntimeResult {
  domain: String,                     // "truth"|"numeric"|"action"|"undefined"|"error"
  value: Any,                         // evaluation result
  error: String|null,                 // ERR_* code if evaluation failed
  context_hash: String,               // hash of context used
  snapshot_ts: Integer,               // evaluation timestamp (ms)
  raw_ast: Object,                    // abstract syntax tree
  canonical_chain: String|null,       // P_canon
  provenance: Object|null,            // provenance record
  explained_literals: Object|null,    // explained literal map
  missing: [String]|null              // list of missing context paths
}
```

### 4.3 Canonical Chain Enforcement

#### 4.3.1 Single Source of Truth

Once the Verified Compiler establishes P_canon, that value is the authoritative and immutable representation for the proposition. The runtime OWNS P_canon and MUST NOT permit re-canonicalization downstream.

#### 4.3.2 Non-Idempotency Detection

If any component (compiler, validator, interpreter) detects that:

```
canonicalize(canonicalize(X)) ≠ canonicalize(X)
```

it MUST reject with ERR_CANONICALIZATION_NON_IDEMPOTENT and halt.

#### 4.3.3 Hash Namespace Separation

Hashes MUST be computed separately by domain:

- If P_canon contains action: compute `action_hash = SHA256(P_canon, "action")`; set `decision_hash = null`, `blocked_hash = null`
- If P_canon is pure reasoning (no action): compute `decision_hash = SHA256(P_canon, "decision")`; set `action_hash = null`, `blocked_hash = null`
- If validation blocks (error ≠ null): set all hashes to null

---

### 4.4 Context Staleness and Skew

#### 4.4.1 Temporal Enforcement

Every value in C_rich MUST have a `timestamp_ms` field. During validation:

```
skew = current_time_ms - value.timestamp_ms
if (skew > max_skew_ms && strict_mode):
  reject with ERR_CONTEXT_STALE
```

#### 4.4.2 Configuration Parameters

- `max_skew_ms`: maximum allowable timestamp deviation (default 1000ms per noe-gate)
- `tau_stale_ms`: evidence freshness threshold (default 1000ms per NIP-012)

---

### 4.5 Epistemic Validation

#### 4.5.1 Epistemic Operator Semantics

Noe's epistemic operators are prefix operators checked against modal sets in C_safe:

- **shi** (knowledge): Checks membership in `C_safe.modal.knowledge`. Returns true if the proposition is known; ERR_EPISTEMIC_MISMATCH in strict mode if not present. Knowledge threshold: `t_shi_min = 0.90`.
- **vek** (belief): Checks membership in `C_safe.modal.belief`. Returns false if the proposition is not in the belief set (not undefined). Belief threshold: `t_vek_min = 0.40`.
- **sha** (certainty): Checks membership in `C_safe.modal.certainty`. Returns the certainty value if present; undefined otherwise.

These operators are defined in NIP-005 and NIP-017. There are no English-language modal qualifiers (`may`, `must`, `might`) in Noe — epistemic status is expressed exclusively through `shi`, `vek`, and `sha`.

#### 4.5.2 Epistemic Validation Rules

| Condition | Error | Handling |
|-----------|-------|----------|
| `shi` operand not in `C_safe.modal.knowledge` (strict) | ERR_EPISTEMIC_MISMATCH | Reject |
| `shi` operand not in `C_safe.modal.knowledge` (partial) | (not error) | Evaluate as false |
| `vek` operand not in `C_safe.modal.belief` | (not error) | Evaluate as false |
| `sha` operand not in `C_safe.modal.certainty` | (not error) | Evaluate as undefined |
| Modal set missing from C_safe entirely | ERR_BAD_CONTEXT | Reject |
| Epistemic confidence below threshold | ERR_UNSAFE_THRESHOLD | Reject in strict; block action in partial |

---

### 4.6 Action Validation

#### 4.6.1 Action Structure

Actions in Noe are produced by delivery operators (`vus`, `vel`, `mek`) and guarded by the `khi` conditional operator or `kra` binary guard. The runtime action object has the following structure:

```
Action {
  type: "action",              // always "action"
  verb: String,                // operator that produced the action (e.g., "mek", "vus", "vel")
  target: String|Object,       // action target (must be defined in C_safe)
  kind: String|null,           // "audit", "delivery", or null
  action_hash: String|null,    // SHA-256 hash of the canonical chain
  provenance: Object|null      // provenance record per NIP-010
}
```

Guards are NOT stored on the action object — they are evaluated by the `khi` expression or `kra` operator in the chain. The guard is the expression preceding the action in the chain (e.g., `shi @condition khi sek mek @target sek nek`). If the guard evaluates to false or undefined, the action is never produced.

#### 4.6.2 Action Validation Rules

| Condition | Error | Handling |
|-----------|-------|----------|
| Action malformed | ERR_INVALID_ACTION | Reject |
| Target undefined in C_safe | ERR_UNDEFINED_TARGET | Reject |
| Guard evaluates to false | (not error) | Block action; continue reasoning |
| Guard evaluates to undefined | (not error) | Block action; continue reasoning |
| Guard raises error | ERR_SAFETY | Reject |
| Confidence < min_threshold | ERR_UNSAFE_THRESHOLD | Reject in strict; block in partial |
| Recursion depth > max | ERR_RECURSION_LIMIT | Reject |
| Guard semantic violation | ERR_ACTION_MISUSE | Reject |

#### 4.6.3 Guard Semantics

Guard evaluation is deterministic and idempotent:

- Guard true AND confidence ≥ threshold → execute action
- Guard false OR undefined OR error → DO NOT execute; no action taken
- Non-deterministic guard evaluation → ERR_SAFETY

The guard MUST be re-evaluated before each action execution; caching is permissible only if C_safe is unchanged.

---

### 4.7 Validation Modes

#### 4.7.1 Strict Mode

Strict mode is the default for safety-critical operations:

```
strict_mode = true
```

Behavior:

- Missing context value → error (fail fast)
- Stale context value → ERR_CONTEXT_STALE
- Unsafe threshold → ERR_UNSAFE_THRESHOLD
- Malformed action → ERR_INVALID_ACTION
- Undefined target → ERR_UNDEFINED_TARGET
- Any validation error → block all execution (action and reasoning)

#### 4.7.2 Partial Mode

Partial mode allows exploratory reasoning but maintains safety boundaries:

```
strict_mode = false
```

Behavior:

- Missing context value → undefined (substitute in reasoning)
- Stale context value → ERR_CONTEXT_STALE (always an error)
- Unsafe threshold → block action only; allow reasoning
- Malformed action → ERR_INVALID_ACTION (always an error)
- Undefined target → block action; allow reasoning
- Validation error outside action path → log and continue

## 5. Rationale

### 5.1 Defense in Depth

Separating compilation and validation into two phases allows:

1. Early detection of morphological and grammatical errors (compiler)
2. Late binding and safety checks that depend on runtime context (validator)
3. Clear separation of concerns and auditability

### 5.2 Canonical Immutability

Enforcement of P_canon as single source of truth prevents:

- Re-interpretation of propositions by downstream components
- Subtle mutations that alter meaning without detection
- Non-deterministic evaluations

### 5.3 Guard Semantics

Treating undefined and false identically for guards ensures:

- No implicit defaults or "undefined = true" behavior
- Explicit opt-in for action execution
- Clear failure modes for missing information

### 5.4 Epistemic Grounding

Epistemic operators (`shi`, `vek`, `sha`) and freshness checks ensure:

- All reasoning is grounded in explicit modal set membership
- Stale information cannot silently invalidate decisions
- Knowledge claims (`shi`) require the highest confidence threshold (0.90)

### 5.5 Hash Namespaces

Separating action_hash and decision_hash prevents:

- Confusion between action execution outcomes and reasoning results
- Cross-domain hash collisions
- Ambiguity in audit trails

## 6. Examples

### 6.1 Guarded Action — Successful Validation (Strict Mode)

**Noe chain:**

```
shi @door_unlocked khi sek mek @open_door sek nek
```

(If @door_unlocked is known, then execute action mek @open_door)

**Context:**

```json
{
  "C_safe": {
    "modal": {
      "knowledge": ["@door_unlocked"]
    },
    "literals": {
      "@door_unlocked": {"value": true, "confidence": 0.95, "timestamp": 1704067200000},
      "@open_door": {"value": true}
    }
  },
  "max_skew_ms": 1000,
  "mode": "strict"
}
```

**Validation:**

1. Context completeness: @door_unlocked present, fresh (skew < 1000ms), confidence 0.95 ≥ 0.80 → pass
2. Epistemic: `shi` checks @door_unlocked ∈ C_safe.modal.knowledge → true, confidence 0.95 ≥ 0.90 (t_shi_min) → pass
3. Literal: @open_door in registry → pass
4. Guard: `khi` guard evaluates to true → action `mek @open_door` permitted
5. Safety: well-formed action, recursion depth 1 ≤ limit → pass

**Result:** `{ok: true, domain: "action", value: {type: "action", verb: "mek", target: "@open_door"}, errors: []}`

### 6.2 Stale Context Rejection (Strict Mode)

**Noe chain:**

```
shi @sensor_active kra vus @data_packet nek
```

**Context:**

```json
{
  "C_safe": {
    "modal": {"knowledge": ["@sensor_active"]},
    "literals": {
      "@sensor_active": {"value": true, "confidence": 0.92, "timestamp": 1704067198000}
    }
  },
  "max_skew_ms": 1000,
  "current_time_ms": 1704067200000,
  "mode": "strict"
}
```

**Validation:**

1. Context completeness: @sensor_active timestamp is 2000ms old; skew = 2000 > max_skew_ms (1000) → ERR_STALE_CONTEXT

**Result:** `{ok: false, errors: [{code: "ERR_STALE_CONTEXT", detail: "@sensor_active age 2000ms > max_skew_ms 1000ms"}]}`

### 6.3 Epistemic Mismatch — Knowledge Threshold Failure

**Noe chain:**

```
shi @route_clear khi sek mek @proceed sek nek
```

**Context:**

```json
{
  "C_safe": {
    "modal": {"knowledge": []},
    "literals": {
      "@route_clear": {"value": true, "confidence": 0.60}
    }
  },
  "mode": "strict"
}
```

**Validation:**

1. Epistemic: `shi` checks @route_clear ∈ C_safe.modal.knowledge → NOT present
2. Strict mode: ERR_EPISTEMIC_MISMATCH (knowledge membership required but absent)
3. Guard evaluates to false → action `mek @proceed` blocked

**Result:** `{ok: false, errors: [{code: "ERR_EPISTEMIC_MISMATCH", detail: "@route_clear not in modal.knowledge"}]}`

### 6.4 Partial Mode with Missing Literal

**Noe chain:**

```
shi @system_ready kra vus @heartbeat nek
```

**Context:**

```json
{
  "C_safe": {
    "modal": {"knowledge": ["@system_ready"]},
    "literals": {"@system_ready": {"value": true, "confidence": 0.95}}
  },
  "mode": "partial"
}
```

**Validation:**

1. Literal: @heartbeat not in C_safe → missing
2. Partial mode: missing literal → undefined (not error), blocks action delivery
3. Guard (`kra`): left operand true, but target @heartbeat undefined → action blocked

**Result:** `{ok: true, domain: "undefined", errors: [], warnings: [{code: "ERR_LITERAL_MISSING", detail: "@heartbeat"}]}`

### 6.5 Guard Failure — Undefined Propagates to Non-Execution

**Noe chain:**

```
shi @zone_clear khi sek mek @move_forward sek nek
```

**Context:**

```json
{
  "C_safe": {
    "modal": {"knowledge": []},
    "literals": {}
  },
  "mode": "strict"
}
```

**Validation:**

1. Epistemic: `shi` checks @zone_clear ∈ C_safe.modal.knowledge → NOT present → undefined
2. Guard (`khi`): guard is undefined → action blocked
3. Per NIP-005: undefined propagates → non-execution

**Result:** `{ok: false, domain: "undefined", errors: [{code: "ERR_CONTEXT_INCOMPLETE", detail: "@zone_clear not grounded"}]}`

## 7. Conformance Requirements

All implementations claiming Noe protocol compliance MUST:

1. Implement Verified Compiler with morphology, grammar, and registry validation (Sections 4.1)
2. Implement Validator with all five validation stages (Section 4.2)
3. Enforce P_canon as immutable single source of truth (Section 4.3)
4. Detect and reject non-idempotent canonicalization (Section 4.3.2)
5. Validate context staleness against max_skew_ms (Section 4.4)
6. Validate epistemic operators (`shi`, `vek`, `sha`) against modal sets in C_safe (Section 4.5)
7. Enforce guard semantics exactly as specified (Section 4.6.3)
8. Implement strict and partial validation modes (Section 4.7)
9. Return error codes from the normative list (Appendix A)
10. Implement hash namespace separation (Section 4.3.3)
11. MUST NOT re-canonicalize downstream of Verified Compiler
12. MUST NOT treat undefined as true for guards or defaults
13. MUST NOT permit action execution when elements are missing, stale, or unsafe

Non-conforming implementations are NOT compliant with NIP-015 and MUST NOT claim Noe protocol support.

---

## 8. Backwards Compatibility

NIP-015 v1.0 establishes baseline behavior for the Verified Compiler and Validator. Future versions may:

- Add new error codes (with normative vs. informative designation)
- Extend validation stages (e.g., new epistemic modals)
- Allow alternative hash functions (SHA256 is required for v1.0)

Implementations MUST support strict mode parsing of NIP-015 v1.0 propositions in perpetuity. Changes to existing error code semantics require a new major version of NIP-015.

## 9. Security and Safety Considerations

### 9.1 Defense-in-Depth

The two-stage pipeline (compiler → validator) ensures:

- Early errors prevent bad data from reaching the interpreter
- Late errors catch context-dependent issues
- No single point of failure

### 9.2 Canonical Immutability

Preventing downstream re-canonicalization:

- Eliminates ambiguity in chain representation
- Ensures audit trails are faithful
- Prevents subtle mutations via re-encoding

### 9.3 Guard Semantics

Treating undefined as false prevents:

- Implicit defaults that hide missing information
- Silent permission grants due to missing context
- Accidental actions due to absent guards

### 9.4 Epistemic Grounding

Mandatory modals and staleness checks prevent:

- Actions based on stale information
- Ungrounded reasoning
- Nested uncertainty that compounds ambiguity

### 9.5 Action Safety

Validation before execution prevents:

- Execution of actions with undefined targets
- Actions with confidence below safety thresholds
- Deep recursion that exhausts resources
- Malformed action structures

### 9.6 Hash Namespaces

Separation of action and decision hashes prevents:

- Conflation of action outcomes with reasoning results
- Cross-domain hash collisions
- Ambiguous audit trails

### 9.7 Configuration Security

Parameterization (max_skew_ms, max_recursion_depth, etc.) allows operators to:

- Enforce domain-specific safety thresholds
- Prevent resource exhaustion (timeout via recursion limits)
- Tune staleness tolerance per use case

Implementations MUST document default parameter values and validate operator-supplied parameters.

### 9.8 Error Handling

All validation failures MUST result in explicit error codes. Implementations MUST NOT:

- Silently drop validation failures
- Proceed with partial results without marking errors
- Convert errors to warnings without operator configuration

| ERR_DELIVERY_MISMATCH † | Delivery operator (vus/vel) context mismatch | Validator |
| ERR_DEMONSTRATIVE_UNGROUNDED † | Demonstrative (dia/doq) cannot be resolved | Validator |
| ERR_SPATIAL_UNGROUNDABLE † | Spatial operator missing required position data | Validator |
| ERR_CANONICALIZATION_NON_IDEMPOTENT † | canonicalize(canonicalize(X)) ≠ canonicalize(X) | Compiler/Validator |
| ERR_RECURSION_LIMIT | Recursion depth exceeds max_recursion_depth | Validator |
| ERR_SAFETY | Guard evaluation raised exception | Validator |
| ERR_CONTEXT_INCONSISTENT | Proposition and its negation both in same modal set (NIP-017 Rule 4) | Validator |
| ERR_MISSING_EVIDENCE | Evidence object null or missing required fields (NIP-017 Rule 3) | Validator |
| ERR_STALE_EVIDENCE | Evidence timestamp exceeds staleness limit (NIP-017 Rule 2) | Validator |
| ERR_UNSAFE_THRESHOLDS | Epistemic threshold below safety floor (NIP-017 §4.7) | Configuration |

> **Note on ERR_STALE_CONTEXT / ERR_CONTEXT_STALE**: Both codes exist in noe-gate v1.0 — `ERR_STALE_CONTEXT` in the validator and `ERR_CONTEXT_STALE` in the runtime. They describe the same condition (context data exceeds temporal freshness threshold). Implementations MUST accept both codes as equivalent for v1.0 compatibility. Future versions SHOULD consolidate to a single canonical code.

## Appendix B: Validation State Machine

```
[Compiler Input]
    |
    v
[Morphology Validation]  → ERR_MORPHOLOGY, ERR_PARSE_FAILED
    |
    v
[Grammar Validation]     → ERR_PARSE
    |
    v
[Registry Validation]    → ERR_INVALID_LITERAL
    |
    v
[P_canon, parse_repr]
    |
    +------------------------------------+
    |                                    |
    v                                    v
[Validator Input]              [Interpreter Queue]
    |
    v
[Context Completeness]         → ERR_CONTEXT_STALE
    |
    v
[Epistemic Validation]         → ERR_BAD_CONTEXT, ERR_EPISTEMIC_MISMATCH
    |
    v
[Literal Validation]           → missing → error (strict) or undefined (partial)
    |
    v
[Action Validation]            → ERR_INVALID_ACTION, ERR_UNDEFINED_TARGET, ERR_RECURSION_LIMIT
    |
    v
[Safety Threshold]             → ERR_UNSAFE_THRESHOLD, ERR_SAFETY
    |
    v
[C_safe, ValidatorResult]      → Interpreter or Reject
```
