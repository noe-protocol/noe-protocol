# NIP-009: Context Model and Safe Projection

## Abstract

NIP-009 defines the canonical Context Model for the Noe Protocol. All semantics (NIP-005), validation (NIP-014, NIP-015, NIP-017), operator grounding, epistemic evaluation, spatial reasoning, demonstratives, and action safety depend entirely on a deterministic, hierarchical, serializable context object.

This standard introduces:

- Three canonical context layers: C_root (global invariants), C_domain (task/environment config), C_local (live sensor layer)
- A deterministic merge operation
- A safe projection function π_safe, which resolves noise, contradictions, missing data, staleness, and ungrounded references, producing the canonical evaluation context C_safe
- Deterministic cryptographic hashing rules for all layers
- Complete rules for staleness, drift, demonstrative grounding, spatial grounding, epistemic consistency, and removal of probabilistic fields

NIP-009 is a frozen structural standard. No Noe interpreter, validator, agent, or runtime may deviate from this specification when producing or consuming context. Any system claiming Noe v1.0 conformance MUST implement NIP-009 exactly.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

---

## 1. Purpose

The purpose of NIP-009 is to establish a unified, deterministic context structure that guarantees:

- **Determinism across agents**: Identical context hashes yield identical evaluation results
- **Safety in multi-agent systems**: Divergent sensor readings collapse into undefined or error states, never contradictory actions
- **Serializable auditability**: Cryptographic hashing enables replayable, certifiable evaluation traces
- **Conflict resolution**: Noise, contradictions, stale data, and missing references are deterministically suppressed before semantics evaluation
- **Spatial and epistemic grounding**: All operators (demonstratives, spatial, epistemic) operate only on validated, complete data

---

## 2. Scope

This specification applies to:

- Any Noe Protocol v1.0 interpreter or validator
- All context construction, merging, and projection pipelines
- Multi-agent runtime environments and coordinated agent systems
- Systems requiring auditability, certification, or regulatory compliance

This specification does NOT apply to:

- Application-specific domain extensions (Tier-2 and above)
- Input data preprocessing unrelated to context layer construction
- Liveness, retry, or recovery strategies (see NIP-016)

---

## 3. Definitions

**C_root**: Global static invariants, identical across all agents and runtimes, unchanging at runtime.

**C_domain**: Environment or task-specific configuration, shared between collaborating agents.

**C_local**: Live sensor state and per-agent internal state, updated every evaluation tick.

**C_merged**: The result of deterministically merging all three layers with precedence C_local > C_domain > C_root.

**C_safe**: The canonical evaluation context produced by π_safe projection; the only legal input to semantics evaluation.

**π_safe**: Deterministic safe projection function that removes noise, conflicts, stale data, and ungrounded references from C_merged to produce C_safe.

**Staleness**: Age of a sensor reading or literal relative to the current timestamp; readings exceeding max_staleness_ms are filtered.

**Demonstrative**: Spatial reference operator (dia, doq) that requires grounded spatial state.

**Epistemic operator**: Knowledge (shi), belief (vek), or certainty (sha) claim dependent on valid literals and modality sets.

**Canonical JSON**: Serialization format per RFC 8785, ensuring deterministic byte-for-byte reproducibility.

**H_safe**: SHA-256 hash of the canonical JSON serialization of C_safe.

**Hash symmetry**: Identical semantic content MUST produce identical hashes across implementations.

## 4. Specification

### 4.1 Design Principles

NIP-009 rests on five core design principles:

1. **Layering**: Three distinct layers capture orthogonal categories of information (global, environmental, local), enabling scalable composition without conflicts.

2. **Determinism**: No probabilistic fields, no ambiguous selection, no implicit defaults. All nondeterminism is eliminated before semantics evaluation.

3. **Safe projection**: Raw data is unsafe. π_safe is the mandatory gateway from raw merges to semantic evaluation.

4. **Canonical serialization**: All hashes and comparisons MUST use RFC 8785 canonical JSON to guarantee hash symmetry across implementations.

5. **Drift to undefined**: When contexts diverge, evaluation MUST degrade into undefined or error, never into contradictory actions.

---

### 4.2 C_root — Global Invariants

C_root contains facts that are static, global, identical across all agents and runtimes, and independent of environment or mission.

#### 4.2.1 Required Structure

C_root MUST include:

```json
{
  "units": { },
  "globals": { },
  "thresholds": {
    "near": null,
    "far": null,
    "default_staleness_ms": null
  },
  "epistemic_defaults": {
    "knowledge": [],
    "belief": [],
    "certainty": {}
  },
  "demonstratives": {
    "dia": { },
    "doq": { }
  },
  "spatial_defaults": { }
}
```

Additional fields MAY exist but MUST remain static and MUST NOT encode agent-specific data.

#### 4.2.2 Invariants

- C_root MUST NOT change at runtime.
- C_root MUST be identical across all agents and evaluations.
- Fields MUST NOT reference C_local or C_domain state.

---

### 4.3 C_domain — Environment / Task Configuration

C_domain defines the shared environment for a mission, task, or collaborative space.

#### 4.3.1 Required Structure

```json
{
  "map": { },
  "entities": {
    "@example": { }
  },
  "environment_thresholds": { },
  "spatial": { },
  "temporal": {
    "frame_start": null,
    "frame_end": null
  },
  "modal": {
    "knowledge": [],
    "belief": [],
    "certainty": {}
  },
  "value_system": {
    "accepted": [],
    "rejected": []
  }
}
```

#### 4.3.2 Invariants

- C_domain MAY differ between missions.
- C_domain MUST be identical between collaborating agents within the same mission.
- C_domain MAY extend C_root but MUST NOT contradict it.

---

### 4.4 C_local — Live Sensor / Agent State

C_local is the only layer that changes on every evaluation tick.

#### 4.4.1 Required Structure

```json
{
  "timestamp": null,
  "literals": {
    "@example": {
      "value": true,
      "timestamp": null
    }
  },
  "spatial": {
    "agent_position": [],
    "objects": { },
    "thresholds": { }
  },
  "modal": {
    "knowledge": [],
    "belief": [],
    "certainty": { }
  },
  "delivery": { },
  "audit": { }
}
```

#### 4.4.2 Spatial Schema — Reserved Names (v1.0)

To avoid namespace collisions with Noe operators, the following JSON key names are **reserved** and MUST NOT appear in `C_local.spatial`:

- `vel` — collides with the `vel` (receive) operator (NIP-008). Use `velocity` instead.
- `pos` — deprecated abbreviation. Use `position` instead.

Canonical spatial entity keys are:

- `spatial.objects.*.position` — required (array of coordinates)
- `spatial.objects.*.velocity` — required when velocity-dependent operators (tra, fra) are used

π_safe MUST reject any spatial entity containing a `vel` or `pos` key and emit ERR_BAD_CONTEXT in strict mode. In partial mode, π_safe MUST rename `pos` → `position` and drop `vel` entirely (since it is ambiguous).

#### 4.4.3 Invariants

- C_local MAY contain more fields than C_domain or C_root.
- π_safe will suppress non-canonical, noisy, conflicting, or stale data.

---

### 4.5 Deterministic Merge

The canonical merge operation is:

```text
C_merged = merge(C_root, C_domain, C_local)
```

with precedence:

```text
C_local > C_domain > C_root
```

#### 4.5.1 Merge Rules

1. **Object fields**: Deep merge with higher-layer keys replacing lower-layer keys.
2. **Lists**: Replace wholesale (never concatenate).
3. **Null values**: A null value overrides the lower layer.
4. **Missing fields**: Inherit from lower layers.
5. **Schema flexibility**: Unknown fields MAY exist but will be removed by π_safe if unsafe or irrelevant.

**Modal sets explicitly**: The `modal` field exists in both C_domain and C_local. Per rule 2, C_local.modal.knowledge **replaces** C_domain.modal.knowledge wholesale — it does NOT union with it. The same applies to modal.belief and modal.certainty. This is intentional: C_local reflects the agent's current epistemic state, which supersedes any domain-level defaults. If an implementation requires epistemic accumulation across layers, it MUST perform that union in an input adapter (§4.6.1) before populating C_local, not during merge.

#### 4.5.2 Determinism

This merge MUST be deterministic across all implementations. No implementation-specific strategies are permitted.

---

### 4.6 Safe Projection (π_safe)

C_merged includes raw real-world data, which may be contradictory, noisy, incomplete, stale, or ungroundable. π_safe transforms C_merged into C_safe, the only legal evaluation context.

```text
C_safe = π_safe(C_merged)
```

π_safe MUST be deterministic and MUST apply the following transformations in the prescribed order.

#### 4.6.1 Deterministic Input Adapters (Optional)

Some deployments MAY apply deterministic preprocessing to raw sensor or model confidence streams before populating C_local. One example is a hysteresis adapter that converts a numeric confidence signal into a stable boolean literal.

**Rules**:

1. Input adapters run before merging and before π_safe.
2. Adapters MUST NOT invent values. If input is missing or unexpired, the adapter MUST emit null (undefined).
3. Adapters MUST emit canonical literal records only: `{ "value": true | false | null, "timestamp": <ms> }`.
4. Adapters MUST NOT introduce probabilistic/confidence values into C_safe.
5. Given identical input streams and configuration, adapter outputs MUST be deterministic.

#### 4.6.2 Noise Removal

π_safe MUST remove:

- Contradictory literals
- Fields without timestamps when timestamps are required
- Probabilistic or confidence-based values
- Malformed entries
- Duplicates and multi-valued sensor readings

**Example**: If `@door = true` and `@door = false` both exist, then `@door = undefined`.

#### 4.6.3 Conflict Resolution

If two independent sources disagree (value1 ≠ value2):

1. Remove the literal
2. Set its value to undefined
3. Remove it from epistemic sets
4. Agents MUST NOT guess which value is correct

#### 4.6.4 Staleness Filtering

If `now - literal.timestamp > max_staleness_ms`, then π_safe removes the literal. Staleness MUST be applied before semantics (see §4.9).

#### 4.6.5 Epistemic Consistency

π_safe MUST ensure:

- No epistemic fact remains about a removed literal
- No shi claim contradicts C_safe
- No belief (vek) set asserts missing values
- Certainty values correspond to grounded sources

**Example**: If @door is suppressed:

```json
{
  "modal": {
    "knowledge": [],
    "belief": [],
    "certainty": {}
  }
}
```

#### 4.6.6 Deterministic Demonstrative Resolution Prerequisite

Before a chain can evaluate demonstratives (dia, doq):

- π_safe MUST ensure the spatial subsystem is complete
- Exactly one referent MUST be resolvable
- Otherwise demonstratives evaluate to undefined

π_safe must eliminate multi-referent ambiguity, missing spatial frames, and incomplete relative location data.

#### 4.6.7 Spatial Grounding Requirements

π_safe MUST ensure:

- nel, tel, xel, tra, fra have valid spatial maps
- Required distance/orientation thresholds exist
- Missing data → literal removed → undefined semantic evaluation

Spatial operators MUST never operate over uncertain or ungrounded fields.

#### 4.6.8 Removal of Probabilistic or Fuzzy Values

Any field containing confidence, probability, uncertainty metrics, or fuzzy classifications MUST be removed. Noe semantics are not probabilistic.

#### 4.6.9 Removal of Non-Canonical Fields

π_safe must remove any field not recognized as canonical unless explicitly required by a domain extension (Tier-2+).

---

### 4.7 C_safe — Required Final Structure

After merging and projection, the interpreter receives C_safe with this canonical structure:

```json
{
  "timestamp": null,
  "literals": {
    "@example": true
  },
  "modal": {
    "knowledge": [],
    "belief": [],
    "certainty": {}
  },
  "spatial": {
    "agent_position": [],
    "objects": {},
    "thresholds": {
      "near": null,
      "far": null
    },
    "orientation": {}
  },
  "temporal": {
    "now": null,
    "history": []
  },
  "demonstratives": {
    "dia": {},
    "doq": {}
  },
  "relations": {},
  "delivery": {},
  "audit": {},
  "value_system": {
    "accepted": [],
    "rejected": []
  },
  "meta": {
    "H_root": "",
    "H_domain_pack": "",
    "H_local": "",
    "H_safe": ""
  }
}
```

All fields required by NIP-005 and NIP-015 MUST exist.

- **Strict mode**: If any required field is missing or malformed → ERR_BAD_CONTEXT
- **Partial mode**: Missing fields → undefined

The interpreter MUST NOT evaluate a chain against anything except C_safe.

### 4.8 Context Hashing

Every context layer MUST be independently hashable using SHA-256 over canonical JSON (RFC 8785).

#### 4.8.1 Required Hashes

```text
H_root         = SHA-256(canonical_json(C_root))
H_domain_pack  = SHA-256(canonical_json(C_domain))
H_local        = SHA-256(canonical_json(C_local))
H_safe         = SHA-256(canonical_json(C_safe))
```

The canonical name is `H_domain_pack`. Early drafts used `H_domain`; implementations encountering this legacy key MUST treat it as an alias for `H_domain_pack`.

#### 4.8.2 Inclusion in C_safe

C_safe MUST contain:

```json
{
  "meta": {
    "H_root": "<sha256>",
    "H_domain_pack": "<sha256>",
    "H_local": "<sha256>",
    "H_safe": "<sha256>"
  }
}
```

#### 4.8.3 Purpose

Hashing enables:

- Deterministic provenance for every evaluation
- Cross-agent state comparison
- Replay verification
- Drift detection
- Auditability for regulators and external systems

Two agents MUST compare hashes—not raw JSON—to determine whether their contexts match.

#### 4.8.4 Determinism Requirement

Different implementations MUST produce identical hashes for identical semantic content. Therefore:

- Keys MUST be sorted
- Floats MUST be canonicalized
- null MUST be explicit
- No NaNs, infinities, or symbolic placeholders

Hash mismatches MUST trigger context incompatibility errors in multi-agent environments.

---

### 4.9 Staleness Semantics

Staleness is a core safety invariant of Noe.

#### 4.9.1 Staleness Check

For any field with a timestamp:

```text
if temporal.now - field.timestamp > thresholds.max_staleness_ms
  → ERR_STALE_CONTEXT (strict mode)
  → undefined (partial mode)
```

max_staleness_ms is resolved from: C_local.thresholds → C_domain.thresholds → C_root.thresholds.

#### 4.9.2 Staleness Before Semantics

Interpretation MUST NOT occur until staleness is evaluated. Order:

1. Merge
2. π_safe filtering
3. Staleness evaluation
4. Semantics evaluation

In strict mode, if stale, interpretation MUST NOT proceed.

#### 4.9.3 Multi-Agent Staleness

If agents disagree on staleness, the system MUST choose the stricter staleness rule. Stale data MUST NOT be shared. No agent may infer missing data.

#### 4.9.4 Stale Epistemic Data

If a literal is stale, then:

- All shi claims referencing it MUST be removed
- All vek beliefs referencing it MUST be removed
- All certainty weights MUST be dropped

#### 4.9.5 Clock Skew (Strict Mode)

Strict mode MUST enforce deterministic skew checks:

```text
skew_ms = | wall_clock_now - temporal.now |

if skew_ms > temporal.max_skew_ms
  → ERR_BAD_CONTEXT (strict)
  → undefined (partial)
```

If temporal.now itself is skew-invalid, staleness evaluation MUST NOT proceed; the validator emits ERR_BAD_CONTEXT. Implementations MUST NOT correct or adjust temporal.now.

---

### 4.10 Determinism Guarantees

NIP-009 establishes two determinism guarantees:

#### 4.10.1 Identical C_safe Hashes

If `H_safe(A) == H_safe(B)`, then `eval_A(chain) == eval_B(chain)`.

This MUST hold even if:

- Agents run different hardware
- Agents use different internal architectures
- Agents use different Noe interpreter implementations

This is enforced by canonical grammar (NIP-004), frozen semantics (NIP-005), frozen validation rules (NIP-015), deterministic π_safe projection, and canonical JSON hashing.

#### 4.10.2 No Contradictory Actions Under Divergent C_local

If `C_local(A) != C_local(B)`, then:

- Agents MAY diverge
- But MUST NOT produce contradictory actions

**Example**: Agent A detects `@human_present = true`, Agent B sees no human. Evaluating a chain that produces an action under A:

- Agent A MAY produce `action: halt`
- Agent B MUST produce either `false` or `ERR_LITERAL_MISSING` (strict)
- Agent B MUST NOT produce `action: resume`

#### 4.10.3 Safety Invariant

Divergence must degrade into undefined/error, never into contradictory actions. When contexts diverge, Noe enforces:

- Undefined propagation (three-valued truth semantics per NIP-005)
- Epistemic grounding suppression
- Literal completeness checks

This ensures: `undefined ⇒ non-execution`, `error ⇒ non-execution`.

---

### 4.11 Error Semantics

Errors MUST be surfaced by the validator before interpretation. Errors MUST NEVER be converted to undefined. Errors MUST NEVER be silently corrected by the interpreter.

#### 4.11.1 Canonical Error Types

| Error Code | Meaning |
|---|---|
| ERR_BAD_CONTEXT | Missing or malformed required subtree |
| ERR_STALE_CONTEXT | Timestamp exceeds staleness threshold |
| ERR_CONTEXT_INCOMPLETE | Required subsystem missing (e.g., no spatial map) |
| ERR_LITERAL_MISSING | Literal absent in strict mode |
| ERR_UNDEFINED_TARGET | Action operator missing required literal target |
| ERR_SPATIAL_UNGROUNDABLE | Spatial operator missing grounding data |
| ERR_EPISTEMIC_MISMATCH | Epistemic operator cannot be grounded |
| ERR_INVALID_LITERAL | Literal name malformed or unsupported |
| ERR_PARSE_FAILED | Syntax invalid according to NIP-004 |

#### 4.11.2 Error Precedence Rule

If multiple errors apply:

```text
ERR_BAD_CONTEXT > ERR_STALE_CONTEXT > ERR_CONTEXT_INCOMPLETE
  > ERR_LITERAL_MISSING > others
```

The highest-precedence error MUST be emitted.

#### 4.11.3 Differentiating Undefined vs. Error

- **undefined**: Structurally valid, semantically incomplete (propagates per NIP-005 truth tables)
- **error**: Context failure, structural failure, or rule violation (halts evaluation)

Undefined MUST propagate through truth evaluation per NIP-005 (three-valued logic).
Errors MUST halt evaluation immediately.

#### 4.11.4 Liveness Separation

When an error is encountered, the interpreter MUST:

- Return domain = "error"
- Stop

It MUST NOT:

- Retry
- Backoff
- Refresh context
- Choose defaults
- Attempt degraded operation

All liveness behavior is defined externally in NIP-016.

---

### 4.12 Serialization Standard

All Noe contexts MUST serialize using Canonical JSON (RFC 8785).

#### 4.12.1 Canonical Serialization Rules

1. **UTF-8 encoding only**
2. **Sorted keys** in lexicographic order
3. **No comments**
4. **No trailing commas**
5. **Strings MUST NOT contain control characters**
6. **Numbers MUST use canonical formatting**: No trailing zeros, no leading zeros (except "0"), no NaN or infinity
7. **Explicit null fields** allowed, but MUST be consistent across layers
8. **Timestamps MUST be numeric** (ms since epoch)
9. **Boolean MUST use true/false**

#### 4.12.2 Serialization Targets

The following MUST be serializable:

- C_root
- C_domain
- C_local
- C_merged (intermediate)
- C_safe (final)

Hashes MUST be computed over these canonical serializations only. Any implementation using noncanonical JSON MUST normalize before hashing.

## 5. Rationale

### 5.1 Why a Context Standard is Necessary

Natural languages tolerate ambiguity and unstated assumptions. Noe does not. Every operator—logical, spatial, demonstrative, epistemic, delivery, audit—depends on values provided by structured context. If two agents evaluate the same chain under different interpretations of space, time, entity references, epistemic sets, value systems, or literals, they may diverge in ways that cannot be detected afterward.

NIP-009 ensures all grounding is explicit, enabling deterministic multi-agent coordination in safety-critical domains.

### 5.2 Why Layering is Essential

Three layers (C_root, C_domain, C_local) capture three distinct categories of information:

- **C_root**: Global, permanent, identical across agents
- **C_domain**: Environment/task-specific, shared between collaborating agents
- **C_local**: Agent-specific, noisy, sensor-derived, constantly changing

This hierarchy guarantees consistency regardless of which agent gathers which data.

### 5.3 Why π_safe Must Be a Hard Projection

Real-world systems contain noise and contradictions. If two sensors report conflicting states, there is no safe way for an agent to "guess" the correct one. π_safe eliminates contradictions, removes stale values, drops uncertain data, and suppresses conflicting literals. The result may be less information, but it is safe information.

### 5.4 Why Deterministic Hashing is Essential

To certify a chain evaluation, regulators and auditors must verify: `chain + C_safe → output`. This is only possible if C_safe is canonical, hashing is deterministic, and merge rules produce the same structure across agents. Without NIP-009, replayability and certification are impossible.

### 5.5 Why Drift Behavior Must Be Explicit

Two agents operating in the same environment cannot avoid drift (asynchronous sensors, occlusion, latency, frame drops). Drift must cause divergence into undefined or error states, never contradictory actions. The cross-agent determinism invariant guarantees this: if two agents share C_safe (same hash), they produce identical outputs; if not, they degrade gracefully.

### 5.6 Why Demonstratives, Spatial Operators, and Epistemics Require Strong Grounding

Operators such as dia/doq (demonstratives), nel/tel/xel/tra/fra (spatial relations), and shi/vek/sha (epistemic operators) are meaningless unless the underlying spatial, temporal, literal, and epistemic structures are complete and unambiguous. NIP-009 ensures all required data is present and consistent.

## 7. Conformance Requirements

An implementation is NIP-009 compliant if and only if:

### 7.1 Layer Implementation

It MUST implement all three canonical layers: C_root, C_domain, C_local. No additional layers may be inserted between them.

### 7.2 Deterministic Merge

It MUST merge layers using: `C_merged = merge(C_root, C_domain, C_local)` with precedence `C_local > C_domain > C_root`.

### 7.3 π_safe Projection

It MUST implement π_safe exactly: noise removal, conflict suppression, epistemic set consistency, deictic preconditions, probabilistic field elimination, stale field filtering.

No implementation may override, weaken, or omit any π_safe rule.

### 7.4 Staleness Enforcement

Staleness MUST be checked before semantics. Stale readings MUST produce ERR_STALE_CONTEXT.

### 7.5 Deterministic Hashing

It MUST compute H_root, H_domain_pack, H_local, and H_safe using canonical JSON (RFC 8785) and SHA-256.

### 7.6 Interpreter Consumption

The interpreter MUST use C_safe only. Evaluating a chain against raw layers is prohibited.

### 7.7 Multi-Agent Determinism

Implementations MUST guarantee:

- Identical C_safe hashes → identical results
- Divergent C_local → disagreement collapses into undefined/error, not contradictory actions

### 7.8 Serialization Compliance

All exported contexts MUST follow RFC 8785 canonical JSON. Any system emitting noncanonical JSON is non-compliant.

---

## 8. Backwards Compatibility

NIP-009 establishes the v1.0 context specification as frozen. Future versions MAY introduce new optional fields within existing layers, but MUST NOT:

- Remove required fields
- Change merge semantics
- Weaken π_safe rules
- Alter hash computation
- Modify staleness thresholds

Legacy systems using non-canonical context formats MUST upgrade to NIP-009 to achieve v1.0 compliance.

## 9. Security and Safety Considerations

### 9.1 Contradiction Safety

Contradictory sensor readings are not debated; they are eliminated. This prevents agents from choosing between conflicting truths and guarantees safety through incompleteness rather than false confidence.

### 9.2 Staleness as Attack Surface

Stale context can enable desynchronization attacks in multi-agent systems. NIP-009 enforces strict staleness checks and requires stricter rules to win in multi-agent consensus. This prevents one slow agent from compromising safety for coordinated systems.

### 9.3 Clock Skew and Liveness Separation

Strict mode includes clock skew detection to prevent temporally incoherent evaluations. However, clock correction is external (NIP-016), ensuring that context remains faithful to observed evidence.

### 9.4 Demonstrative Grounding

Ungrounded demonstratives are undefined rather than inferred. This prevents spatial operators from silently degrading when spatial data is incomplete, which could cause positional errors in robotics applications.

### 9.5 Cryptographic Provenance

SHA-256 hashing enables cryptographic proof of deterministic evaluation. Auditors and regulators can verify that a specific chain output was produced under a specific context, enabling certification and liability tracking.

### 9.6 Determinism as Safety Property

The guarantee that identical C_safe hashes produce identical results is a safety property: it enables verification, replayability, and forensic analysis of agent behavior.
