# NIP-004: Core Grammar

## Abstract

This document defines the formal grammar of the Noe Protocol. It specifies how morphologically resolved tokens form chains: well-structured, deterministic expressions used by agents, evaluators, symbolic systems, and BCI engines. The grammar is defined as a Parsing Expression Grammar (PEG) that produces exactly one parse tree for every valid chain. NIP-004 covers clause and phrase formation, operator precedence, chain structure, explicit scopes, conditionals, embedded clauses, interrogatives, and structural extension points. The grammar defined in this NIP is frozen for v1.0; only bug fixes are permitted.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

## 1. Purpose

NIP-004 defines the complete syntactic rules for Noe chains. It specifies clause and phrase formation, operator arity and structural behavior, deterministic parse requirements, explicit precedence between operators, scope formation using sek...sek, unary operators (logical, temporal, epistemic, delivery, normative), binary operators (logical, comparative, relational, spatial), conditional forms using khi, embedded clauses via da, interrogative chain structure via qua, and structural slots for numeric expressions and intensity modifiers.

Semantics (truth evaluation, epistemics, numeric logic, delivery, audit) are defined in NIP-005 and related NIPs. Grammar defines how chains are formed, not what they mean.

## 2. Scope

### 2.1. In Scope

Syntactic structure of Noe chains, operator arity and structural behavior, deterministic parse requirements, explicit precedence between operators, scope formation (sek...sek), all unary and binary operator classes, conditional guard forms (khi), embedded clauses (da), interrogative chains (qua), structural slots for numeric expressions (NIP-007) and intensity modifiers (NIP-006), the formal PEG grammar, and the Operator Extension Protocol.

### 2.2. Out of Scope

Morphology (NIP-003), semantic evaluation (NIP-005), scalar semantics (NIP-006), numeric logic semantics (NIP-007), BCI/haptic/light encoding, transport-layer concerns, and parser implementation details beyond the normative PEG.

## 3. Definitions

**Chain:** A complete, ordered symbolic expression optionally terminated by nek.

**Clause:** A syntactic unit formed from atoms, unary operations, binary operations, conditional forms, embedded propositions, or explicit scopes.

**Atom:** The smallest syntactic unit. Atoms include literals (@x, true, false, numeric literals), glyph roots (Tier-0 and Tier-1 items from the registry), nominal or verbalized forms that have already passed morphology, and action events (mek and men with a target).

**Morphological Resolution:** All fusion, inversion, nominalization, and mek-conversion MUST be fully resolved before grammar applies. Grammar NEVER interprets morphology; it sees only already-formed tokens.

**Deterministic Parse:** Every valid chain yields exactly one syntactic interpretation. Multiple valid parses MUST trigger ERR_AMBIGUOUS_PARSE.

**Token Boundary:** Operators are recognized only as standalone tokens, never as substrings of other tokens. The tokenizer MUST apply longest-valid-token preference. LITERAL_SYM (e.g., @banana) is opaque; internal substrings MUST NOT become separate tokens.

## 4. Specification

### 4.1. Core Grammar Principles

**Deterministic Parsing:** Every valid chain MUST have exactly one parse.

**Morphology First:** All lexical operations MUST resolve prior to grammar. The grammar operates over a token stream in which each token is already a valid glyph, literal, or morphologically resolved fused form.

**Explicit Structure:** There is no implicit grouping. All structure arises from explicit operators, scope markers (sek), and the chain terminator (nek).

**Minimal Syntax:** Only syntax required for Tier-0 and Tier-1 is included. Extension NIPs MAY extend grammar via the Operator Extension Protocol (Section 4.12).

**Predication Status:** Glyphs used for predication (es) and nominalization (tok, al) MAY appear as atoms, but predicative semantics are out of scope for v1.0. Future NIPs will formalize predication; until then, implementations MUST treat them as opaque roots with no special model-theoretic behavior. Note: `es` appears in examples throughout the protocol (e.g., `dai es fel`) as a syntactically valid atom. These usages are grammatically correct under this specification; the deferral concerns only the formal model-theoretic semantics of predication, not the syntactic acceptability of `es` as a token.

### 4.2. Grammar Operators

Epistemic operators (shi, vek, sha) and the normative operator (tor) are not logical connectives in the Boolean sense. They are typed unary predicates over propositions, applied to clauses at the semantic level, often via embedded clauses introduced with da.

#### 4.2.1. Logical Unary Operators

| Glyph | Meaning | Notes |
|-------|---------|-------|
| nai | Logical negation | Unary NOT |
| nex | Exclusion | Removes from active domain |

These apply only to the immediately following clause or primary expression.

#### 4.2.2. Temporal Unary Operators

| Glyph | Meaning | Notes |
|-------|---------|-------|
| nau | Present reference | Unary temporal |
| ret | Past reference | Unary temporal |
| tri | Future reference | Unary temporal |
| qer | Repetition / loop | Unary temporal |

Temporal unary operators share a precedence band with other core unary operators (Section 4.7). They modify only the immediately following clause and introduce no implicit scope.

#### 4.2.3. Epistemic and Normative Unary Operators

| Glyph | Meaning | Notes |
|-------|---------|-------|
| shi | Knowledge | Unary epistemic over P |
| vek | Belief | Unary epistemic over P |
| sha | Near certainty | Unary epistemic over P |
| tor | Normative correctness | Unary predicate over P |

These operators apply to the immediately following clause or primary expression and are resolved against C_safe.modal and C_safe.value_system as specified in NIP-005.

#### 4.2.4. Relational Binary Operators

| Glyph | Meaning | Notes |
|-------|---------|-------|
| kos | Relation / from source | Relational connective |
| til | Relation / to target | Relational connective |

Form: `X kos Y` or `P til Q`. These sit in the relational precedence band. Their semantics are defined in NIP-005.

#### 4.2.5. Spatial and Integrity Binary Operators

| Glyph | Meaning | Notes |
|-------|---------|-------|
| nel | Near / proximal | Spatial predicate |
| tel | Far / distal | Spatial predicate |
| xel | Aligned / oriented | Spatial predicate |
| tra | In front of / ahead | Directional |
| fra | Behind / opposite | Directional |
| en | Containment / in region | Spatial predicate (D_spatial, Tier-0) |
| kra | Assertion / integrity check | Binary operator (D_action, Tier-0) |

These connect a left and right expression and are interpreted against C_safe.spatial or C_safe.integrity as defined in NIP-005 and NIP-010.

#### 4.2.6. Conditional Guard Operator (khi)

Canonical form (infix, one-armed guard):

```noe
GuardExpr khi sek ActionExpr sek
```

The left operand (GuardExpr) MUST be truth-typed at the semantic level. The right operand (ActionExpr) MUST be action-typed (or a list of actions). If the guard evaluates to true, the action scope executes. If the guard evaluates to false or undefined, the action scope MUST NOT execute and yields undefined.

khi MUST always be followed by `sek ActionExpr sek`. Short forms such as `shi @p khi mek halt` are not permitted in the v1.0 grammar. All guarded actions MUST use the explicit scoped form.

#### 4.2.7. Logical Binary Operators

| Glyph | Meaning |
|-------|---------|
| an | Logical AND |
| ur | Logical OR |

These are left-associative unless overridden by scope (sek...sek).

#### 4.2.8. Scope Operator (sek)

sek MUST appear in pairs. The content between sek tokens MUST be a valid expression. Empty scope is invalid. Unpaired sek MUST raise ERR_EMPTY_SCOPE. Scope overrides operator precedence.

Parenthesized expressions `(Expr)` are syntactic sugar for `sek Expr sek` and MUST produce an identical parse tree. Implementations MUST accept both forms. The parenthesized form exists for programmer familiarity; `sek...sek` remains the canonical scoping mechanism in spoken, haptic, and BCI modalities where parentheses are unavailable.

#### 4.2.9. Clause Introduction (da)

da introduces an embedded clause: `shi da P`, `vek da P`, `sha da P`, `tor da P`. da binds to the following expression P and is treated as a unary operator at the core unary precedence level.

#### 4.2.10. Interrogative Operator (qua) and WH-Roots

qua marks a chain as a question. It MUST appear only as the first token. It MUST NOT appear inside an expression. The chain MUST terminate with nek.

WH-roots: soi (entity / "what"), kru (agent / "who"), fek (explanation / "why"). WH-roots appear inside the question body but do not alter expression structure. Their semantics are defined in NIP-005.

#### 4.2.11. Intensity Operators (Optional)

If NIP-006 is implemented, postfix unary intensity modifiers (single-quote ', double-quote ", degree °) attach to permitted atoms after morphology and before grammar atom handling. These operators apply multiplicative scaling factors (0.5x, 1.0x, 2.0x respectively) to the scalar magnitude of their target. Attachment rules are semantic and enforced by NIP-006.

#### 4.2.12. Delivery and Audit Glyphs

Delivery and audit glyphs participate syntactically as unary delivery operators (vus, vel) and action events (mek, men). Their semantics are defined in NIP-005, NIP-008, and NIP-010.

### 4.3. Chain Termination

Every Noe chain has an implicit end at the message boundary. nek MAY appear zero or one time in a chain. If present, nek MUST be the final token. Anything after nek is a grammar error. nek MUST NOT appear inside sek...sek scopes, between an operator and its operand, between da and its clause, or inside the body of qua before the final terminator. nek has no semantic value; it is a purely syntactic terminator and MUST NOT affect truth values or action semantics.

### 4.4. Interrogative Chains

**Form:** `qua QuestionBody nek`

qua MUST be the first token. nek MUST terminate the chain. Nothing may follow nek. QuestionBody consists of an optional QuestionType (soi, kru, or fek) followed by an Expr. When QuestionType is present, the parser MUST produce an AST node that includes the type tag (soi, kru, or fek) alongside the body expression. When QuestionType is omitted, the parser MUST produce a QuestionBody node with no type tag; inference of the answer domain is a semantic concern deferred to NIP-005 and MUST NOT affect the parse tree.

**Valid:** `qua soi sek hum es fel sek nek`

**Invalid:** `khi qua soi hum es fel nek` (qua not at position 1)

### 4.5. Token Boundary Rules

Operators are recognized only as standalone tokens, never as substrings of other tokens. `mekan` is not `mek`; `@banana` MUST NOT leak the token `an`; `mek an vus` MUST tokenize as exactly three tokens: [mek] [an] [vus].

Scanners MUST NOT extract operators from inside IDENT or LITERAL_SYM. Longest-valid-token matching MUST be applied at the lexical stage. Violations trigger ERR_AMBIGUOUS_PARSE or ERR_UNKNOWN_GLYPH.

### 4.6. Reserved Tokens

The morphology joiner (·) is allowed only between valid glyph morphemes, MUST NOT begin or end a token, and MUST NOT appear inside LITERAL_SYM. Morphology roots (nei, tok) MUST tokenize as single tokens; partial/substring matches inside longer identifiers are prohibited.

### 4.7. Operator Precedence

Highest precedence first:

1. **Core unary operators** — nai, nex, shi, vek, sha, tor, nau, ret, tri, qer, vus, vel, da. Reserved unary roots (eni, sem, mun, fiu) MAY be defined by future NIPs.
2. **Action constructors** — mek, men (in the form `mek Atom` or `men Atom`). These construct values in the action domain.
3. **Comparative operators** — <, >, <=, >=, =
4. **Relational / spatial / integrity operators** — kos, til, nel, tel, xel, tra, fra, en, kra, noq. noq is a binary request operator of the form `entity noq action`; the right-hand operand MUST be action-typed. Semantics are defined in NIP-005.
5. **Conjunction** — an
6. **Disjunction** — ur
7. **Conditional guard** — khi

Scope (sek...sek) overrides precedence. nek is not an operator; it is a terminator consumed at parse time. Unary operators are right-associative, binary operators are left-associative, and khi is non-associative.

### 4.8. Formal Grammar (PEG)

This section defines the normative PEG grammar. In case of minor discrepancies between this PEG and the reference evaluator, the reference evaluator and conformance tests in NIP-011 are authoritative.

#### 4.8.1. Lexical Conventions

```peg
S           <- [ \t\r\n]*
S1          <- [ \t\r\n]+

TRUE        <- 'true'
FALSE       <- 'false'
NUMBER      <- ('0' / [1-9][0-9]*) ('.' [0-9]+)?
LITERAL_SYM <- '@' [A-Za-z0-9_]+
IDENT       <- [A-Za-z_][A-Za-z0-9_·]*

LPAR        <- '('
RPAR        <- ')'
```

#### 4.8.2. Top-Level Chains

```peg
chain
  <- S question_chain S !.
   / S statement_chain S !.

statement_chain
  <- Expr S ('nek' S)?

question_chain
  <- 'qua' S QuestionBody S 'nek' S

QuestionBody
  <- QuestionType S Expr
   / Expr

QuestionType
  <- 'soi' / 'kru' / 'fek'
```

#### 4.8.3. Expression Grammar

```peg
Expr
  <- GuardExpr

GuardExpr
  <- OrExpr (S 'khi' S ActionScope)?

ActionScope
  <- Scoped

OrExpr
  <- AndExpr (S 'ur' S AndExpr)*

AndExpr
  <- RelExpr (S 'an' S RelExpr)*

RelExpr
  <- CompExpr (S RelOp S CompExpr)*

RelOp
  <- 'kos' / 'til' / 'nel' / 'tel' / 'xel' / 'tra' / 'fra' / 'en' / 'kra' / 'noq'

CompExpr
  <- UnaryExpr (S CompOp S UnaryExpr)*

CompOp
  <- '<=' / '>=' / '<' / '>' / '='

UnaryExpr
  <- PrefixOp S UnaryExpr
   / Primary

PrefixOp
  <- 'nai' / 'nex' / 'shi' / 'vek' / 'sha' / 'tor'
   / 'nau' / 'ret' / 'tri' / 'qer'
   / 'vus' / 'vel' / 'da'
```

#### 4.8.4. Primary, Scoped, and Action Atoms

```peg
Primary
  <- Scoped / ActionEvent / ParenExpr / Atom

Scoped
  <- 'sek' S Expr S 'sek'

ParenExpr
  <- LPAR S Expr S RPAR

ActionEvent
  <- 'mek' S Atom
   / 'men' S Atom

Atom
  <- TRUE / FALSE / NUMBER / LITERAL_SYM / IDENT
```

If NIP-006 is implemented, a ScalarMod postfix is added:

```peg
Atom
  <- (TRUE / FALSE / NUMBER / LITERAL_SYM / IDENT) ScalarMod?

ScalarMod
  <- '\'' / '"' / '°'
```

#### 4.8.5. Invalid Forms

The following are rejected by this grammar or by validation:

- Multiple khi per GuardExpr without explicit scoping.
- khi not followed by sek...sek.
- nek occurring more than once or not at end of chain.
- qua appearing anywhere except as first token in question_chain.
- Unpaired sek.
- Empty sek...sek scopes.

### 4.9. Grammar Freeze Rule

The grammar defined in this NIP is a frozen component of the Noe Protocol. Only bug fixes are permitted. Any structural changes, operator reordering, or modifications that alter the parse tree or precedence MUST be introduced through a new NIP and treated as a protocol fork.

### 4.10. Operator Extension Protocol

Any NIP introducing new operators MUST define:

1. Arity (unary, binary, or justified n-ary).
2. Operator class (logical, numeric, epistemic, spatial, etc.).
3. Precedence band (one of the existing bands or a new band with an updated table).
4. Associativity (left, right, none).
5. Grammar insertion point (which nonterminal is extended).
6. Examples demonstrating legal and edge-case usage.

No extension may introduce a parallel grammar. All new operators MUST compose through the PEG defined in this NIP.

## 5. Rationale

The grammar is specified as a PEG rather than a context-free grammar because PEGs are inherently unambiguous: the ordered-choice operator eliminates the need for disambiguation rules. This guarantees the deterministic-parse property that Noe requires. The operator precedence table is deliberately flat (seven bands) to minimize cognitive load while preserving the necessary distinctions between unary, comparative, relational, logical, and conditional operators. The requirement that khi be followed by sek...sek (rather than allowing bare action expressions) prevents ambiguity in nested conditionals and ensures that the action scope is always syntactically delimited. The grammar freeze rule exists because any change to parse behavior would invalidate all existing chains and conformance tests.

## 6. Examples

### 6.1. Guarded Action

```noe
shi @human_present khi sek mek @halt sek nek
```

Parses as: GuardExpr = `shi @human_present`, ActionScope = `sek mek @halt sek`.

### 6.2. Interrogative

```noe
qua soi shi @human_present nek
```

Parses as: QuestionType = soi, Expr = `shi @human_present`.

### 6.3. Spatial Predicate

```noe
@robot nel @obstacle nek
```

Parses as: RelExpr with RelOp = nel connecting two atoms.

### 6.4. Nested Scope

```noe
sek @a an @b sek ur @c nek
```

Parses as: `((@a an @b) ur @c)` — scope overrides default precedence.

### 6.5. Embedded Clause

```noe
shi da @robot nel @target nek
```

Parses as: shi applies to the embedded clause `da (@robot nel @target)`.

## 7. Conformance Requirements

An implementation conforms to NIP-004 if and only if:

1. It accepts exactly the class of chains described by the PEG in Section 4.8.
2. It rejects chains that violate the rules for khi, sek, qua, or nek.
3. It parses all valid chains deterministically into a single AST.
4. It enforces token boundary rules: no false operator extraction inside tokens.
5. It implements longest-valid-token preference at the lexical stage.
6. It raises ERR_AMBIGUOUS_PARSE or ERR_UNKNOWN_GLYPH for non-conformant tokenization.
7. It passes the conformance tests defined in NIP-011 that exercise grammar behavior.

## 8. Backwards Compatibility

The grammar defined in this NIP is the first formal specification of Noe chain syntax. Earlier informal grammar descriptions are superseded by this document. All chains that were valid under informal specifications and that conform to this PEG remain valid. Chains that were informally accepted but violate this PEG (e.g., bare action after khi without sek...sek) are no longer valid and MUST be rejected.

## 9. Security and Safety Considerations

An ambiguous grammar would allow different evaluators to produce different parse trees for the same chain, leading to divergent semantic evaluation. In safety-critical deployments (robotics, autonomous agents), this divergence could produce contradictory actions. The PEG specification, combined with the deterministic-parse requirement and the grammar freeze rule, eliminates this class of vulnerability. The token boundary rules prevent injection attacks where operator glyphs are hidden inside literal names or identifiers.

### 9.1 Depth and Recursion Limits

The grammar permits recursive nesting via `sek...sek` scopes, `da`-embedded clauses, and chained unary operators. Pathologically deep chains can exhaust stack space, cause denial-of-service in constrained runtimes, or exceed processing budgets in BCI and haptic channels. Implementations SHOULD enforce a configurable maximum AST depth. The RECOMMENDED default is 100. Chains exceeding the configured depth limit MUST be rejected with error code `ERR_DEPTH_EXCEEDED`. Implementations targeting constrained environments (BCI, embedded, real-time) SHOULD set a lower limit appropriate to their resource budget.
