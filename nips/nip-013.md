# NIP-013: Domain Packs and Grounding Templates

## Abstract

Noe separates core semantics from domain knowledge. To operate safely in robotics, AI agents, and cyber-physical systems, a Noe Runtime must load one or more Domain Packs.

A Domain Pack defines:

- Available literals
- Sensor sources
- Required context fields
- Spatial and temporal grounding parameters
- Deixis thresholds
- Safety classifications
- Operator-to-context requirements (R_O)
- Canonical versioning and hashing

Noe does not perform grounding — the application does. A Domain Pack is a **schema contract** that documents the expected shape of grounded context so that the validator (NIP-015) can verify context completeness, freshness, and structural correctness. Domain Packs keep NIP-005 semantics domain-agnostic while giving deployments a machine-readable specification of "what the symbols mean in this world" and "what context the application must populate before evaluation."

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

This document uses:

- **C_root**, **C_domain**, **C_local**, **C_safe**, **C_rich** — Context levels from NIP-009
- **π_safe** — Safety-critical grounding projection (NIP-009)
- **R_O** — Operator requirements mapping (operator → required context paths)
- **H_domain_pack** — SHA-256 hash of Domain Pack canonical JSON (RFC 8785)
- **T, Dₙ, Dₛ, Dₑ, D_spatial, D_action** — Noe semantic domains (NIP-005)
- **undefined** — Suppresses all actions and marks evaluation incomplete
- **RFC 8785** — JSON Canonicalization Scheme (deterministic, comparable hashes)

## 1. Purpose

This NIP specifies:

1. A canonical Domain Pack JSON format for declaratively defining symbol-to-sensor mappings
2. The hashing and versioning rules for Domain Pack integrity and auditability
3. Advisory operator-to-context requirements (R_O) for grounding verification tooling
4. The integration of Domain Packs with:
   - NIP-009 context model (C_root, C_domain, C_local, π_safe)
   - NIP-015 verified validator pipeline
   - NIP-014 deixis semantics and spatial thresholds
5. The mapping between Domain Pack types and Noe semantic domains

**Architectural note**: Noe does not do grounding — your application does. The application reads sensors, applies thresholds, and populates `C_safe.modal.knowledge` and `C_safe.modal.belief` directly. Noe then checks membership in those sets during evaluation. A Domain Pack describes what context paths your grounding code should populate and what thresholds it should respect, but the runtime does not autonomously enforce `operator_requirements` or `safety` classifications. These fields are schema documentation consumed by external tooling, linters, and deployment validators — not by the Noe evaluator itself.

### 2.1 In Scope

- Canonical Domain Pack JSON structure and required fields
- Hashing rules (RFC 8785 canonicalization) and hash circularity resolution
- Operator-to-context requirements (R_O) specification
- Integration with C_root, C_domain, C_local context layers

- Literal type mapping to Noe semantic domains

- Learning or inference of Domain Pack structure

## 3. Definitions and Assumptions

### 3.1 Domain Pack

A JSON document that describes how symbols (literals) map to sensors, operational thresholds, required context fields, and safety classifications. A Domain Pack is a machine-readable specification of a concrete operational domain.

### 3.2 Canonical JSON

All hashing and identity comparisons MUST use **RFC 8785 – JSON Canonicalization Scheme**. This ensures:

- UTF-8 encoding
- Lexicographically sorted object keys
- Normalized floating-point representations
- Deterministic Unicode normalization
- Identical hashes for semantically equivalent packs

Hash functions operating outside RFC 8785 canonicalization produce non-comparable results and MUST be rejected.

### 3.3 Hash Circularity

A Domain Pack contains a "hash" field that holds the SHA-256 digest of the pack itself. To avoid circularity:

**Canonical Rule**: The "hash" field MUST be excluded when computing the canonical JSON and the resulting SHA-256 digest. The hash is computed over the entire pack with the "hash" field removed or set to null.

This allows validators to verify that a received Domain Pack matches the declared identity without requiring prior knowledge of the hash value.

### 3.4 π_safe Integration

The grounding architecture follows this flow:

1. The **application** reads sensors, applies domain-specific thresholds, and populates `C_rich`
2. **π_safe** (NIP-009, NIP-012) filters `C_rich` into `C_safe` based on freshness, confidence, and consistency
3. The **Noe evaluator** operates exclusively on `C_safe`

Domain Packs document the expected shape of `C_rich` and `C_safe` but do not drive the grounding process. Specifically:

- Evaluators MUST NEVER use raw `C_rich` for safety-critical decisions
- Validators MAY recompute `π_safe(C_rich)` to verify that the provided `C_safe` matches
- Mismatch between provided and computed `π_safe` MUST trigger rejection
- The Domain Pack's `required_context` paths describe what the application SHOULD populate — `π_safe` and the evaluator use them as a completeness check, not as a grounding instruction

### 3.5 Domain Type Mappings

The following type-to-domain mappings MUST be used for all "type" fields in Domain Pack literals:

| Domain Pack Type | Noe Domain | Meaning |
|---|---|---|
| "boolean" | T (truth) | Literal returns true or false |
| "numeric" | Dₙ | Numeric quantity (measurement) |
| "enum" | Dₛ | State or quality value |
| "set" | Dₑ | Entity set (membership) |
| "location" | D_spatial | Spatial region or coordinate |
| "event" or "action" | D_action | Action or event occurrence |

These mappings are normative for validator type-checking and semantic correctness. A Domain Pack literal using an unmapped or undefined type is non-compliant.

## 4. Specification

### 4.1 Top-Level Structure

A Domain Pack MUST be a JSON object with the following required top-level fields:

```json
{
  "id": "string",
  "version": "string",
  "hash": "string",
  "description": "string",
  "literals": { ... },
  "sensors": { ... },
  "spatial": { ... },
  "temporal": { ... },
  "safety": { ... },
  "operator_requirements": { ... },
  "adapters": { ... }
}
```

Where:

- **id** (required): Globally unique identifier for this pack (e.g., "noe.robotics.simple")
- **version** (required): Semantic version string (e.g., "1.0.0")
- **hash** (required): SHA-256 of RFC 8785 canonical JSON with "hash" field excluded
- **description** (required): Human-readable summary of the pack's purpose and domain
- **literals** (required): Object mapping literal names to literal definitions
- **sensors** (required): Object defining sensor modalities and fields
- **spatial** (required): Frames, thresholds, axes, and defaults for spatial grounding
- **temporal** (required): Staleness, latency, and time model parameters
- **safety** (required): Lists of critical and non-critical literals
- **operator_requirements** (required): Operator-to-context mappings for validator checks
- **adapters** (optional): Deterministic input adapters (e.g., hysteresis stabilization)

### 4.1.1 Identification and Versioning

- **id** MUST be a reversed-domain-style identifier (e.g., "noe.robotics.simple", "noe.manufacturing.assembly")
- **id** MUST be globally unique and human-readable
- **version** MUST follow semantic versioning (MAJOR.MINOR.PATCH)
- **hash** MUST be a lowercase hexadecimal string (SHA-256 = 64 characters)

The triple (id, version, hash) uniquely identifies a Domain Pack and its provenance. Validators MUST log this triple for auditability.

### 4.1.2 Adapters (Optional)

A Domain Pack MAY include an "adapters" object describing deterministic input-stabilization policies applied before values enter C_local or C_rich and before π_safe is computed.

Adapters MUST satisfy:

1. **Determinism**: Adapter output is a pure function of input, time, and adapter configuration
2. **No Inference**: Adapters MUST NOT infer or fabricate missing values or critical literals
3. **Transparency**: All adapter operations MUST be traceable in provenance logs
4. **Completeness**: Adapters do not override validator context-completeness rules; missing required_context fields remain missing

Typical adapters include hysteresis (hold times, thresholds) or temporal filtering, but NOT machine-learned transformations or inference.

### 4.2 Literals

The "literals" object maps literal names (prefixed with "@") to literal definitions. Each literal MUST specify:

```json
"@zone_clear": {
  "type": "boolean",
  "source": ["sensor.camera", "sensor.lidar"],
  "safety_critical": true,
  "description": "Zone in front of robot is free of obstacles",
  "required_context": [
    "C_local.sensors.camera.zone_status",
    "C_local.sensors.lidar.point_cloud"
  ]
}
```

**Required Fields:**

- **type** (required): MUST map to a Noe domain per Section 3.5 (boolean, numeric, enum, set, location, event, action)
- **source** (required): Array of sensor or model IDs that produce this literal
- **safety_critical** (required): Boolean; if true, undefined ⇒ non-execution
- **description** (required): Human-readable explanation of the literal's meaning
- **required_context** (required): Array of context paths needed to ground this literal

**Semantics:**

- A literal is **true** (or defined) only if all paths in required_context exist and have non-null values
- A missing required_context path ⇒ literal is **undefined** ⇒ context_incomplete = true
- A safety-critical undefined literal MUST suppress all actions

### 4.3 Sensors

The "sensors" object describes the physical or virtual sensors that populate the context:

```json
"sensors": {
  "sensor.camera": {
    "modality": "vision",
    "independence_group": "vision_group_1",
    "fields": [
      "C_local.sensors.camera.image",
      "C_local.sensors.camera.human_detections",
      "C_local.sensors.camera.zone_status"
    ]
  },
  "sensor.lidar": {
    "modality": "depth",
    "independence_group": "depth_group_1",
    "fields": [
      "C_local.sensors.lidar.point_cloud"
    ]
  }
}
```

**Required Fields:**

- **modality** (required): Type of sensor (e.g., "vision", "depth", "temperature", "controller")
- **independence_group** (required): Identifier for grouping independent sensors (used by π_safe)
- **fields** (required): Array of context paths this sensor populates

**Semantics:**

- Sensors in the same independence_group are assumed to have shared error modes and are not combined for π_safe
- Sensors in different groups can be fused safely (per NIP-009)

### 4.4 Spatial

The "spatial" object defines coordinate frames, thresholds, and axes:

```json
"spatial": {
  "frames": {
    "world": { "description": "Global world frame." },
    "robot_base": { "description": "Robot base frame." }
  },
  "thresholds": {
    "collision_distance_m": 0.5,
    "zone_radius_m": 2.0,
    "proximal_threshold_m": 1.0,
    "distal_threshold_m": 3.0
  },
  "axes": {
    "reference_frame": "world",
    "x_positive": "right",
    "x_negative": "left",
    "y_positive": "front",
    "y_negative": "back",
    "z_positive": "vertical_positive",
    "z_negative": "vertical_negative"
  },
  "defaults": {
    "frame_for_nel": "world"
  }
}
```

**Required Fields:**

- **frames** (required): Object mapping frame names to frame descriptions
- **thresholds** (required): Object with required deixis and spatial thresholds
- **axes** (required): Object mapping spatial axes to directions
- **defaults** (required): Default values for spatial reasoning

**Required Thresholds:**

- **collision_distance_m**: Safety distance for collision avoidance
- **zone_radius_m**: Radius of operational zone
- **proximal_threshold_m**: Distance threshold for "near" deixis (dia)
- **distal_threshold_m**: Distance threshold for "far" deixis (doq)

These thresholds are used by NIP-014 deixis operators and NIP-015 validators for spatial grounding and determinism.

### 4.5 Temporal

The "temporal" object specifies time-based grounding parameters:

```json
"temporal": {
  "stale_threshold_ms": 200,
  "max_latency_ms": 100,
  "time_model": "monotonic_ms"
}
```

**Required Fields:**

- **stale_threshold_ms** (required): Maximum age of context before data is considered stale
- **max_latency_ms** (required): Maximum acceptable latency for critical decisions
- **time_model** (required): Time semantics ("monotonic_ms", "wall_clock", etc.)

**Semantics:**

- Data older than stale_threshold_ms MUST NOT be used for safety-critical decisions
- Latency exceeding max_latency_ms triggers context_incomplete
- Used by NIP-015 validators and ret (temporal) operator from NIP-005

**Override Hierarchy**: The π_safe projection (NIP-012) uses `tau_stale_ms` from its `ProjectionConfig` (default 1000ms per NIP-009/NIP-012). A Domain Pack's `stale_threshold_ms` MAY specify a stricter (lower) value for a given deployment. When both are present, the application SHOULD use the **more restrictive** (smaller) value. Domain Packs MUST NOT set `stale_threshold_ms` higher than the protocol default without explicit justification in the pack's description.

### 4.6 Safety

The "safety" object classifies literals as critical or non-critical:

```json
"safety": {
  "critical_literals": ["@human_in_zone", "@zone_clear", "@temperature_safe"],
  "non_critical_literals": ["@load_balanced"]
}
```

**Semantics:**

The safety classification is **advisory metadata** consumed by deployment tooling, linters, and external validators — not by the Noe evaluator itself. The runtime does not read `critical_literals` or `non_critical_literals` at evaluation time.

- **Critical literals**: The application's grounding code SHOULD treat undefined critical literals as grounds for non-execution. External deployment validators SHOULD enforce this policy.
- **Non-critical literals**: Undefined non-critical literals SHOULD be logged but need not suppress execution.

> **Note**: The Noe evaluator enforces safety through the epistemic model (NIP-005, NIP-009): if a literal is not in `C_safe.modal.knowledge`, operators like `shi` return the appropriate K3 value. The safety classification in the Domain Pack tells the *application* which literals matter — it does not add runtime enforcement beyond what the epistemic model already provides.

### 4.7 Operator Requirements (R_O)

The "operator_requirements" object specifies, for each operator, what context paths the application's grounding code SHOULD populate:

```json
"operator_requirements": {
  "dia": {
    "required_context": [
      "C_local.demonstratives",
      "C_local.speaker.location",
      "C_domain.spatial.thresholds.proximal_threshold_m"
    ]
  },
  "doq": {
    "required_context": [
      "C_local.demonstratives",
      "C_local.speaker.location",
      "C_domain.spatial.thresholds.distal_threshold_m"
    ]
  },
  "nel": {
    "required_context": [
      "C_local.position.robot",
      "C_local.position.package",
      "C_root.spatial.frames",
      "C_domain.spatial.thresholds.collision_distance_m"
    ]
  },
  "ret": {
    "required_context": ["C_safe.temporal", "C_domain.temporal"]
  },
  "sha": {
    "required_context": ["C_safe.modal.certainty"]
  },
  "shi": {
    "required_context": ["C_safe.modal.knowledge"]
  },
  "vek": {
    "required_context": ["C_safe.modal.belief"]
  }
}
```

**Advisory Status:**

The `operator_requirements` field is **advisory metadata** — it documents what context paths the application's grounding code should populate before an operator can be meaningfully evaluated. The Noe evaluator does not read `operator_requirements` at runtime; operator semantics are enforced through the epistemic model (e.g., `shi` checks `C_safe.modal.knowledge` membership, `dia` checks `C_safe.spatial` presence).

**Recommended Tooling Behavior:**

External deployment validators, linters, and Domain Pack compliance checkers SHOULD:

1. Before deployment, verify that the grounding pipeline populates ALL paths listed in `operator_requirements` for each operator used in the expression set
2. Flag missing paths as deployment warnings or errors
3. NOT seed or merge missing `required_context` fields from defaults — this masks incompleteness

**Application Grounding Code:**

Application code that populates `C_rich` SHOULD use `operator_requirements` as a checklist: if the application uses spatial operators (nel, dia, doq), it MUST ensure the listed paths are populated before passing context to Noe.

### 4.8. Integration with Context Model (NIP-009)

Domain Packs populate the context hierarchy as follows:

- **C_root.spatial** ← Domain Pack spatial.frames, spatial.axes
- **C_domain.literals** ← Domain Pack literals (for audit and inference)
- **C_domain.sensors** ← Domain Pack sensors
- **C_domain.temporal** ← Domain Pack temporal
- **C_domain.safety** ← Domain Pack safety
- **C_domain.operator_requirements** ← Domain Pack operator_requirements

**Validator Correctness:**

Validators MAY recompute π_safe(C_rich) at runtime to verify that the provided C_safe matches the computed safe projection. If mismatched, the validator MUST:

1. Log the discrepancy
2. Use the computed C_safe instead
3. Or reject the execution if reconciliation fails

This enforcement of grounding correctness prevents sensor spoofing and ensures safety-critical decisions rest on verified π_safe values.

### 4.9. Integration with Verified Validator (NIP-015)

At runtime, the validator pipeline MUST perform the following steps:

1. **Load Domain Pack**: Deserialize the Domain Pack JSON
2. **Verify Hash**: Compute RFC 8785 canonical JSON (with "hash" field excluded) and verify SHA-256 matches the declared hash field
3. **Populate Context**: Merge Domain Pack data into C_root, C_domain
4. **Check Literal Completeness**: For each literal in the pack's `literals` section, verify that `required_context` paths exist in C_rich (this is the runtime's only normative use of `required_context` — via `is_explained_literal()` in π_safe)
5. **Apply Spatial/Temporal Grounding**: Use Domain Pack thresholds for deixis resolution and staleness checks
6. **Enforce π_safe**: Verify all safety-critical literals ground to C_safe (not C_rich)
7. **Output Provenance**: Include domain_pack_hash and domain_pack_id in validator output

> **Note**: The validator does NOT enforce `operator_requirements` at runtime. R_O checking is the responsibility of external deployment tooling (linters, pre-flight validators). The runtime enforces safety through the epistemic model and π_safe projection.

**Validator Output Requirement:**

The validator output MUST include:

```json
{
  "result": "valid|invalid|undefined",
  "context_complete": true|false,
  "domain_pack_hash": "<SHA-256 hash>",
  "domain_pack_id": "<id>",
  "domain_pack_version": "<version>",
  ...
}
```

And provenance (per NIP-010) MUST log:

```json
{
  "domain_pack_hash": "<hash>",
  "domain_pack_id": "<id>",
  "timestamp": "...",
  "operator_completeness": { ... }
}
```

This ensures full auditability and reproducibility of all decisions made under a Domain Pack.

## 5. Rationale

Domain Packs solve several critical problems in the design of safe, deployable Noe runtimes:

1. **Deterministic Grounding**: By explicitly declaring required context paths and thresholds, Domain Packs eliminate ambiguity about whether an expression can be evaluated
2. **Safety Classification**: Critical vs. non-critical literals allow the validator to implement the missing-grounding ⇒ non-execution guarantee
3. **Multi-Agent Interoperability**: Two agents can load the same Domain Pack and produce identical results
4. **Auditability**: Hash-based identity and provenance logging enable post-hoc verification and forensics
5. **Context Completeness**: R_O provides a machine-checkable specification of what must be true before an operator is safe
6. **Deixis and Spatial Determinism**: Explicit thresholds prevent referential ambiguity and ensure spatial operators produce the same result across deployments
7. **Decoupling Semantics from Deployment**: NIP-005 remains universal and domain-agnostic; Domain Packs carry all operational context

Without Domain Packs, a Noe expression is semantically meaningful but operationally unanchored — the application has no machine-readable specification of what context to populate. With a Domain Pack, the application knows exactly what its grounding code must provide, and the validator can verify that the provided context is structurally complete.

      "y_positive": "front",

## 7. Conformance Requirements

### 7.1 Domain Pack Conformance

A Domain Pack is compliant if and only if:

1. It is valid JSON and follows the structure in Section 4.1
2. All canonical JSON hashing uses RFC 8785
3. Hash is computed by excluding the "hash" field from canonicalization
4. All literal types map to Noe domains per Section 3.5
5. All spatial thresholds (collision_distance_m, proximal_threshold_m, distal_threshold_m, zone_radius_m) are declared
6. All operators used in expressions are declared in operator_requirements
7. All operator_requirements paths reference valid context levels (C_root, C_domain, C_local, C_safe, C_rich)
8. All literals appear in either critical_literals or non_critical_literals
9. The pack is fully canonicalizable without errors
10. The hash value is stable (repeated canonicalization produces the same hash)

### 7.2 Runtime Conformance

A Runtime is compliant if:

1. It loads Domain Packs deterministically (same pack always produces the same load result)
2. It populates C_root and C_domain according to the Domain Pack specification
3. It uses the Domain Pack's `required_context` paths for literal completeness checks (via `is_explained_literal()` in π_safe)
4. It validates Domain Pack hash before use (rejects hash mismatches)
5. It logs domain_pack_hash and domain_pack_id in all provenance records
6. It only evaluates safety-critical semantics over C_safe (never C_rich)
7. It enforces the epistemic model: literals not in `C_safe.modal.knowledge` produce appropriate K3 results
8. It DOES NOT seed or infer missing required_context fields from defaults

> **Note**: Runtimes are NOT required to enforce `operator_requirements` or `safety.critical_literals` at evaluation time. These fields are advisory metadata for external tooling. Safety is enforced through the epistemic model and π_safe — not through Domain Pack metadata fields.

### 7.3 Domain Pack Authors

- [ ] Use RFC 8785 for all canonicalization and hashing
- [ ] Declare all literals with required_context paths
- [ ] Specify operator_requirements for all operators used
- [ ] Set collision_distance_m, proximal_threshold_m, distal_threshold_m, zone_radius_m
- [ ] Classify all literals as critical or non-critical
- [ ] Group sensors by independence (for π_safe correctness)
- [ ] Ensure proximal_threshold_m < distal_threshold_m
- [ ] Document all adapters (if used) and their determinism guarantees
- [ ] Test hash stability (repeated canonicalization must produce identical hashes)

### 7.4 Validator Implementers

- [ ] Verify Domain Pack hash before use
- [ ] Reject hash mismatches
- [ ] Enforce operator_requirements completeness (fail on missing required_context)
- [ ] Never seed missing required_context from defaults
- [ ] Log domain_pack_hash in all provenance records
- [ ] Suppress actions if any critical literal is undefined
- [ ] Use spatial thresholds for deixis resolution
- [ ] Verify staleness (max_latency_ms, stale_threshold_ms)
- [ ] Enforce C_safe-only evaluation for safety-critical literals

## 8. Backwards Compatibility

This is the first release of the Domain Pack specification. Future versions MUST:

1. Maintain the hash circularity rule (hash field excluded)
2. Preserve all existing top-level fields
3. Add new fields only at the end of the JSON structure
4. Provide migration guidance if operator_requirements semantics change
5. Use semantic versioning to signal breaking changes

Validators encountering unknown fields or versions MUST log a warning but may proceed if the required fields are present.

## 9. Security and Safety Considerations

### 9.1 Trusted Computing Base

Domain Packs are part of the runtime's trusted computing base (TCB). A malicious or corrupted Domain Pack can:

- Weaken safety by setting low collision_distance_m thresholds
- Hide safety-critical literals by classifying them as non-critical
- Demand incomplete context and suppress safety checks via R_O
- Forge sensor independence groups, breaking π_safe correctness

**Mitigation**: Hash verification is mandatory. Validators MUST reject any Domain Pack with hash mismatch. Deployments SHOULD use cryptographic signatures (out of scope) for Domain Pack authentication.

### 9.2 π_safe Correctness

Domain Packs declare sensor independence groups. The validator assumes sensors in different groups can be safely fused. If this assumption is violated (e.g., shared error sources), π_safe fails.

**Mitigation**: Domain Pack authors MUST carefully model sensor dependencies. Validators MAY add redundancy checks or request updated packs.

### 9.3 Critical Literals and Non-Execution

The `safety.critical_literals` classification is advisory metadata for application-level enforcement. The application's grounding code SHOULD treat undefined critical literals as grounds for non-execution. The Noe runtime itself enforces safety through the epistemic model: if a critical literal is not in `C_safe.modal.knowledge`, any `shi` check on it will not return true, preventing knowledge-gated actions from executing.

Application grounding code MUST NOT:

- Assume default values for missing critical literals
- Proceed with safety-critical execution if any critical literal is undefined in `C_safe`

Violating this guidance breaks the deployment's safety contract.

### 9.4 Deixis and Referential Clarity

Deixis operators (dia, doq) depend on spatial thresholds to resolve references unambiguously. Poorly chosen thresholds can create ambiguous or contradictory references (e.g., an object is neither near nor far).

**Mitigation**: Domain Pack authors SHOULD ensure proximal_threshold_m < distal_threshold_m and that these values reflect deployment geometry. Validators SHOULD check threshold validity.

### 9.5 Determinism and Reproducibility

Domain Packs enable reproducibility: the same pack, context, and expression produce identical results. This is crucial for debugging and safety analysis.

**Mitigation**: Adapters (Section 4.1.2) MUST be deterministic. Time-dependent adapters MUST be logged. Validators MUST produce identical output for identical inputs.
