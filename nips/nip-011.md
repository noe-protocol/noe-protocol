# NIP-011: Reference Interpreter and Conformance Suite

## Abstract

NIP-011 defines the official conformance suite for Noe v1.0 and establishes normative requirements for reference interpreter behavior. This NIP specifies a comprehensive set of JSON test vectors that MUST be passed by any implementation claiming compatibility with Noe v1.0. The conformance pack covers strict action validation, epistemic correctness, operator precedence, K3 logic, spatial operators, and multi-agent determinism across 60 canonical test vectors.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) and [RFC 8174](https://www.rfc-editor.org/rfc/rfc8174) when, and only when, they appear in all capitals, as shown here.

## 1. Purpose

This NIP defines:

1. The authoritative set of test vectors that MUST pass for v1.0 conformance
2. The expected behavior of a reference interpreter implementing NIP-004 and NIP-005
3. The JSON schema and runtime format for expressing conformance tests
4. The evaluation semantics for all operators, epistemic constructs, and spatial functions
5. Safety and security requirements that MUST be enforced in strict mode

The conformance suite serves as both a normative specification and a practical validation tool for implementations.

## 2. Scope

This NIP applies to:

- All Noe v1.0 implementations claiming standards compliance
- Reference interpreter implementations of NIP-004 (parsing) and NIP-005 (evaluation)
- Test vector authoring and maintenance
- Conformance certification and compatibility verification

This NIP does NOT specify:

- Liveness behavior (retries, backoff, timeouts) — see NIP-016
- Serialization formats beyond JSON test vectors
- Performance characteristics or optimization strategies
- UI/UX for tools consuming conformance tests

## 3. Definitions

**Canonical Test Vector**: A JSON object in `conformance_pack_v1.0.0.json` representing a single test case. All 60 canonical vectors MUST pass for v1.0 compatibility.

**Conformance Pack**: The complete set of test vectors, including canonical (60 required) and experimental (31 optional) cases.

**Domain Output Shape**: The type of value produced by an expression: `truth`, `numeric`, `action`, `question`, `error`, `undefined`, `list`, or `literal`.

**Expectation Type**: The predicate against which actual output is validated: `EXPECT_ALLOW`, `EXPECT_BLOCK`, `EXPECT_ERROR_CODE`.

**Strict Mode**: Evaluation mode that disallows ambiguous or incomplete constructs and enforces all safety kernel invariants.

**Partial Mode**: Evaluation mode that permits incompleteness and defers some validation.

**K3 Logic**: Three-valued logic incorporating undefined as a first-class truth value, with propagation rules for conjunction and disjunction.

**Determinism**: Property that identical input chains in identical contexts MUST produce identical output across all agents in a cohort.

## 4. Specification

### 4.1 Test Vector Format

Each canonical test vector is a JSON object with the following structure:

```json
{
  "id": "strict_action_001",
  "description": "Valid action with defined target",
  "mode": "strict",
  "chain": ["@actor act-on @target"],
  "context": {
    "actor": "alice",
    "target": "door"
  },
  "expected": {
    "type": "EXPECT_ALLOW",
    "domain": "action"
  }
}
```

**Fields**:

- `id` (string, required): Unique identifier within the conformance pack
- `description` (string, required): Human-readable summary of the test case
- `mode` (string, required): Either `"strict"` or `"partial"`
- `chain` (array of strings, required): Ordered sequence of expressions to evaluate
- `context` (object or null, optional): Variable bindings for strict/single-agent tests
- `agents` (array of objects, optional): Multi-agent context for determinism tests; each agent has `name` and `context`
- `expected` (object, required): Expected outcome specification

**Context Validation**: The context field MUST be either:

- A JSON object with string keys and any values
- `null`

If context is an array or a non-null primitive, the test MUST produce `ERR_BAD_CONTEXT`.

### 4.2 Expectation Types

**EXPECT_ALLOW**:
- Assertion that the expression MUST evaluate successfully
- The expression MUST NOT raise an error
- The resulting domain shape MUST match the `domain` field if present

**EXPECT_BLOCK**:
- Assertion that the expression MUST be rejected
- An error MUST be raised with code matching `error_code` if specified
- No output value is produced

**EXPECT_ERROR_CODE**:
- Assertion that evaluation MUST produce an error with a specific code
- Valid error codes include: `ERR_UNDEFINED_TARGET`, `ERR_BAD_CONTEXT`, `ERR_TYPE_MISMATCH`, `ERR_INJECTION`, `ERR_PARSE_FAILURE`

### 4.3 Domain Output Shapes

The conformance suite defines eight domain output shapes:

| Domain | Description | Example |
|--------|-------------|---------|
| `truth` | Boolean value from K3 logic (true, false, undefined) | `shi @fact nek` → true |
| `numeric` | Integer or floating-point value | NIP-007 numeric atoms |
| `action` | Action object specifying verb and target | `mek @target nek` |
| `question` | Query result with optional provenance | `qua soi shi @fact nek` |
| `error` | Error object with code and metadata | `ERR_UNDEFINED_TARGET` |
| `undefined` | Explicit undefined value from K3 logic | Missing literal in strict mode |
| `list` | Ordered sequence of values | Multiple results in scope |
| `literal` | Raw string or number literal | `@banana` |

### 4.4 Operator Evaluation Semantics

#### 4.4.1 Epistemic Operators

Epistemic operators are unary and follow modal membership rules (NIP-005 §4.8), not generic truth-functional propagation.

**shi (knowledge)**:
```noe
shi @literal nek
```
Returns `true` if `@literal` is in `C_safe.modal.knowledge`, `false` otherwise, `undefined` if the modal subsystem is missing. Must satisfy the knowledge threshold (NIP-017). In strict mode, if `@literal` is not grounded in C_safe, raises `ERR_EPISTEMIC_MISMATCH`.

**vek (belief)**:
```noe
vek @literal nek
```
Returns `true` if `@literal` is in `C_safe.modal.belief`, `false` otherwise (NIP-005 §4.8.2), `undefined` if modal is missing. Must satisfy the belief threshold (NIP-017).

**sha (certainty)**:
```noe
sha @literal nek
```
Returns `true` if `@literal` is in `C_safe.modal.certainty`, `false` otherwise (NIP-005 §4.8.3), `undefined` if modal is missing. Must satisfy the calibrated certainty threshold (NIP-017). `sha` is the highest-confidence epistemic operator, not a group-assertion operator.

#### 4.4.2 K3 Logic Operators

**an (conjunction — Strong Kleene)**:
```noe
@a an @b nek
```
Returns true only if both operands are true. Returns false if either operand is false. Returns undefined if neither is false but at least one is undefined.

**ur (disjunction — Strong Kleene)**:
```noe
@a ur @b nek
```
Returns true if either operand is true. Returns false only if both operands are false. Returns undefined if neither is true but at least one is undefined. `ur` is the OR operator, not an undefined-producer.

#### 4.4.3 Spatial Operators

Spatial operators are binary conjunction-precedence operators (NIP-005 §4.16). They require grounded spatial data in `C_safe.spatial`.

**nel (near)**: `@a nel @b` — true if distance between entities ≤ threshold. Missing spatial data returns `undefined`.

**tel (far)**: `@a tel @b` — true if distance between entities ≥ threshold. Missing spatial data returns `undefined`.

**xel (aligned)**: `@a xel @b` — true if angular alignment is within tolerance. Missing orientation returns `undefined`.

**en (containment)**: `@a en @b` — true if entity A is within radius of B. Missing spatial data returns `undefined`.

**tra (towards)**: `@a tra @b` — true if A's velocity vector points towards B (dot product ≥ cos_theta). Missing velocity returns `undefined`.

**fra (behind)**: `@a fra @b` — true if A's velocity vector points away from B (dot product ≤ -cos_theta). Missing velocity returns `undefined`.

#### 4.4.4 Demonstrative Operators

**dia (proximal demonstrative)**: Resolves to the nearest/most salient referent in `C_safe.demonstratives.dia`. Must resolve to exactly one entity; ambiguous or missing referents return `undefined`.

**doq (distal demonstrative)**: Resolves to a distal referent in `C_safe.demonstratives.doq`. Same resolution rules as `dia`.

### 4.5 Multi-Agent Determinism

For multi-agent tests, all agents MUST:

1. Parse the same chain identically across the cohort
2. Evaluate each expression with their local context
3. Produce identical output shapes (though domain-specific values may differ)
4. NOT drift due to message ordering or temporal misalignment

Cross-agent determinism tests verify:

- **Universal truth**: Shared true assertions remain true across agents
- **Private literals**: Agents with local-only context do not produce universal outputs
- **Drift/staleness**: Temporal delays do NOT cause evaluation to diverge
- **Partial overlap**: Agents with overlapping but non-identical knowledge produce consistent error codes
- **Conflicting beliefs**: Contradictory assertions produce `undefined` uniformly
- **Temporal boundary**: Knowledge cutoff times are respected uniformly

### 4.6 Strict Mode Safety Kernel

In strict mode, the interpreter MUST enforce:

1. **No ambiguous constructs**: All variable references MUST resolve to exactly one binding
2. **No incomplete constructs**: All required arguments to operators MUST be provided
3. **No implicit type coercion**: Types MUST match operator expectations exactly
4. **No injection vulnerability**: Special characters in literals MUST NOT be interpreted as code
5. **No tokenization drift**: Symbols like `@banana` MUST tokenize as a single unit, NOT as `@` + `banana`

Violations MUST raise appropriate errors and block evaluation.

### 4.7 Interpreter Integration Requirements

A conforming interpreter MUST:

1. **Parse** expressions according to NIP-004
2. **Evaluate** chains according to NIP-005
3. **Validate** output according to NIP-015 and NIP-017
4. **Merge** results according to NIP-009
5. **NOT** implement liveness behavior (NIP-016 is separate)
6. **NOT** reorder or cache chain evaluation results

### 4.8 Conformance Pack Structure

The authoritative conformance pack is `conformance_pack_v1.0.0.json`, which is a **manifest** listing per-file SHA-256 checksums and vector counts. The individual test vectors are stored in separate JSON files:

```json
{
  "version": "1.0.0",
  "total_vectors": 60,
  "excluded_experimental": 31,
  "manifest_hash": "<sha256>",
  "files": {
    "nip011_adversarial.json":     { "sha256": "...", "vectors": 10 },
    "nip011_audit.json":           { "sha256": "...", "vectors": 2  },
    "nip011_context.json":         { "sha256": "...", "vectors": 3  },
    "nip011_cross_agent.json":     { "sha256": "...", "vectors": 5  },
    "nip011_delivery.json":        { "sha256": "...", "vectors": 1  },
    "nip011_demonstratives.json":  { "sha256": "...", "vectors": 5  },
    "nip011_epistemic.json":       { "sha256": "...", "vectors": 11 },
    "nip011_literals.json":        { "sha256": "...", "vectors": 3  },
    "nip011_miscommunication.json":{ "sha256": "...", "vectors": 6  },
    "nip011_quantization.json":    { "sha256": "...", "vectors": 14 },
    "nip011_spatial.json":         { "sha256": "...", "vectors": 2  },
    "nip011_staleness.json":       { "sha256": "...", "vectors": 4  },
    "nip011_strict_actions.json":  { "sha256": "...", "vectors": 2  },
    "nip011_ungrounded.json":      { "sha256": "...", "vectors": 4  }
  }
}
```

The 31 experimental vectors are excluded from the pack and are not required for v1.0 conformance. They are tracked separately and MAY be promoted to canonical in future versions.

> **Note:** Additional vectors exist in `nip011_runtime.json` (15 vectors), `nip011_strict.json` (1 vector), and `nip011_requests.json` (1 vector). These are supplementary runtime validation vectors that extend the canonical suite. The manifest registers only the 14 files above (60 vectors total).

### 4.8.1 Quantization Test Vectors

The `nip011_quantization.json` file uses a distinct schema for testing the π_safe float-to-integer quantization pipeline (NIP-009 §4.6):

```json
{
  "name": "q_ties_to_even_down",
  "desc": "Verify round-half-to-even behavior (0.5 -> 0)",
  "input_str": "0.5",
  "scale": 1,
  "expected_safe": 0
}
```

**Fields:**
- `name` (string): Unique test identifier
- `desc` (string): Human-readable description
- `input_str` (string): Numeric input as a string
- `scale` (integer): Quantization scale factor
- `expected_safe` (integer): Expected integer output after round-half-to-even

These vectors verify that all implementations produce identical deterministic rounding behavior, which is essential for hash symmetry (NIP-009 §4.8.4).

Implementations MAY produce demo artifacts showing test execution:

```json
    "conformance_pack_version": "1.0.0"
  },
  "test_results": [
    {
      "test_id": "strict_action_001",
      "status": "PASSED",
      "output_shape": "action",
      "hashes": {
        "input_hash": "sha256:abc123...",
        "output_hash": "sha256:def456..."
      },
      "provenance": {
        "evaluated_by": "alice",
        "timestamp": "2025-12-10T14:30:01Z"
      }
    },
    {
      "test_id": "strict_action_002",
      "status": "BLOCKED",
      "error_code": "ERR_UNDEFINED_TARGET",

        "input_hash": "sha256:ghi789...",

      "provenance": null

```

**Invariant**: For blocked outcomes, all hashes in the output MUST be `null`. Only successful evaluations produce non-null hashes.

## 5. Rationale

### 5.1 Why 60 Canonical Test Vectors?

The 60 canonical tests are distributed across 14 files in the conformance pack:

- **11** epistemic cases (shi/vek/sha membership semantics, threshold enforcement)
- **10** adversarial cases (deep nesting, unicode, type mismatches, injection, empty chains)
- **14** quantization cases (round-half-to-even, scale factors, negative values, edge cases)
- **6** miscommunication prevention cases (operator precedence, commutativity, associativity)
- **5** cross-agent determinism cases (universal truth, private literals, drift, overlap, conflict)
- **5** demonstrative cases (dia/doq resolution)
- **4** staleness cases (temporal boundary enforcement)
- **4** ungrounded cases (references without context)
- **3** context validation cases (null, array, string contexts)
- **3** literal cases (raw string/number handling)
- **2** strict action cases (undefined target detection)
- **2** spatial operator cases (nel/tel with missing data)
- **2** audit cases (logging and provenance)
- **1** delivery case (chain ordering)

This stratified approach ensures coverage of both happy path and error cases across all major features, with particular depth in epistemic enforcement and quantization determinism.

### 5.2 Why Strict Mode?

Strict mode is necessary to:

- Eliminate ambient ambiguity in knowledge representation
- Prevent silent failures and implicit type coercion
- Enforce injection protection at parse time
- Enable deterministic behavior across heterogeneous implementations
- Reduce attack surface in security-critical deployments

Partial mode is provided for legacy compatibility and experimentation, but v1.0 conformance requires strict mode compliance.

### 5.3 Why K3 Logic?

K3 (Kleene's three-valued logic) is necessary to:

- Represent incomplete knowledge faithfully
- Avoid false negatives from missing assertions
- Distinguish "unknown" from "false" in epistemic contexts
- Support graceful degradation when data is missing
- Enable consistent semantics across distributed agents with partial information

### 5.4 Why Demonstrate Output Hashing?

Output hashing provides:

- Cryptographic proof of expression evaluation
- Non-repudiation of demonstrated outcomes
- Tamper detection for recorded evaluations
- Audit trails for compliance verification

The null-hash invariant for blocked outcomes prevents false claims of successful evaluation.

## 7. Conformance Requirements

### 7.1 Mandatory Conformance

An implementation claiming Noe v1.0 compatibility MUST:

1. Pass ALL 60 canonical test vectors
2. Operate in strict mode by default
3. Enforce all safety kernel invariants (Section 4.6)
4. Produce correct domain output shapes (Section 4.3)
5. Implement all operators specified in Section 4.4
6. Validate context according to Section 4.1
7. Produce error codes matching the test vectors
8. Support multi-agent evaluation for determinism tests

### 7.2 Optional Conformance

Implementations MAY:

1. Support the 31 experimental test vectors
2. Provide partial mode for legacy compatibility
3. Produce demo artifacts with hashing (Section 4.9)
4. Implement extended operators beyond NIP-011
5. Optimize evaluation while maintaining semantic equivalence

### 7.3 Conformance Certification

Implementations that pass all 60 canonical tests are eligible for certification. Certification artifacts SHOULD include:

- Signed attestation of test passage
- Version information (interpreter, protocol, conformance pack)
- Execution environment metadata
- Demo artifacts with input/output hashes

## 8. Backwards Compatibility

### 8.1 Breaking Changes from Pre-v1.0

NIP-011 does not guarantee backwards compatibility with pre-v1.0 implementations or draft NIPs. The conformance suite is defined for v1.0 and later.

### 8.2 Forward Compatibility

Future versions of the conformance suite (v1.1.0, v2.0.0, etc.) MUST:

1. Preserve all canonical tests from prior versions
2. Add new test groups in the experimental section first
3. Move experimental tests to canonical only when stable
4. Maintain separate version markers for each generation

Implementations SHOULD support querying the conformance pack version and MAY reject evaluation requests for packs from incompatible futures.

## 9. Security and Safety Considerations

### 9.1 Injection Attacks

The tokenization safety requirement (Section 4.6, item 5) prevents adversaries from escaping quoted literals or symbols. The test case `adversarial_001` (Section 6.8) verifies this.

### 9.2 Type Confusion

Strict mode disallows implicit type coercion, preventing adversaries from crafting inputs that behave differently than intended. All type mismatches are caught at evaluation time.

### 9.3 Incomplete Constructs

Requiring all operator arguments to be provided prevents silent defaults and invisible fallbacks that could be exploited.

### 9.4 Ambient Ambiguity

Requiring all variable references to resolve to exactly one binding prevents shadowing attacks and context collision.

### 9.5 Non-Repudiation

Output hashing with the null-hash invariant prevents false claims of successful evaluation without cryptographic evidence.

### 9.6 Distributed Attack Surface

Multi-agent determinism requirements prevent adversaries from exploiting temporal misalignment or message ordering to cause cohorts to diverge in their evaluation results.
