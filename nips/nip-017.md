# NIP-017: Epistemic Mapping Specification

## Abstract

This document specifies the deterministic mapping from probabilistic evidence to epistemic modal sets within the Noe Protocol. It defines the confidence-to-epistemic transformation, validator rules for evidence integrity, adversarial defenses, and performance constraints necessary for real-time control loop integration.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

This document uses the following notation:

- `c(P)`: confidence value for proposition P, a real number in [0, 1]
- `c(¬P)`: confidence in the negation of P, derived from positive evidence of absence
- `vek P`: the belief modal operator, evaluates the belief set
- `shi P`: the knowledge modal operator, evaluates the knowledge set
- `sha P`: the certainty modal operator, evaluates the certainty set
- `C_safe.modal`: the epistemic modal context containing three sets: belief, knowledge, certainty
- `Map<Proposition, Boolean>`: an associative container mapping propositions to boolean values
- `t_vek_min`, `t_shi_min`: global confidence thresholds for belief and knowledge respectively
- `certainty_threshold`: runtime-configurable threshold for the `sha` operator, read from `C_safe.modal.certainty_threshold`
- `staleness_limit_ms`: maximum age in milliseconds for evidence to remain valid
- `drift_budget_ms`: additional margin for clock synchronization tolerance

## 1. Purpose

NIP-017 establishes the authoritative specification for converting probabilistic confidence measurements into discrete epistemic modal classifications. This mapping is critical for ensuring:

- Deterministic and repeatable epistemic judgments across distributed validators
- Calibrated confidence thresholds that balance false positives and false negatives
- Defense against adversarial manipulation of evidence and confidence values
- Real-time performance within control loop budgets (< 10% utilization)
- Logical consistency and soundness in epistemic commitments

## 2. Scope

This specification applies to all components within the Noe Protocol that:

- Accept probabilistic evidence with confidence measurements
- Classify propositions into epistemic modal sets (belief, knowledge, certainty)
- Evaluate epistemic modal operators (vek, shi, sha)
- Validate evidence integrity before insertion into modal sets
- Interface with cross-cutting validation and consistency checking (NIP-002, NIP-005)

The specification covers both default global thresholds and per-proposition overrides via domain packs (NIP-013).

## 3. Definitions

**Confidence**: A real-valued measurement in [0, 1] representing the probability or degree of belief in a proposition, supplied by evidence sources.

**Evidence**: A structured datum containing a confidence value, timestamp, source identifier, and boolean value, used to support epistemic classifications.

**Modal Set**: A container holding propositions that satisfy the requirements for a particular epistemic modality. The belief and knowledge sets are boolean maps (`Map<Proposition, Boolean>`). The certainty shard (`C_safe.modal.certainty`) is a numeric map (`Map<Proposition, Float>`) compared against a runtime threshold.

**Threshold**: A calibrated confidence value serving as the boundary for classification into a modal set.

**Hysteresis**: An optional mechanism that prevents rapid oscillation of propositions between modal sets by applying an asymmetric threshold on withdrawal versus insertion.

**Staleness**: The elapsed time since an evidence item was created, measured against the current system clock.

**Drift Budget**: An allowance added to the staleness limit to accommodate clock synchronization errors in distributed systems.

**Validator Rule**: A deterministic check applied to evidence before insertion, enforcing consistency, freshness, and logical integrity.

## 4. Specification

### 4.1 Confidence-to-Epistemic Mapping

#### 4.1.1 Belief and Knowledge Classification

The transformation from confidence to the `vek` (belief) and `shi` (knowledge) modal sets uses global thresholds from `EPISTEMIC_THRESHOLDS`:

```
if confidence >= t_shi_min then
    insert into knowledge set (and belief set, since knowledge implies belief)
else if confidence >= t_vek_min then
    insert into belief set only
else
    classification = undefined (insufficient evidence)
```

Where:

- `t_vek_min` (default): 0.40 — minimum confidence for belief set inclusion
- `t_shi_min` (default): 0.90 — minimum confidence for knowledge set inclusion

These thresholds match `EPISTEMIC_THRESHOLDS` in noe-gate's `context_projection.py`. Default thresholds may be overridden on a per-proposition basis via domain pack configuration (NIP-013). All threshold overrides must be registered in the authority registry before use (NIP-009).

#### 4.1.2 Certainty Classification

The `sha` (certainty) operator uses a fundamentally different mechanism. It does NOT use a global threshold from `EPISTEMIC_THRESHOLDS`. Instead:

1. The application populates `C_safe.modal.certainty[P]` with a numeric certainty level ∈ [0, 1].
2. The evaluator reads `C_safe.modal.certainty_threshold` (runtime-configurable per deployment).
3. `sha P` returns the truth value from the knowledge or belief map if `certainty[P] >= certainty_threshold`; otherwise `undefined`.

In strict mode, a missing `certainty_threshold` produces `ERR_EPISTEMIC_MISMATCH`. In non-strict mode, a legacy fallback of 0.8 applies. See §4.5 for full operator semantics.

### 4.2 Evidence Schema

Evidence structures supply the confidence measurements. The canonical evidence format is:

```json
{
  "confidence": <float [0.0, 1.0]>,
  "timestamp_ms": <integer (milliseconds since epoch)>,
  "source": <string identifier>,
  "value": <boolean>
}
```

All fields are required. Absence of any field results in error code `ERR_MISSING_EVIDENCE` and rejection of the evidence item. Validators MUST NOT infer, estimate, or backfill missing fields.

### 4.3 Validator Rules

Before insertion into a modal set, evidence must pass all four validator rules in the following order:

#### Rule 1: Confidence Inflation Defense

Recompute the confidence value from the raw evidence using the original inference or measurement methodology. If the recomputed confidence is below the applicable threshold for the classified modal set, reject with error code `ERR_EPISTEMIC_MISMATCH`.

**Rationale**: Protects against adversarial padding or rounding of confidence values to artificially elevate classification.

#### Rule 2: Freshness

Compute the staleness as:

```
staleness = current_timestamp_ms - evidence.timestamp_ms
effective_limit = staleness_limit_ms + drift_budget_ms
```

The default `staleness_limit_ms` is 1000 milliseconds. The default `drift_budget_ms` is 5 milliseconds, accommodating clock skew in distributed environments. If `staleness > effective_limit`, reject with error code `ERR_STALE_EVIDENCE`.

Deployments operating in safety-critical real-time control loops (e.g., robotics, autonomous systems) SHOULD configure a tighter `staleness_limit_ms` appropriate to their control frequency. A 10 Hz control loop, for example, would typically use a staleness limit of 100–200 ms.

**Rationale**: Ensures epistemic commitments reflect the freshest available information and prevents replayed or delayed evidence from distorting modal sets.

#### Rule 3: Evidence Existence

If the evidence object is null or missing, reject with error code `ERR_MISSING_EVIDENCE`.

**Rationale**: Guards against null pointer dereferences and ensures all epistemic claims are backed by actual evidence.

#### Rule 4: Logical Consistency

Check the epistemic modal context `C_safe.modal` for logical conflicts:

- If proposition P is in a modal set AND its negation ¬P is in the same set, reject with error code `ERR_CONTEXT_INCONSISTENT`.

This check operates at the level of propositional equivalence; equivalent propositions are considered identical for consistency purposes.

**Rationale**: Prevents logical contradiction within a single modal set, which would violate classical logic and undermine epistemic integrity.

### 4.4 Negation Semantics

The confidence in a negation, `c(¬P)`, is NOT derived as `1 - c(P)`. Instead, it must be computed from positive evidence of absence:

```
c(¬P) = confidence_from_absence_evidence
```

This requires that negations be supported by explicit, independent evidence rather than by deferring to the absence of positive evidence. This prevents spurious high-confidence negations and enforces evidentiary burden symmetry.

**Rationale**: Aligns with classical epistemic principles and prevents asymmetric treatment of positive and negative propositions.

### 4.5 Epistemic Operator Semantics

The three epistemic modal operators are defined as follows, where `P` is a proposition and `C_safe.modal` contains the three modal sets:

```
vek P =
  if P in C_safe.modal.knowledge then knowledge[P]
  else if P in C_safe.modal.belief then belief[P]
  else undefined
  -- Knowledge implies belief; check knowledge first.

shi P =
  if P in C_safe.modal.knowledge then knowledge[P]
  else undefined

sha P =
  let cert_level = C_safe.modal.certainty[P]    (numeric, [0, 1])
  let threshold  = C_safe.modal.certainty_threshold
  if threshold is undefined then
    error ERR_EPISTEMIC_MISMATCH   (strict mode)
    -- or use legacy fallback 0.8  (non-strict mode)
  if cert_level >= threshold then
    return truth value of P from knowledge or belief map
  else
    undefined
```

The `vek` and `shi` operators return the boolean value associated with the proposition if it is present in their respective modal maps, or `undefined` if absent. The `sha` operator uses a different mechanism: it reads a numeric certainty level from `C_safe.modal.certainty[P]` and compares it against `C_safe.modal.certainty_threshold`. If the certainty level meets the threshold, `sha` returns the truth value from the knowledge or belief map; otherwise it returns `undefined`. In strict mode, a missing `certainty_threshold` is an error (`ERR_EPISTEMIC_MISMATCH`); in non-strict mode, a legacy fallback of 0.8 is used. All evaluation is deterministic and has no side effects.

### 4.6 Insertion Protocol

The complete insertion protocol is as follows:

1. **Recompute Confidence**: Use the original measurement or inference methodology to recompute the confidence value from raw data.
2. **Apply Hysteresis (Optional)**: If hysteresis is configured for this proposition, apply asymmetric thresholds for insertion versus withdrawal.
3. **Validate Rules 1–4**: Execute all four validator rules in order. If any rule fails, stop and return the corresponding error code.
4. **Insert or Reject**: If all rules pass, insert the proposition and its value into the appropriate modal set. If any rule failed, reject the evidence and do not modify any modal set.

**No Partial Updates**: The insertion protocol is atomic. Partial insertions or multi-step updates are not permitted; either the evidence is inserted completely or not at all.

### 4.7 Threshold Floor Enforcement

A safety floor is enforced on all threshold values to prevent pathologically low thresholds:

- `t_vek_min >= 0.30`
- `t_shi_min >= 0.60`
- `certainty_threshold >= 0.50`

If a domain pack or configuration specifies thresholds violating these floors, the system MUST reject the configuration and raise error code `ERR_UNSAFE_THRESHOLDS`.

**Rationale**: Ensures that even with per-proposition overrides, epistemic classifications remain meaningful and conservative, avoiding degenerate cases where any evidence results in maximum confidence.

### 4.8 Performance Constraints

Epistemic mapping operations SHOULD consume less than 10% of the control loop budget. Implementations SHOULD benchmark their mapping latency against their target control frequency and document the results.

> **Informative — Reference Measurements**: Early benchmarks on commodity hardware showed cached modal lookups at ~0.018 ms and full confidence recomputation at ~0.186 ms, suggesting compatibility with 10–100 Hz control loops. These figures are hardware-dependent and NOT normative; implementations MUST measure on their target platform.

### 4.9 Clock Drift Tolerance

The effective staleness limit accommodates distributed clock skew via the drift budget:

```
effective_limit_ms = staleness_limit_ms + drift_budget_ms
```

Default values are 1000 ms and 5 ms respectively. System operators may increase the drift budget on a per-environment basis to match observed clock synchronization characteristics, up to a recommended maximum of 50 ms. Operators deploying in latency-sensitive environments SHOULD reduce `staleness_limit_ms` to match their control loop period.

## 5. Rationale

### 5.1 Why Three Modal Sets?

The three-tier structure (belief, knowledge, certainty) aligns with classical epistemic logic and reflects different grades of warrant:

- **Belief** (vek): Plausible but uncertain; useful for preliminary reasoning
- **Knowledge** (shi): Justified true belief; strong warrant, suitable for most reasoning
- **Certainty** (sha): A numeric certainty level compared against a runtime threshold; appropriate for high-assurance claims where the application must explicitly configure the required certainty bar

### 5.2 Why Calibrated Thresholds?

The global thresholds (t_vek_min=0.40, t_shi_min=0.90) are calibrated through empirical validation against control loop performance and false-positive/false-negative trade-offs. The knowledge threshold (0.90) is set conservatively high to ensure that propositions classified as "known" carry strong evidentiary warrant, reducing the risk of acting on insufficiently grounded claims. The certainty threshold is deliberately NOT a global constant — it is runtime-configurable via `C_safe.modal.certainty_threshold`, allowing deployments to tune certainty requirements to their operational context.

### 5.3 Why No Confidence Inversion for Negations?

Negations require positive evidence rather than derivation from `1 - c(P)` to avoid asymmetric treatment. If only positive evidence for P exists, deriving high confidence in ¬P would be epistemically unsound.

### 5.4 Why Atomic Insertions?

Atomicity prevents intermediate inconsistency states. Partial insertions could leave the modal context in a logically incoherent state if validation fails midway.

### 5.5 Why Validator Rules?

The four validator rules collectively defend against:

- **Confidence Inflation** (Rule 1): Adversarial falsification of measurements
- **Temporal Attacks** (Rule 2): Replay and delay attacks using stale evidence
- **Null Pointer Attacks** (Rule 3): Resource exhaustion and crashes
- **Logical Contradiction** (Rule 4): Epistemic incoherence

## 6. Examples

### Example 1: Simple Insertion

A sensor reports confidence 0.93 that proposition `weather:raining` is true, with current timestamp.

1. Recompute confidence: 0.93 (confirmed by sensor data)
2. Apply hysteresis: None configured
3. Validate:
   - Rule 1: 0.93 >= t_shi_min (0.90) ✓
   - Rule 2: Staleness = 2 ms < 1005 ms ✓
   - Rule 3: Evidence is present ✓
   - Rule 4: Neither `weather:raining` nor `¬weather:raining` in same set ✓
4. Insert `weather:raining` → true into the **knowledge (shi)** set

### Example 2: Negation

A sensor provides explicit evidence of absence: confidence 0.92 that `animal:present` is false (from motion detector inactivity plus thermal imaging), with fresh timestamp.

1. Recompute confidence: 0.92 (derived from sensor fusion)
2. Apply hysteresis: None configured
3. Validate: All rules pass
4. Insert `¬animal:present` → true into **knowledge (shi)** set

Note: This is NOT derived as `1 - 0.92` from weak evidence that the animal is present. It rests on independent evidence of absence.

### Example 3: Stale Evidence Rejection

Evidence arrives with timestamp 1200 ms old, confidence 0.95.

1. Recompute confidence: 0.95
2. Validate:
   - Rule 2: Staleness = 1200 ms > effective_limit (1005 ms) ✗
3. Reject with `ERR_STALE_EVIDENCE`

The evidence is not inserted, and the modal context is unchanged.

### Example 4: Confidence Inflation Detection

Evidence claims confidence 0.93, but recomputation yields 0.82 (below t_shi_min of 0.90).

1. Recompute confidence: 0.82 (differs from claimed 0.93)
2. Validate:
   - Rule 1: 0.82 < t_shi_min (0.90) ✗
3. Reject with `ERR_EPISTEMIC_MISMATCH`

The inflated value is detected and the evidence is rejected.

### Example 5: Logical Inconsistency

The modal context already contains `risk:high` → true in the certainty set. New evidence attempts to insert `¬risk:high` → true into the same set.

1. Validate:
   - Rule 4: `risk:high` and `¬risk:high` both present in certainty ✗
2. Reject with `ERR_CONTEXT_INCONSISTENT`

## 7. Conformance Requirements

Implementations claiming compliance with NIP-017 MUST:

1. Implement the confidence-to-epistemic mapping as specified in Section 4.1
2. Enforce all four validator rules (Section 4.3) in the prescribed order
3. Support the evidence schema including all required fields (Section 4.2)
4. Implement negation semantics requiring positive evidence of absence (Section 4.4)
5. Evaluate epistemic operators deterministically (Section 4.5)
6. Perform insertions atomically (Section 4.6)
7. Enforce threshold floors (Section 4.7)
8. Benchmark and document epistemic mapping latency against target control loop budget (Section 4.8)
9. Provide configurable clock drift tolerance (Section 4.9)
10. Support per-proposition threshold overrides via domain packs (Section 4.1, NIP-013)

Implementations MAY:

- Implement hysteresis for proposition withdrawal (Section 4.6)
- Optimize cached lookups (Section 4.8)
- Configure clock drift budget beyond the default (Section 4.9)

## 8. Backwards Compatibility

Systems transitioning from earlier epistemic classification schemes should implement a compatibility mode:

1. **Logging Phase**: Log all decisions under both old and new mapping rules; compare outcomes but do not enforce strict compliance.
2. **Mixed Enforcement Phase**: Enforce new rules for new evidence but apply legacy rules to existing modal sets; monitor divergence.
3. **Strict Enforcement Phase**: Full compliance with NIP-017; reject any evidence or configuration not meeting specifications.

This phased approach minimizes disruption while ensuring eventual convergence to uniform epistemic standards.

## 9. Security and Safety Considerations

### 9.1 Adversarial Evidence

An attacker may attempt to:

- **Inflate confidence values**: Mitigated by Rule 1 (recomputation)
- **Replay stale evidence**: Mitigated by Rule 2 (freshness)
- **Inject null or malformed evidence**: Mitigated by Rule 3 (existence)
- **Create logical contradictions**: Mitigated by Rule 4 (consistency)

### 9.2 Clock Skew

Distributed systems may exhibit clock drift. The effective staleness limit incorporates a drift budget to prevent false rejection of valid evidence. Operators should monitor observed clock skew and adjust the drift budget to match their environment (up to ~50 ms).

### 9.3 Threshold Misconfiguration

Thresholds below the safety floors (Section 4.7) are rejected to prevent degenerate epistemic classifications. Administrators cannot bypass these floors even with domain pack overrides.

### 9.4 Hysteresis Stability

If hysteresis is used, asymmetric thresholds should be chosen to prevent oscillation. Widening the gap between insertion and withdrawal thresholds increases stability but may increase staleness of modal classifications.
