# NIP-018: Formal Operator Semantics

## Abstract

This NIP defines the canonical operator semantics for Noe v1.0, establishing the complete semantic behavior of all logical, numeric, temporal, spatial, modal, and action operators. It specifies value domains, operator signatures, truth tables, undefined/error propagation rules, precedence and associativity rules, and deterministic evaluation criteria. This specification ensures consistent interpretation across all conformant implementations.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

The following notational conventions are used throughout this document:

- **D_t**: Truth value domain = {true, false, undefined}
- **D_e**: Entity domain (individuals in the fact base)
- **D_n**: Numeric domain (integers and decimals)
- **D_s**: Scalar/intensity domain (per NIP-006)
- **D_tms**: Temporal/timestamp domain
- **D_lit**: Literal domain (constants, ground terms)
- **A**: Action domain
- **C_safe**: Safe projected context (per NIP-009)
- **→**: Function signature notation (domain → codomain)
- **⊢**: Provability/derivability
- **≡**: Definitional equivalence
- **⟨x, y⟩**: Ordered pair notation

## 1. Purpose

The purpose of this NIP is to:

1. Establish a formal, unambiguous semantics for all operators in the Noe language
2. Define the complete type signatures and domain mappings for operator evaluation
3. Specify how undefined values and errors propagate through expression evaluation
4. Clarify the distinction between type errors (undefined behavior) and domain errors
5. Ensure deterministic, reproducible evaluation across all conformant implementations
6. Provide the semantic foundation for NIP-004 (Syntax and Operators) and NIP-005 (Core Semantics)

## 2. Scope

This NIP covers:

- Logical operators (conjunction, disjunction, negation)
- Equality and comparison operators
- Numeric/arithmetic operators
- Spatial/directional operators
- Temporal operators
- Scalar/intensity operators (with reference to NIP-006)
- Epistemic operators (with reference to NIP-017)
- Deictic operators
- Conditional operators
- Action constructors
- Operator precedence and associativity
- Error classification and propagation
- Determinism guarantees

This NIP does not cover:

- Specific syntax for operator application (covered in NIP-004)
- Context model and safe projection (covered in NIP-009)
- Epistemic mapping and evidence validation (covered in NIP-017)
- Demonstrative resolution algorithms (covered in NIP-014)

## 3. Definitions

**Operator**: A function that takes one or more operands (values from defined domains) and returns a value in a defined codomain.

**Domain**: The set of all possible input values for an operator; the set of all possible output values.

**Arity**: The number of operands an operator requires (unary = 1, binary = 2, etc.).

**Signature**: The formal specification of an operator's input and output domains, written as Domain₁ × Domain₂ × … → Codomain.

**Truth value**: An element of D_t = {true, false, undefined}. Note: "undefined" is a truth value, distinct from error.

**Undefined**: A special value indicating missing context, missing entity, or unknown truth value. Operators may propagate undefined through expressions.

**Error**: A special condition indicating a type mismatch, domain violation, or malformed operation. Errors typically halt evaluation or propagate up the call stack.

**Determinism**: Given identical input state (fact base, registry, C_safe), evaluation of any expression yields identical results across all interpreters.

**Precedence**: The binding strength of operators; higher precedence operators bind more tightly than lower precedence operators.

**Associativity**: The direction in which operators of equal precedence are grouped; left-associative operators group left-to-right, right-associative operators group right-to-left.

**K3 logic**: Three-valued logic (Kleene 3-valued logic) with truth values {true, false, undefined}; used for logical operator semantics.

## 4. Specification

### 4.1 Value Domains

The Noe language operates over the following value domains:

| Domain | Symbol | Elements | Description |
|--------|--------|----------|-------------|
| Truth values | D_t | {true, false, undefined} | Boolean and three-valued logic |
| Entities | D_e | Elements of fact base | Individual objects, agents, entities |
| Numerics | D_n | ℤ, ℚ (integers, decimals) | Numeric values |
| Scalars | D_s | [0, 1] ∪ {undefined} | Intensity/credence values (per NIP-006) |
| Timestamps | D_tms | ISO 8601 timestamps | Temporal instants and intervals |
| Literals | D_lit | Constants, ground terms | Symbolic constants |
| Actions | A | {type, verb, target, kind} | Action terms (per NIP-005) |

### 4.2 Logical Operators

#### 4.2.1 Conjunction (an)

**Signature**: D_t × D_t → D_t

**Truth table** (K3 logic, false-dominated):

| Left | Right | an(Left, Right) |
|------|-------|-----------------|
| true | true | true |
| true | false | false |
| true | undefined | undefined |
| false | true | false |
| false | false | false |
| false | undefined | false |
| undefined | true | undefined |
| undefined | false | false |
| undefined | undefined | undefined |

**Semantics**: Conjunction (logical AND) follows Kleene 3-valued logic with false-domination. False is sticky: if either operand is false, the result is false. If neither operand is false but either is undefined, the result is undefined. Only if both operands are true is the result true.

#### 4.2.2 Disjunction (ur)

**Signature**: D_t × D_t → D_t

**Truth table** (K3 logic, true-dominated):

| Left | Right | ur(Left, Right) |
|------|-------|-----------------|
| true | true | true |
| true | false | true |
| true | undefined | true |
| false | true | true |
| false | false | false |
| false | undefined | undefined |
| undefined | true | true |
| undefined | false | undefined |
| undefined | undefined | undefined |

**Semantics**: Disjunction (logical OR) follows Kleene 3-valued logic with true-domination. True is sticky: if either operand is true, the result is true. If neither operand is true but either is undefined, the result is undefined. Only if both operands are false is the result false.

#### 4.2.3 Negation (nai)

**Signature**: D_t → D_t

**Truth table**:

| Input | nai(Input) |
|-------|------------|
| true | false |
| false | true |
| undefined | undefined |

**Semantics**: Negation inverts true to false and false to true. Undefined values pass through unchanged. nai(nai(P)) ≡ P for all P ∈ D_t (law of double negation).

### 4.3 Structural Operators (el, nul)

These operators belong to D_struct (structural domain) per `registry.json`. They are NOT numeric equality operators.

#### 4.3.1 Identity (el)

**Registry**: g_el, D_struct, type_sig: Pred

**Signature**: D_e × D_e → D_t (binary structural predicate)

**Semantics** (per NIP-005 §4.9.1):
- `A el B` returns true if A and B denote the same value (structural identity)
- `A el B` returns false if both are defined and unequal
- `A el B` returns undefined if either operand is undefined

`el` tests value identity, not numeric equality. It operates across all value domains.

> **Grammar note**: `el` is registered in `registry.json` (g_el, D_struct, type_sig: Pred) but does not currently appear in the NIP-004 PEG grammar or `operator_lexicon.py`. It is parsed as a relational-band binary operator when encountered. Implementations SHOULD treat `el` as a binary predicate at relational precedence (band 4 per NIP-004 §4.7). A future NIP may formalize its grammar insertion point.

#### 4.3.2 Null (nul)

**Registry**: g_nul, D_struct, type_sig: Const

**Semantics** (per NIP-005 §4.9.2):
- `nul` is a structural constant representing the empty/null value
- `A el nul` evaluates to true if A is an empty structure
- `A el nul` evaluates to false if A is a non-empty defined value
- `A el nul` evaluates to undefined if A is undefined

`nul` is NOT an operator — it is a constant. It does not take arguments. To test for null, use `el` with `nul` as the right-hand operand.

### 4.4 Comparison Operators

**Signatures** (per NIP-004 §4.7, precedence band 3):
- `<` : D_n × D_n → D_t
- `>` : D_n × D_n → D_t
- `<=` : D_n × D_n → D_t
- `>=` : D_n × D_n → D_t
- `=` : D_n × D_n → D_t (numeric equality)

**Semantics**:
- Comparisons evaluate to true, false, or undefined following standard numeric comparison
- If any argument is undefined, result is undefined
- If any argument is non-numeric, result is error
- `=` is the numeric equality operator (distinct from `el`, which is structural identity)

### 4.5 Numeric/Arithmetic Operators

Numeric operators are in D_numeric_op (type_sig: Op). Full semantics are defined in NIP-007.

| Operator | Phonetic | Semantic | Signature | Description |
|----------|----------|----------|-----------|-------------|
| g_ap | ap | Add | D_n × D_n → D_n | Numeric sum |
| g_su | su | Sub | D_n × D_n → D_n | Numeric difference |
| g_ka | ka | Mul | D_n × D_n → D_n | Numeric product |
| g_vo | vo | Div | D_n × D_n → D_n | Numeric quotient |
| g_ran | ran | Range | D_n × D_n → D_n | Numeric range |

**Common semantics**:
- If either argument is undefined, result is undefined
- If either argument is non-numeric, result is error
- Division by zero (`vo(n, 0)`) → error
- Numeric digits (zo=0, un=1, du=2, tua=3, fo=4, pen=5, hek=6, sep=7, ok=8, nan=9) are in D_numeric with type_sig: Num

### 4.6 Spatial Operators

Spatial operators fall into two categories: **proximity operators** (D_spatial, type_sig: Rel) and **directional operators** (D_spatial, type_sig: Rel, axis-aligned Cartesian).

All spatial operators have the signature: D_e × D_e → D_t

#### 4.6.1 Proximity Operators

| Operator | Phonetic | Semantic | Description |
|----------|----------|----------|-------------|
| g_nel | nel | Near | Proximal — e₁ is near e₂ (within `thresholds.near`) |
| g_tel | tel | Far | Distal — e₁ is far from e₂ (beyond `thresholds.far`) |
| g_xel | xel | Contact | Aligned/in contact — e₁ is contiguous with e₂ |

#### 4.6.2 Directional Operators (Axis-Aligned Cartesian)

Per NIP-014, directional operators use axis-aligned Cartesian comparisons on (x, y, z) coordinates:

| Operator | Phonetic | Semantic | Axis Test |
|----------|----------|----------|-----------|
| g_lef | lef | Left | x₁ < x₂ |
| g_rai | rai | Right | x₁ > x₂ |
| g_fai | fai | Front | y₁ > y₂ |
| g_ban | ban | Behind | y₁ < y₂ |
| g_sup | sup | Up | z₁ > z₂ |
| g_bel | bel | Down | z₁ < z₂ |

Position is resolved via three-layer lookup: `C_local.position` → `C_root.spatial.frames` → `C_safe.entities`.

**Common semantics**:
- If either entity's position cannot be resolved, result is undefined
- Evaluation requires C_safe spatial data (per NIP-014)
- Missing or non-numeric coordinates → undefined
- Spatial operators sit in precedence band 4 (relational operators per NIP-004 §4.7)

**Deictic usage**: Spatial operators serve as directional filters in demonstrative resolution (NIP-014 §4.2 Step 2), constraining which candidate entity a deictic term (dia/doq) resolves to.

### 4.7 Temporal Operators

Temporal operators are **unary prefix operators** in D_temporal (registry domain). They modify the temporal frame of the following expression.

**Signature**: D_t → D_t (temporal frame modification)

**Operators** (from `registry.json`):

| Operator | Phonetic | Semantic | type_sig | Description |
|----------|----------|----------|----------|-------------|
| g_nau | nau | Now | Op | Present tense — evaluates P in the current temporal frame |
| g_ret | ret | Past | Op | Past tense — evaluates P against the most recent past snapshot |
| g_tri | tri | Future | Op | Future tense — evaluates P against projected future state |
| g_qer | qer | Iteration | loop_op | Repetition — evaluates P over repeated cycles |

**Common semantics**:
- Temporal operators modify the evaluation context's temporal reference point, not the expression's truth value directly
- If the required temporal snapshot is unavailable, result is undefined
- `nau`, `ret`, `tri` share precedence band 1 (core unary operators per NIP-004 §4.7)
- `qer` has type_sig `loop_op` and introduces iteration semantics over a time window
- Temporal operators are right-associative and bind only to the immediately following clause

> **Note**: Noe does NOT have binary temporal relational operators (e.g., `before(t₁, t₂)` or `after(t₁, t₂)`). Temporal reasoning is expressed through unary tense operators applied to propositions: `ret P` ("P was true"), `tri P` ("P will be true"), `nau P` ("P is true now").

### 4.8 Scalar/Intensity Operators

Scalar intensity operators are **unary postfix operators** defined in NIP-006. They apply multiplicative scaling factors to the scalar magnitude of their target atom. They do NOT affect truth values.

**Operators** (per NIP-006):

| Operator | Symbol | Multiplier | Semantic |
|----------|--------|-----------|----------|
| Diminished | `'` (single quote) | 0.5x | Halves scalar magnitude |
| Neutral | `"` (double quote) | 1.0x | No change (baseline) |
| Amplified | `°` (degree) | 2.0x | Doubles scalar magnitude |

**Signature**: D_s → D_s (postfix, unary)

**Computation model** (per NIP-006):
```
output_scalar = intrinsic_value * multiplier
```

**Semantics**:
- Intensity operators modify scalar magnitude only; truth values are unaffected
- An expression with an intensity operator and its unmodified counterpart yield identical truth values under all evaluations
- If the operand is `undefined`, the result is `undefined`
- Absence of an intensity marker implies baseline (1.0x), identical to explicit `"`
- Intensity operators bind with higher precedence than all other postfix operators except morphological operators

### 4.9 Epistemic Operators

Epistemic operators (shi, vek, sha) are defined per NIP-005 §4.8 and NIP-017. They take a proposition (literal key) and check modal set membership, returning a truth value from the appropriate modal map.

**Signatures**: Proposition → D_t (modal set membership lookup)

| Operator | Phonetic | Semantic | Modal Map | Absent Return |
|----------|----------|----------|-----------|---------------|
| g_shi | shi | Knowledge | C_safe.modal.knowledge | undefined |
| g_vek | vek | Belief | C_safe.modal.knowledge then .belief | undefined |
| g_sha | sha | Certainty | C_safe.modal.certainty (numeric threshold) | undefined |

**Semantics** (per NIP-005 §4.8 and NIP-017):
- `shi P`: Returns the truth value of P from `C_safe.modal.knowledge`. If P is not in the knowledge map, returns `undefined`. In strict mode, absence produces `ERR_EPISTEMIC_MISMATCH`.
- `vek P`: Checks knowledge first (knowledge implies belief), then belief. Returns truth value if found; `undefined` if absent from both maps.
- `sha P`: Reads a numeric certainty level from `C_safe.modal.certainty[P]` and compares against `C_safe.modal.certainty_threshold`. If threshold met, returns truth value from knowledge or belief map; otherwise `undefined`.

**Important interaction rules**:
- `shi (nai P)`: "We know not-P" — requires positive evidence of absence; distinct from `nai (shi P)`
- `nai (shi P)`: "We do NOT know P" — epistemic ignorance; the agent lacks knowledge of P
- Epistemic operators sit in precedence band 1 (core unary operators per NIP-004 §4.7)
- Epistemic operators cannot nest with action constructors

### 4.10 Demonstrative Operators

Demonstrative operators (dia, doq) are in D_demonstrative (type_sig: Ref). They resolve to entities via dual-path resolution per NIP-014.

**Registry entries**:
- `g_dia` — phonetic: dia, semantic: "This" (proximal demonstrative)
- `g_doq` — phonetic: doq, semantic: "That" (distal demonstrative)

**Signature**: Unit → D_e ∪ {undefined}

**Resolution** (per NIP-014 §4.2):
1. **Direct binding (priority path)**: Check `C_local.demonstratives.{dia|doq}.entity`. If present, resolve immediately.
2. **Spatial fallback**: If no direct binding, resolve against candidate entities using distance thresholds:
   - `dia` resolves to the nearest entity within `thresholds.near`
   - `doq` resolves to the farthest entity beyond `thresholds.far`
3. Spatial fallback applies directional filters if the demonstrative appears as an operand to a spatial operator (e.g., `dia lef X` filters candidates where the resolved entity is left of X)
4. Ties (multiple equidistant candidates) → undefined

**Semantics**:
- Demonstratives resolve to an entity in D_e or `undefined` if resolution fails
- Demonstratives can appear in spatial operator arguments (`dia lef X` = "this thing, to the left of X")
- Demonstratives can appear in action constructor arguments
- If the demonstrative resolves to an entity, that entity MUST exist in `C_safe.entities`

### 4.11 Conditional Operators (khi)

**Signature**: D_t × A → A (khi takes a guard condition and an action)

**Semantics**:
- khi(guard, action): If guard is true, return action; otherwise return undefined
- khi(true, a) → a
- khi(false, a) → undefined
- khi(undefined, a) → undefined
- khi(error, a) → error

**Evaluation order**: The guard is always evaluated before the action. The action is never evaluated if the guard is false or undefined.

### 4.12 Action Semantics

Action terms are constructed via `mek` and produce values in D_action with the structure `{type: "action", verb, target, kind, action_hash, provenance}` (per NIP-005 §4.11).

**Signature**: (Symbol, D_lit ∪ D_e) → A ∪ {error}

**Semantics**:
- `mek` constructs an action term with `type`, `verb`, `target`, and `kind` fields
- The target must be a valid literal or entity reference in C_safe
- If any required field is undefined, the entire action is undefined
- Malformed action terms (invalid target reference) → `ERR_BAD_ACTION_TARGET_REF`
- Each fact chain contains at most one action constructor; multiple actions → error
- Circular action references → `ERR_ACTION_CYCLE`

**Action execution**: Actions are values in D_action, distinct from truth values. They are produced only when the guard condition (via `khi`) evaluates to true. Evaluation of `mek` is pure and deterministic; execution is handled by the delivery layer (vus/vel per NIP-008).

### 4.13 Precedence and Associativity

Operator precedence and associativity are authoritative in NIP-004 §4.7. The following summary is provided for reference:

**Precedence** (highest to lowest, per NIP-004 §4.7):
1. **Core unary operators** — nai, nex, shi, vek, sha, tor, nau, ret, tri, qer, vus, vel, da
2. **Action constructors** — mek, men
3. **Comparative operators** — <, >, <=, >=, =
4. **Relational / spatial / integrity operators** — kos, til, nel, tel, xel, tra, fra, en, kra, noq
5. **Conjunction** — an
6. **Disjunction** — ur
7. **Conditional guard** — khi

Scope (`sek`...`sek`) overrides precedence. `nek` is a terminator, not an operator.

**Associativity**:
- Left-associative: binary operators (an, ur, relational, comparative)
- Right-associative: unary operators
- Non-associative: khi

### 4.14 Error vs. Undefined Classification

A critical distinction is made between undefined and error:

| Condition | Classification | Propagation | Example |
|-----------|-----------------|-------------|---------|
| Missing entity | undefined | Propagates | Entity e₁ position unresolvable, nel(e₁, e₂) → undefined |
| Missing context | undefined | Propagates | Temporal snapshot unavailable, ret P → undefined |
| Type mismatch | error | Halts/propagates | Non-numeric operand, ap(e₁, e₂) → error |
| Division by zero | error | Halts/propagates | vo(n, 0) → error |
| Invalid operator | error | Halts/propagates | Using spatial operator with non-entities → error |
| Malformed action | error | Halts/propagates | ERR_BAD_ACTION_TARGET_REF |

**Propagation rules**:
- undefined operands produce undefined results (with exceptions for an/ur false-true domination)
- error operands typically produce error results and halt evaluation
- Mixing error and undefined in the same expression: error takes precedence

### 4.15 Determinism Guarantee

**Theorem**: Given identical input state (fact base F, registry R, and safe context C_safe), evaluation of any expression E yields identical results ⟨v, s⟩ across all conformant interpreters.

**Conditions for determinism**:
1. The fact base F is identical
2. The operator registry R is identical
3. The safe context constraints C_safe are identical
4. No external non-deterministic sources (random values, system time during evaluation, network I/O) are introduced
5. The evaluation order follows NIP-004 precedence rules exactly

**Consequence**: Deterministic evaluation is essential for distributed consensus. All implementations must honor operator signatures and semantics exactly as specified in this NIP.

## 5. Rationale

### 5.1 Three-Valued Logic (K3)

Noe employs Kleene 3-valued logic rather than classical 2-valued logic to handle incomplete information gracefully. In a distributed fact base, information may be genuinely unknown, and this is distinct from false. The choice of false-domination for conjunction and true-domination for disjunction follows standard epistemic logic conventions where:

- False represents definite falsity (strong negation)
- Undefined represents lack of information
- True represents definite truth

This ensures that queries that depend on false facts fail early and decisively.

### 5.2 Error vs. Undefined

The distinction between error and undefined is crucial:

- **Undefined** (missing context, missing entity) is recoverable and propagates gracefully through expressions
- **Error** (type mismatch, malformed operation) indicates a fundamental violation and should halt evaluation

This separation prevents subtle bugs where type errors silently become undefined values.

### 5.3 Determinism for Consensus

Distributed consensus in Noe depends on identical evaluation results across independent agents. Deterministic operator semantics ensure that different implementations, running independently, produce identical conclusions from identical inputs. This is essential for fault tolerance and agreement protocols.

### 5.4 Spatial and Temporal Operators

Spatial operators use axis-aligned Cartesian comparisons (per NIP-014) to provide deterministic, reproducible directional reasoning. Temporal operators use unary tense modification (nau/ret/tri/qer) rather than binary interval relations, reflecting Noe's design of temporal reasoning as frame modification on propositions rather than relational algebra on timestamps.

### 5.5 Epistemic Operators

Epistemic operators (shi, vek, sha) enable agents to distinguish between facts they know (shi — knowledge), facts they believe (vek — belief), and facts with high certainty (sha — certainty threshold). The distinction between `shi (nai P)` and `nai (shi P)` is subtle but crucial: the former requires positive evidence of absence, while the latter merely indicates lack of knowledge. This supports the epistemic mapping framework (NIP-017).

### 5.6 Demonstrative Operators and Context-Dependence

Demonstrative operators (dia, doq) enable situated reasoning through proximal/distal reference resolution. `dia` resolves to the nearest entity ("this") and `doq` to the farthest ("that"), using dual-path resolution (direct binding or spatial fallback per NIP-014). Demonstratives naturally compose with spatial operators as directional filters.

### 5.7 Action Semantics and Controlled Side Effects

Action semantics (via mek) are designed to be pure (no side effects during evaluation), but executable in dedicated execution contexts. This separation ensures that evaluation is deterministic and side-effect-free, while allowing controlled execution of actions when appropriate.

## 6. Examples

### 6.1 Logical Operator Examples

**Example 1: Conjunction with undefined**

```
Fact base: agent_x_is_tired = true
Query: an(agent_x_is_tired, agent_x_completed_task)

agent_x_completed_task is not in fact base → undefined
Result: an(true, undefined) = undefined
Interpretation: Cannot determine if both conditions hold; insufficient information.
```

**Example 2: Disjunction with false**

```
Fact base: has_permission = false, has_override = undefined
Query: ur(has_permission, has_override)

Result: ur(false, undefined) = undefined
Interpretation: At least one disjunct is not known to be true; cannot assert the disjunction.
```

**Example 3: Double negation**

```
Query: nai(nai(agent_x_is_tired)) where agent_x_is_tired = true
Result: nai(nai(true)) = nai(false) = true
Interpretation: Law of double negation holds in K3 logic.
```

### 6.2 Structural and Comparison Operator Examples

**Example 4: Structural identity (el)**

```
Query: @sensor_a el @sensor_a
Result: true (same value identity)

Query: @sensor_a el @sensor_b
Result: false (different entities)

Query: @sensor_a el nul
Result: false (sensor_a is not empty)

Query: undefined el @sensor_a
Result: undefined
```

**Example 5: Numeric comparison (=, <)**

```
Context: C_safe.literals.@temperature = 7

Query: @temperature = un zo    /* 7 = 10? */
Result: false

Query: @temperature < un zo    /* 7 < 10? */
Result: true

Query: @temperature < undefined
Result: undefined
```

### 6.3 Spatial Operator Examples

**Example 6: Proximity and directional relationships**

```
Context:
  C_safe.entities.agent_a.position = {x: 10, y: 20, z: 0}
  C_safe.entities.agent_b.position = {x: 20, y: 20, z: 0}
  thresholds.near = 15.0

Query: nel(agent_a, agent_b)  /* Is agent_a near agent_b? */
Result: true (distance ~10 < thresholds.near of 15)

Query: lef(agent_a, agent_b)  /* Is agent_a left of agent_b? */
Result: true (agent_a.x=10 < agent_b.x=20)

Query: rai(agent_a, agent_b)  /* Is agent_a right of agent_b? */
Result: false (agent_a.x=10 is NOT > agent_b.x=20)

Query: nel(agent_a, nonexistent_agent)
Result: undefined (nonexistent_agent position unresolvable)
```

### 6.4 Temporal Operator Examples

**Example 7: Tense operators**

```
Context:
  C_safe.literals.@door_locked = true   (current snapshot)
  Past snapshot: @door_locked = false   (1 cycle ago)

Query: nau @door_locked   /* Is the door locked NOW? */
Result: true (current snapshot confirms)

Query: ret @door_locked   /* Was the door locked in the past? */
Result: false (past snapshot shows unlocked)

Query: tri @door_locked   /* Will the door be locked in the future? */
Result: undefined (no projected future state available)
```

### 6.5 Epistemic Operator Examples

**Example 8: Knowledge vs. belief**

```
Context:
  C_safe.modal.knowledge.@sensor_active = true
  C_safe.modal.belief.@weather_clear = true
  (No entry for @engine_ready in any modal map)

Query: shi @sensor_active   /* Do we KNOW sensor_active? */
Result: true (found in knowledge map)

Query: vek @weather_clear   /* Do we BELIEVE weather_clear? */
Result: true (not in knowledge, but found in belief map)

Query: vek @sensor_active   /* Do we BELIEVE sensor_active? */
Result: true (knowledge implies belief — found in knowledge map first)

Query: shi @engine_ready    /* Do we KNOW engine_ready? */
Result: undefined (not in knowledge map)

Query: shi (nai @sensor_active)  /* Do we know NOT sensor_active? */
Result: undefined (no positive evidence of absence in knowledge map)

Query: nai (shi @sensor_active)  /* Do we NOT know sensor_active? */
Result: false (nai(true) = false — we DO know it)
```

### 6.6 Action Constructor Examples

**Example 9: Conditional action execution**

```
Fact base:
  permission_granted = true
  user_id = user_123

Query: khi(permission_granted, mek(execute_action, user_id))
Result: action(execute_action, [user_123])

Query: khi(false, mek(execute_action, user_id))
Result: undefined (action not executed)

Query: khi(undefined, mek(execute_action, user_id))
Result: undefined (action not executed due to unknown guard)
```

**Example 10: Nested operators**

```
Context:
  C_safe.literals.@temperature = 7
  C_safe.entities.agent_a.position = {x: 10, y: 20, z: 0}
  C_safe.entities.agent_b.position = {x: 12, y: 20, z: 0}

Evaluation:
  @temperature < un zo  →  7 < 10  →  true
  nel(agent_a, agent_b)  →  distance ~2 < 15  →  true

```

## 7. Conformance Requirements

An implementation is conformant with NIP-018 if and only if:

1. **Truth value semantics**: All logical operators (an, ur, nai) implement the K3 truth tables specified in §4.2.

2. **Domain signatures**: All operators implement the domain signatures specified in §4.

3. **Undefined propagation**: Undefined operands produce undefined results (except where false-true domination applies in an/ur).

4. **Error classification**: Type mismatches, malformed operations, and domain violations are classified as errors and propagate as specified in §4.14.

5. **Determinism**: Given identical input state, evaluation of any expression yields identical results.

6. **Precedence and associativity**: Operator precedence and associativity follow NIP-004 §4.7 exactly.

7. **Context requirements**: Spatial and demonstrative operators use C_safe position data and demonstrative bindings (per NIP-009, NIP-014).

8. **Action semantics**: Action constructors (mek) produce action terms or errors as specified in §4.12.

9. **Epistemic operator semantics**: Epistemic operators (vek, shi, sha) follow NIP-017 semantics exactly.

10. **No non-determinism**: No external non-deterministic sources (random values, system time, I/O) affect operator evaluation.

## 8. Backwards Compatibility

NIP-018 is a normative specification for Noe v1.0. As a Foundational NIP, it defines semantics that were assumed in earlier NIPs but not formally specified.

**Changes from earlier Noe versions**:
- Noe v0.9 and earlier used informally specified operator semantics
- This NIP formalizes those semantics and resolves all ambiguities
- All v0.9 code that conformed to the implicit semantics remains conformant with NIP-018

**Compatibility guarantee**: Code written for Noe v0.9 that follows the informal semantics implied by NIP-004, NIP-005, and NIP-017 will produce identical results under NIP-018 semantics.

**Future versions**: NIP-018 is frozen for Noe v1.0. Changes to operator semantics in Noe v1.1 or later would require a new NIP and possibly a new version number.

## 9. Security and Safety Considerations

### 9.1 Type Safety

Enforcing strict domain signatures prevents type confusion attacks. An agent cannot accidentally (or maliciously) treat an entity as a number or vice versa; type mismatches result in errors, not silent conversions.

### 9.2 Error vs. Undefined

The distinction between error and undefined ensures that queries fail decisively on type errors rather than silently succeeding with undefined results. This prevents subtle security vulnerabilities where malformed data is treated as missing data.

### 9.3 Safe Context Requirements

Spatial operators and demonstrative operators require position data from C_safe (per NIP-014). Missing or unresolvable position coordinates produce `undefined`, not errors, preventing silent use of stale or fabricated spatial data.

### 9.4 Action Determinism

Deterministic action semantics ensure that conditionals and guards behave predictably. An action will execute if and only if its guard evaluates to true; no side effects occur during evaluation.

### 9.5 Epistemic Integrity

Epistemic operators (shi, vek, sha) derive truth values exclusively from calibrated modal maps populated via NIP-017's validator rules. Confidence inflation, stale evidence, and logical contradictions are rejected before they enter the modal context, ensuring epistemic operators operate on verified evidence only.

### 9.6 Temporal Operator Safety

Temporal tense operators (nau, ret, tri) require the relevant temporal snapshot to be available in the evaluation context. If a past or future snapshot is unavailable, the operator returns `undefined` rather than silently using the current snapshot. This prevents temporal reasoning attacks where stale or projected state is substituted without explicit support.
