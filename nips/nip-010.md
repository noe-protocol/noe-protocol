# NIP-010: Audit and Provenance Semantics

## Abstract

NIP-010 defines the audit and provenance semantics that govern the recording of evaluation metadata in the Noe protocol. Every evaluation produces a deterministic provenance record that captures the canonical execution chain, context fingerprints, and cryptographic hashes that identify the evaluation outcome. This specification establishes three v1.0 invariants: (1) one canonical chain string per evaluation, (2) namespace separation between action_hash and decision_hash, and (3) blocked outcomes carry no execution-identifying hashes. The provenance record enables cryptographic verification, auditability, and cross-agent reproducibility of Noe evaluations.

## Notation Convention

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC 2119] [RFC 8174] when, and only when, they appear in ALL CAPITALS, as shown here.

## 1. Purpose

The purpose of NIP-010 is to establish normative semantics for recording, hashing, and verifying the provenance of Noe evaluations. Provenance records serve as the audit trail for decision making and action execution within the Noe protocol. By defining canonical representations, hash namespaces, and deterministic provenance structures, this specification enables:

- Cryptographic verification of evaluation authenticity
- Cross-agent reproducibility and validation
- Immutable audit trails for compliance and forensics
- Prevention of hash collision attacks through namespace separation

## 2. Scope

This specification covers:

- Canonical chain representation and normalization rules
- Context fingerprinting mechanisms (context_hash and domain_pack_hash)
- Hash namespace definitions for action, decision, and child action identification
- Provenance record structure and payload composition
- Determinism requirements for cross-implementation consistency

This specification does NOT cover:

- The evaluation algorithm itself (see NIP-004, NIP-005)
- Domain-specific result serialization (see NIP-009)
- Storage or transmission of provenance records

## 3. Definitions

**canonical chain**: The single source of truth representation of an evaluation execution sequence, produced by the runtime and subject to NFKC normalization and whitespace normalization.

**context_hash**: A hierarchical SHA-256 hash representing the complete evaluation context. Computed as `H_total = SHA-256(H_root || H_domain || H_local)`, where H_root, H_domain, and H_local are the individual layer hashes from NIP-009 §4.8.1 and `||` denotes raw byte concatenation. This is distinct from `H_safe` (which hashes the merged C_safe directly); `H_total` preserves layer identity and is the value used in provenance records. Attached to every provenance record.

**domain_pack_hash (H_domain_pack)**: A SHA-256 hash representing the domain-specific configuration and packing rules, attached to every provenance record.

**canonical JSON**: UTF-8 encoded JSON with sorted object keys and stable representation, used as input to all hashing operations.

**action_hash**: Namespace-specific hash computed only when result_domain equals "action" and the evaluation is not blocked.

**decision_hash**: Namespace-specific hash computed only when result_domain does not equal "action", the evaluation is not blocked, and the evaluation succeeded.

**child_action_hash**: Namespace-specific hash computed when an action is executed as a child of a parent action.

**provenance_hash**: The master hash computed over the complete provenance payload, null if the evaluation is blocked or did not complete execution.

**mutual exclusivity**: The property that action_hash and decision_hash are never both present in a provenance record.

**epistemic_basis**: A sorted, deduplicated list of literal keys (e.g., `["@channel_open", "@human_present"]`) that were consulted during evaluation and contributed to the result. These are the grounding literals that justified the action or decision.

**value_system_basis**: A sorted, deduplicated list of normative policy identifiers from `C_safe.value_system` that were active during evaluation. These record which value constraints (accepted/rejected policies) governed the evaluation.

**non-execution invariant**: The property that if result_domain is undefined or indicates an error, all identity hashes are set to null.

**ast_repr**: An optional human-readable string representation of the parse tree produced by NIP-004 parsing. When present, it enables structural comparison of evaluations independent of whitespace or surface syntax differences.

**ast_hash**: SHA-256 hash of `ast_repr`. If `ast_repr` is absent, `ast_hash` MUST be set to `"0" * 64` (64 zero characters). If `ast_repr` is present, `ast_hash = SHA-256(ast_repr)`.

**action_structure_hash**: An optional hash computed over the action descriptor's verb, target, sorted modifiers, and parameters (RECOMMENDED but not required).

## 4. Specification

### 4.1 Canonical Chain Representation

The canonical chain is the authoritative representation of an evaluation's execution history. The runtime is the single source of truth for the canonical chain.

Canonicalization of the chain string MUST apply:

1. Unicode Normalization Form NFKC (as defined in Unicode Standard Annex #15)
2. Whitespace normalization: collapse internal whitespace to single spaces, trim leading and trailing whitespace

```text
CanonicalChain = NFKC(chain) normalized for whitespace
```

### 4.2 Context Fingerprinting

Two context fingerprints MUST be computed and attached to every evaluation:

- **context_hash (H_total)**: Hierarchical SHA-256 hash: `SHA-256(H_root_bytes || H_domain_bytes || H_local_bytes)`, where each layer hash is computed per NIP-009 §4.8.1
- **domain_pack_hash (H_domain_pack)**: SHA-256 hash of domain-specific configuration

Both hashes are included in all subsequent hash namespace computations and in the provenance payload.

### 4.3 Canonical JSON Representation

All data structures used as input to hash operations MUST be serialized as canonical JSON with the following properties:

- Encoding: UTF-8
- Key ordering: object keys sorted in lexicographic order
- No extraneous whitespace
- Stable representation across implementations

```json
{
  "noe.action.v1": null,
  "canonical_chain": "...",
  "context_hash": "...",
  "domain_pack_hash": "..."
}
```

All hash inputs are normalized to canonical JSON before hashing.

### 4.4 Hash Namespaces

#### 4.4.1 action_hash

The action_hash is computed only when all of the following conditions hold:

- result_domain == "action"
- The evaluation is not blocked
- The evaluation completed successfully

Computation:

```text
action_hash = SHA256(CanonicalJSON([
  "noe.action.v1",
  canonical_chain,
  context_hash,
  H_domain_pack
]))
```

#### 4.4.2 decision_hash

The decision_hash is computed only when all of the following conditions hold:

- result_domain != "action"
- The evaluation is not blocked
- The evaluation completed successfully

Computation:

```text
decision_hash = SHA256(CanonicalJSON([
  "noe.decision.v1",
  canonical_chain,
  context_hash,
  H_domain_pack
]))
```

#### 4.4.3 child_action_hash

The child_action_hash is computed only when all of the following conditions hold:

- The action is executed as a child of a parent action
- A parent_action_hash exists
- result_domain == "action"
- The evaluation is not blocked

Computation:

```text
child_action_hash = SHA256(CanonicalJSON([
  "noe.child_action.v1",
  parent_action_hash,
  canonical_chain,
  context_hash,
  H_domain_pack
]))
```

#### 4.4.4 Mutual Exclusivity

A provenance record MUST NOT contain both action_hash and decision_hash. These namespaces are mutually exclusive by design: an evaluation produces a result in exactly one domain at a time.

### 4.5 Provenance Hash

The provenance_hash is the master hash computed over the complete provenance payload.

Computation:

```text
hash_payload = {
  "version": "noe-prov-v1",
  "chain_hash": SHA256(canonical_chain),
  "ast_hash": <AST representation hash>,
  "context_hash": context_hash,
  "result": { "domain": <result_domain>, "value": <result_value> },
  "epistemic_basis": <epistemic metadata>,
  "value_system_basis": <value system metadata>,
  "parent_action_hash": <parent hash or null>,
  "action_hash": <action_hash or null>,
  "decision_hash": <decision_hash or null>,
  "child_action_hash": <child_action_hash or null>,
  "domain_pack_hash": H_domain_pack
}

provenance_hash = SHA256(CanonicalJSON(hash_payload))
```

If the evaluation is blocked or did not complete execution, provenance_hash MUST be set to null.

### 4.6 Non-Execution Invariant

If result_domain is undefined or indicates an error state, the following MUST hold:

- action_hash = null
- child_action_hash = null
- decision_hash = null
- provenance_hash = null

This invariant ensures that failed or incomplete evaluations do not produce execution-identifying hashes.

### 4.7 Non-Execution Outcome Semantics

When an evaluation does not produce a successful result — i.e., `result_domain` is `"error"` or `"undefined"` (per NIP-005 §4 three-valued logic and NIP-009 §4.11 error semantics):

- All identity hashes MUST be null: action_hash, child_action_hash, decision_hash
- provenance_hash MUST be null
- The provenance record is still recorded for audit purposes
- No execution-identifying information is preserved in the hash chain

There is no separate `"blocked"` domain. A guard failure (e.g., `khi` with a false condition) produces `result_domain = "undefined"`. A context error produces `result_domain = "error"`. Both trigger the non-execution invariant.

### 4.8 Action Structure Hashing (Recommended)

Implementations MAY compute an optional action_structure_hash over the action descriptor's components:

```text
action_structure_hash = SHA256(CanonicalJSON({
  "verb": <action verb>,
  "target": <action target>,
  "modifiers": <sorted modifier list>,
  "parameters": <parameter map>
}))
```

This hash enables structural validation of actions independent of execution context. Computing action_structure_hash is RECOMMENDED but not required for conformance.

## 5. Rationale

### 5.1 Canonical Chain as Single Source of Truth

The runtime is designated as the authoritative source for canonical chain representation because only the runtime observes the complete execution sequence and the temporal ordering of events. By centralizing this authority, ambiguity in chain representation is eliminated, enabling reproducibility.

### 5.2 Namespace Separation

Action and decision hashes are placed in separate namespaces to prevent hash collisions and to enable cryptographic binding to the specific execution domain. A verifier can determine the intended domain of an evaluation by checking which hash is present.

### 5.3 Blocked Outcome Invariant

Blocked evaluations produce no execution-identifying hashes. This prevents hash-based tracking of blocked actions and ensures that failures do not generate cryptographic signatures that could be misinterpreted as successful executions.

### 5.4 Determinism

Deterministic provenance generation requires that identical inputs (canonical_chain, context_hash, H_domain_pack, result_domain) always produce identical hashes across all compliant implementations. This enables cross-agent verification: if two agents evaluate the same chain with the same context, they MUST produce identical provenance records.

### 5.5 UTF-8 and SHA-256

UTF-8 encoding and SHA-256 hashing are chosen for universal compatibility, resistance to collision attacks, and widespread implementation support across programming languages and platforms.

## 6. Examples

### 6.1 Truth Evaluation

A truth evaluation of `shi @sky_blue nek` produces a decision:

```json
{
  "version": "noe-prov-v1",
  "chain": "shi @sky_blue nek",
  "chain_hash": "abc123...",
  "ast_repr": "(unary shi (literal @sky_blue))",
  "ast_hash": "def456...",
  "context_hash": "...",
  "result": {
    "domain": "truth",
    "value": true
  },
  "epistemic_basis": ["@sky_blue"],
  "value_system_basis": [],
  "parent_action_hash": null,
  "action_hash": null,
  "decision_hash": "ghi789...",
  "child_action_hash": null,
  "domain_pack_hash": "...",
  "provenance_hash": "mno012...",
  "created_ts_ms": 1672531200000
}
```

The presence of decision_hash and absence of action_hash indicate that this evaluation produced a truth domain result.

### 6.2 Guarded Action Executed

A guarded action `shi @has_key khi sek mek @open_door sek nek` is evaluated where the guard succeeds:

```json
{
  "version": "noe-prov-v1",
  "chain": "shi @has_key khi sek mek @open_door sek nek",
  "chain_hash": "pqr345...",
  "ast_repr": "(guard (unary shi (literal @has_key)) (scope (action mek (literal @open_door))))",
  "ast_hash": "stu678...",
  "context_hash": "...",
  "result": {
    "domain": "action",
    "value": {
      "type": "action",
      "verb": "mek",
      "target": "@open_door"
    }
  },
  "epistemic_basis": ["@has_key"],
  "value_system_basis": [],
  "parent_action_hash": null,
  "action_hash": "yza901...",
  "decision_hash": null,
  "child_action_hash": null,
  "domain_pack_hash": "...",
  "provenance_hash": "efg234...",
  "created_ts_ms": 1672531201000,
  "action_structure_hash": "hij567..."
}
```

The presence of action_hash and absence of decision_hash indicate that this evaluation produced an action domain result.

### 6.3 Guarded Action — Guard Fails

The same chain is evaluated in a context where `@has_key` is false:

```json
{
  "version": "noe-prov-v1",
  "chain": "shi @has_key khi sek mek @open_door sek nek",
  "chain_hash": "klm789...",
  "ast_repr": "(guard (unary shi (literal @has_key)) (scope (action mek (literal @open_door))))",
  "ast_hash": "nop012...",
  "context_hash": "...",
  "result": {
    "domain": "undefined",
    "value": null
  },
  "epistemic_basis": ["@has_key"],
  "value_system_basis": [],
  "parent_action_hash": null,
  "action_hash": null,
  "decision_hash": null,
  "child_action_hash": null,
  "domain_pack_hash": "...",
  "provenance_hash": null,
  "created_ts_ms": 1672531202000
}
```

All execution-identifying hashes are null. The provenance_hash is null. The guard failure produces `result_domain = "undefined"`, triggering the non-execution invariant (§4.6).

## 7. Conformance Requirements

An implementation conforms to NIP-010 if and only if:

1. Every evaluation produces exactly one provenance record
2. The canonical chain is computed by the runtime and normalized per §4.1
3. Context hashes (context_hash = H_total per §3, and H_domain_pack) are attached to every evaluation
4. Hash namespaces are computed according to §4.4, with correct mutual exclusivity
5. Provenance hashes are computed per §4.5, with null provenance_hash for non-execution outcomes (`"error"` or `"undefined"`)
6. The non-execution invariant (§4.6) is enforced
7. All hash inputs are serialized as canonical JSON (§4.3)
8. SHA-256 is used for all hash operations
9. The provenance record conforms to the schema defined in §4.5
10. Determinism is achieved: identical inputs produce identical provenance records across implementations

## 8. Backwards Compatibility

NIP-010 introduces the provenance record schema as a new addition to the Noe protocol. Implementations that do not support provenance recording are not compliant with this specification. Systems that need to remain compatible with earlier Noe versions MUST implement a version negotiation mechanism to detect NIP-010 support.

Provenance records are append-only: they do not modify existing evaluation semantics or change the structure of actions or decisions. Systems that ignore provenance records will continue to function correctly, but will not benefit from auditability and cross-agent verification features.

## 9. Security and Safety Considerations

### 9.1 Hash Collision Resistance

All hash computations in this specification use SHA-256, which provides 256 bits of collision resistance. Implementations MUST NOT use weaker hash functions. If cryptographic advances render SHA-256 unsafe, a new NIP MUST be issued to define migration to a stronger algorithm.

### 9.2 Blocked Action Confidentiality

The invariant that non-executing evaluations (undefined or error) produce no execution-identifying hashes prevents information leakage about what actions were attempted. An observer cannot determine from the provenance record alone which actions failed their guards, preserving privacy of failed authorization checks.

### 9.3 Provenance Immutability

Provenance records SHOULD be stored in append-only logs or immutable data structures. If a provenance record is modified after creation, its provenance_hash will no longer match the computed value. Systems SHOULD cryptographically verify provenance_hash values before accepting records as authentic.

### 9.4 Determinism and Reproducibility

The requirement for deterministic provenance generation enables an attacker to precompute provenance records for a given canonical_chain and context. Implementations MUST NOT treat provenance_hash alone as proof of execution; additional authentication mechanisms (e.g., digital signatures) are required for security-critical applications.

### 9.5 Whitespace Normalization

The NFKC normalization and whitespace collapsing rules in §4.1 eliminate ambiguity in canonical chain representation but do not prevent semantic attacks. An attacker could submit two evaluations with semantically equivalent but syntactically distinct canonical chains to produce different provenance hashes. Systems SHOULD validate semantic equivalence independently of provenance records.

### 9.6 Context Fingerprint Security

Context hashes (context_hash and H_domain_pack) are included in all subsequent hash computations. If context_hash is not cryptographically strong, an attacker may be able to find two different contexts that hash to the same value, enabling hash collision attacks. Implementations MUST ensure that context_hash is computed with the same collision resistance as SHA-256.
