# NIP-008: Delivery Semantics

## Abstract

This document specifies the semantics of message delivery and audit event mechanisms in Noe. Delivery operations (`vus`, `vel`, `men`) are unary operators that produce events in the action domain (D_action) rather than truth values. To make delivery conditional, the guard operator `kra` gates delivery on a truth-valued condition; the request operator `noq` creates delivery requests. This NIP defines the behavior of delivery channels, integrity verification, audit tracing, and their interaction with the Noe type system.

## 1. Purpose

The purpose of this NIP is to establish formal semantics for message delivery, receipt verification, and audit event generation in Noe systems. These mechanisms enable distributed communication, integrity assurance, and provenance tracking while maintaining the distinction between action domain events and propositional assertions.

---

## 2. Scope

This NIP covers:

- Delivery event (`vus`) semantics and channel selection
- Receipt event (`vel`) semantics and integrity verification
- Audit event (`men`) semantics and provenance tracking
- Guard-based conditional delivery via `kra` and request delivery via `noq`
- Context requirements for each delivery mechanism
- Multi-agent delivery semantics
- Scope boundaries and context isolation

This NIP does NOT cover the full audit and verification semantics, which are defined in NIP-010 §4.

---

## 3. Definitions

**Delivery Event (E_send)**
: An event produced by `vus` denoting that a message has been placed on a delivery channel for transmission.

**Receipt Event (E_receive)**
: An event produced by `vel` denoting that a message has been received from a delivery channel.

**Audit Event (E_audit)**
: An event produced by `men` denoting the recording of a causal trace or provenance assertion.

**D_action**
: The domain of action-producing terms; delivery and audit operations inhabit this domain rather than the propositional domain.

**Channel (C.delivery)**
: A mechanism for message transmission, selected from categories: direct (in-process), network (remote), shared_memory (IPC), or external (user-defined).

**Integrity Context (C.integrity)**
: Mechanisms for verifying message authenticity, including hash digests, cryptographic signatures, and provenance chains.

**Audit Context (C.audit)**
: The provenance model and verification methods used to establish causal traces and transaction history.

**Context Subsystem**
: A named collection of constraints and capabilities (e.g., `C.delivery`, `C.integrity`, `C.audit`). If a required subsystem is absent, the affected operation is undefined.

**Guard Wrapping**
: The application of `kra` to gate a delivery event on a truth-valued condition. The guard does not convert the event to a proposition — it conditionally passes through or blocks the D_action event.

## 4. Specification

### 4.1 Delivery Event Semantics (vus)

The delivery operator `vus` is a **unary** operator (NIP-005 §4.10.2) with the following semantics:

```
V(vus X) in D_action
```

where:
- `X` is the operand (typically a literal denoting a message or payload, e.g., `@packet1`)
- The result is an event in the action domain D_action

The sender identity is determined by the evaluation context, not by syntax. To bind a sender to a delivery event, use the action constructor `mek` (NIP-005 §4.10.1): `@alice mek vus @packet1`.

**Channel Selection:**
The channel is selected from the available options in `C.delivery`:
- **direct**: in-process transmission (no serialization required)
- **network**: remote transmission (requires serialization and routing)
- **shared_memory**: inter-process communication via shared buffers
- **external**: user-defined channels (behavior defined by implementation)

**Undefined Conditions:**
`vus X` is **undefined** if any of the following hold:
- `X` is not a valid literal or entity in the current context
- No channel in `C.delivery` is applicable
- The evaluation context lacks a sender binding

**Truth Value:**
Bare delivery events (`vus` without guard wrapping) do NOT carry truth values. They are action domain events.

### 4.2 Receipt Event Semantics (vel)

The receipt operator `vel` is a **unary** operator (NIP-005 §4.10.3) with the following semantics:

```
V(vel X) in D_action
```

where:
- `X` is the operand (typically a literal denoting the expected message or payload)
- The result is an event in the action domain

The receiver identity is determined by the evaluation context. To bind a receiver, use `mek`: `@bob mek vel @packet1`.

**Integrity and Authentication:**
When a `vel` event is used as the right operand of a `kra` guard (see §4.4), the integrity and authenticity of the received message are verified using the constraints in `C.integrity`. Verification includes:
- Hash digest comparison (if available)
- Cryptographic signature validation (if required)
- Provenance chain verification (if applicable)

**Undefined Conditions:**
`vel X` is **undefined** if:
- `X` is not a valid literal or entity
- `C.integrity` is absent or incomplete when verification is required

---

### 4.3 Audit Event Semantics (men)

The audit operator `men` has the following semantics:

```
men T → E_audit
```

where:
- `T` is a causal trace, transaction record, or provenance assertion
- `E_audit` is an event in the action domain

**Provenance Tracking:**
`men` uses `C.audit` to determine:
- Which entities and transactions to record
- How provenance chains are constructed
- What verification methods are applicable
- How causal ordering is established

**Full Audit Semantics:**
The complete specification of audit event generation, verification, and causal reconstruction is defined in NIP-010 §4. This NIP covers only the delivery aspect of audit events.

**Undefined Conditions:**
`men T` is **undefined** if:
- `T` is not a valid trace or provenance assertion
- `C.audit` is absent or incomplete

---

### 4.4 Guarded Delivery

Delivery events inhabit D_action and do not carry truth values on their own. To make delivery conditional, Noe uses the **guard operator** `kra`.

In noe-gate, `kra` is a binary conjunction-precedence operator with three-valued guard semantics:

```text
V(P kra A) = A    if V(P) = true
V(P kra A) = undefined   if V(P) = false
V(P kra A) = undefined   if V(P) = undefined
```

The left operand is evaluated as a condition; if true, the right operand (typically a delivery action) passes through. If false or undefined, the entire expression is undefined — the delivery does not occur.

#### 4.4.1 Guarded Send (kra + vus)

```noe
shi @channel_open kra vus @packet1
```

This evaluates `shi @channel_open` as a three-valued condition. If the channel is epistemically confirmed open (true), the delivery event `vus @packet1` is executed. If the condition is false or undefined, the result is undefined and no delivery occurs.

To bind a sender entity:

```noe
shi @channel_open kra sek @alice mek vus @packet1 sek
```

#### 4.4.2 Request Semantics (noq)

The request operator `noq` (registry: g_noq, Tier-1, D_action, type_sig: Action, semantic: Request) constructs a request event from an entity subject and an action target.

```
V(E noq A, C) =
    {type: "action", kind: "request", verb: "noq",
     subject: key(E), target: A, child_action_hash: A.action_hash}
        if E resolves to an entity AND A is an action
    undefined   if E does not resolve to an entity
    undefined   if A = undefined
    ERR_ACTION_MISUSE   if A is not an action AND mode = strict
    undefined   if A is not an action AND mode ≠ strict
```

**Entity Resolution (`key(E)`):**
The left operand is resolved to an entity key as follows:
- If E is a deixis struct: extract `entity` field
- If E is a string in GLYPH_MAP with domain D_e: use as-is
- If E is a literal string: use as entity key
- If E is boolean, numeric, or unresolvable: return undefined (no request produced)

**Example:**

```noe
dai noq mek vus @packet1
```

This creates a delivery request. The subject (`dai`) MUST resolve to an entity, and the right operand MUST evaluate to an action (typically a `mek vus` delivery action). The resulting request event is placed in D_action and references the child action by hash for pointer-stable identity.

**Constraints:**
- Left operand MUST resolve to a valid entity key; otherwise the expression evaluates to undefined
- Right operand MUST be an action (type: "action"); non-action values yield undefined (or ERR_ACTION_MISUSE in strict mode)
- The `child_action_hash` field links the request to the specific action being requested, enabling provenance tracking via NIP-010

#### 4.4.3 Guarded Receipt (kra + vel)

```noe
shi @integrity_ok kra vel @packet1
```

When a `vel` event appears as the right operand of `kra`, the guard condition determines whether receipt proceeds. The integrity and authenticity of the received message are verified using `C.integrity` as part of evaluating the guard condition.

---

### 4.5 Evaluation Rules for Guarded Delivery

For a guarded delivery expression of the form `P kra vus X`:

**Result:**
- **D_action event** if V(P) = true — the delivery event is produced
- **undefined** if V(P) = false — the guard blocks delivery
- **undefined** if V(P) = undefined — the guard is indeterminate; no delivery occurs (safety invariant: undefined MUST NOT yield an action)

The guard condition P is typically an epistemic operator (shi, vek, sha) applied to a context predicate that tests channel availability, integrity, or authorization. The guard does NOT produce truth values about the delivery — it gates whether the delivery action executes.

---

### 4.6 Multi-Agent Delivery Semantics

In multi-agent systems, each agent maintains independent context subsystems:
- `C.delivery[i]` for agent `i`
- `C.integrity[i]` for agent `i`
- `C.audit[i]` for agent `i`

**Cross-Agent Communication:**
When two agents exchange messages:
- If their provenance models are compatible, delivery proceeds normally
- If their provenance models are incompatible, the result is **undefined**

**Provenance Tracking:**
Each agent records the delivery event in its own audit log using `C.audit[i]`.

> **Note:** Context subsystem negotiation between agents (e.g., agreeing on shared integrity or audit models before delivery) is an anticipated extension but is not specified in v1.0. See §5.4 for design rationale.

---

### 4.7 Negation and Delivery Guards

The negation operator `nai` applies to the guard condition, NOT to the delivery event itself:

```noe
nai shi @channel_open kra vus @packet1
```

This negates the guard condition (`nai shi @channel_open`). Since `nai` is a unary operator with higher precedence than `kra`, it binds to the epistemic condition. The result: if the channel is NOT confirmed open, the negated condition is true and delivery proceeds. This pattern is useful for fallback delivery channels.

Negating a bare delivery event (`nai vus @packet1`) is semantically incoherent — `nai` operates on truth values, and delivery events inhabit D_action. The result is undefined.

---

### 4.8 Scope and Context Isolation

Delivery events inside a scope delimiter `sek ... sek` are local to that scope:

```noe
sek vus @secret_msg sek
```

Events within this scope:
- Are evaluated in the local context
- Do NOT leak to the outer scope
- Produce values visible only to the enclosing expression

**Chain Termination (nek):**
Per NIP-004 §4.3, `nek` is a purely syntactic chain terminator with no semantic value. It MUST NOT affect truth values or action semantics. It marks the end of a chain — it does not "halt evaluation" or "abandon" pending delivery events. A delivery chain terminated with `nek` simply ends:

```noe
shi @channel_open kra vus @packet1 nek
```

**Scope Modification (nex):**
The operator `nex` negates the scope of an entity. If a `nex`-modified entity is required for delivery evaluation, the result is **undefined**.

## 5. Rationale

### 5.1 Separation of Action and Proposition Domains

Delivery events produce actions rather than truth values because:
1. Delivery is fundamentally a side-effecting operation
2. Truth values do not capture the essential properties of message transmission
3. Guard-based composition (`kra`) allows flexible gating of delivery on truth conditions without collapsing D_action into the propositional domain

### 5.2 Context Subsystems

Requiring explicit context subsystems ensures:
1. Delivery behavior is explicitly specified rather than implicit
2. Different systems can use different delivery mechanisms without conflict
3. Missing or incomplete contexts produce undefined results (fail-safe)

### 5.3 Integrity Verification

Integrity verification is tied to the guard condition (`kra`) rather than the delivery event itself because:
1. It allows delivery events to be composed without premature verification
2. Different guards may impose different verification requirements
3. Authentication is a property of the condition gating the action, not the event alone

### 5.4 Multi-Agent Semantics

Multi-agent systems require provenance compatibility checks because:
1. Agents may use incompatible audit models
2. Cross-agent communication must establish shared semantics
3. Undefined results prevent silent failures in heterogeneous systems

A future NIP MAY define a negotiation protocol by which agents agree on shared context subsystems before delivery. In v1.0, incompatible provenance models simply yield undefined — the fail-safe default.

## 6. Examples

### 6.1 Simple Delivery

```noe
vus @hello_msg
```

This produces an event in D_action. It is not a proposition and carries no truth value. The sender is determined by the evaluation context.

### 6.2 Guarded Delivery

```noe
shi @channel_open kra vus @hello_msg
```

The epistemic guard `shi @channel_open` is evaluated. If true, the delivery event `vus @hello_msg` is produced. If false or undefined, the result is undefined and no delivery occurs.

### 6.3 Bound Sender Delivery

```noe
shi @channel_open kra sek @alice mek vus @hello_msg sek
```

The `mek` action constructor binds `@alice` as the sender entity to the delivery event.

### 6.4 Guarded Receipt

```noe
shi @integrity_ok kra vel @hello_msg
```

The guard verifies integrity before the receipt event proceeds. To bind a receiver:

```noe
shi @integrity_ok kra sek @bob mek vel @hello_msg sek
```

### 6.5 Delivery Request

```noe
dai noq mek vus @hello_msg
```

This requests that the demonstrative entity (`dai`) perform a delivery. The target MUST be a delivery action.

### 6.6 Negated Guard

```noe
nai shi @channel_open kra vus @hello_msg
```

The negation applies to the guard condition. If the channel is NOT confirmed open, `nai` makes the condition true and delivery proceeds — useful for fallback channels.

### 6.7 Scoped Delivery

```noe
sek
  vus @secret_msg
  vel @secret_msg
sek
```

Both the send and receipt events are local to this scope and do not affect the outer context.

## 7. Conformance Requirements

Implementations of NIP-008 MUST:

1. **Unary Operator Form (§4.1, §4.2):**
   - Implement `vus` and `vel` as unary operators per NIP-005 §4.10.2–4.10.3
   - Return D_action events, not truth values

2. **Channel Selection (§4.1):**
   - Support at least one channel from `C.delivery` (direct, network, shared_memory, or external)
   - Return undefined if no channel is applicable

3. **Guard Semantics (§4.4, §4.5):**
   - Implement `kra` as a binary guard: if the left operand is true, return the right operand; otherwise return undefined
   - NOT treat `kra` as a propositional wrapper or truth-lifter

4. **Integrity Verification (§4.2, §4.4.3):**
   - Perform integrity checks when `vel` is guarded by `kra`
   - Compare message digests and validate signatures per `C.integrity`

5. **Context Subsystems (§4.1, §4.2, §4.3):**
   - Provide explicit `C.delivery`, `C.integrity`, and `C.audit` subsystems
   - Return undefined if a required subsystem is missing

6. **Multi-Agent Isolation (§4.6):**
   - Maintain independent context subsystems per agent
   - Return undefined for incompatible provenance models

7. **Scope Isolation (§4.8):**
   - Isolate delivery events within `sek ... sek` scopes
   - Treat `nek` as a syntactic chain terminator with no semantic effect (per NIP-004 §4.3)
   - Return undefined if `nex` removes a required entity

---

## 8. Backwards Compatibility

NIP-008 introduces delivery and audit semantics that do not exist in NIP-001 through NIP-007. Therefore, backwards compatibility is not applicable.

However, implementations supporting both NIP-007 (numeric logic) and NIP-008 (delivery) MUST:
- Maintain separate evaluation rules for propositional and action domain terms
- Ensure that guard-based delivery (`kra`) does not affect the semantics of core propositions (NIP-001–007)

## 9. Security and Safety Considerations

### 9.1 Message Integrity

Delivery without integrity verification is vulnerable to tampering. Implementations MUST verify message authenticity when `C.integrity` is present and a `vel` event is guard-wrapped by `kra`.

### 9.2 Provenance Spoofing

In multi-agent systems, agents MAY forge provenance records. Implementations MUST validate provenance chains using the signatures and timestamps in `C.audit`.

### 9.3 Channel Availability

If a delivery channel is unavailable, the delivery event is undefined. Implementations MUST handle channel failures gracefully and not silently drop messages.

### 9.4 Scope Isolation

Delivery events MUST remain local to their scope to prevent unintended side effects. Implementations MUST enforce scope boundaries using `sek` delimiters. The chain terminator `nek` is syntactic only and MUST NOT be relied upon for security-critical scope enforcement.

### 9.5 Context Subsystem Completeness

Missing context subsystems lead to undefined behavior. Implementations SHOULD validate context completeness at system startup and warn users of incomplete configurations.
